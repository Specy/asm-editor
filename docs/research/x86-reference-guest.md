# The x86 reference guest, booted

Recorded 2026-10-31 for M0 of [x86-devices-plan.md](../design/x86-devices-plan.md): the pinned QEMU guest of [x86-devices.md](../design/x86-devices.md) ("The pinned guest", [ADR 0067](../adr/0067-x86-devices-follow-a-qemu-guest.md)) booted, probed, and compared with the Core. This is a record of facts, not a set of decisions: where the guest differs from the Core or the design, the design record and the Core are corrected from here.

How the facts were gathered:

- The guest was booted under QEMU 10.2.1 with the configuration below, and the probe (`packages/asm-editor/scripts/reference-guest/probe.c`, a static x86-64 binary) ran in it as root, section by section. Its output is the fixture [`facts.txt`](../../packages/asm-editor/scripts/reference-guest/facts.txt), one fact a line.
- Keys, tablet moves, buttons and wheel notches were injected through QMP's `input-send-event` while the probe read every event device.
- The guest's sound went to a WAV file through QEMU's `wav` audiodev, and the host analysed it for the tones played.
- The same probe binary then ran in the Core (`@specy/x86` as built in `packages/x86/blink-js/dist`, Core d42e3e3, wasm `c1c4fc51…`) through `core-run.mjs`, and `guest.py compare` set the two outputs side by side, device by device. Every "Core" value below is what that run printed, unless it says it comes from the docs or the code.

The QEMU command line, with `$CACHE` the cache folder (`.cache/qemu-guest/` of the main checkout):

```sh
qemu-system-x86_64 -name reference-guest \
  -machine pc-q35-10.2,vmport=off,pcspk-audiodev=snd0 -accel tcg -cpu qemu64 -smp 2 -m 2G \
  -display none -vga std \
  -drive file=$CACHE/guest.qcow2,if=none,id=disk0,format=qcow2 -device virtio-blk-pci,drive=disk0,addr=0x3 \
  -netdev user,id=net0 -device virtio-net-pci,netdev=net0,addr=0x2 \
  -device qemu-xhci,id=xhci,addr=0x4 -device usb-tablet,bus=xhci.0 \
  -audiodev wav,id=snd0,path=$CACHE/out.wav -device intel-hda,id=hda,addr=0x5 -device hda-duplex,audiodev=snd0 \
  -chardev socket,id=ser0,path=$CACHE/serial.sock,server=on,wait=off,logfile=$CACHE/serial.log,logappend=off \
  -serial chardev:ser0 -qmp unix:$CACHE/qmp.sock,server=on,wait=off -pidfile $CACHE/qemu.pid
```

The first boot alone adds `-smbios type=11,value=io.systemd.credential:passwd.plaintext-password.root=reference -smbios type=11,value=io.systemd.credential:firstboot.timezone=Etc/UTC`.

### Where the configuration departs from the design's pins, and why

| Design                                                  | As pinned                                                                                     | Why                                                                                                                                                                                                                                                                                                                                                                                                              |
| ------------------------------------------------------- | --------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| QEMU 10.0, `pc-q35-10.0`                                | QEMU 10.2.1, `pc-q35-10.2`                                                                    | The host's QEMU; settled by the owner. 10.2's tablet has five buttons                                                                                                                                                                                                                                                                                                                                            |
| (KVM implied)                                           | TCG                                                                                           | `dev` is not in the `kvm` group and nothing runs as root. | Debian 13's generic image                               | The `nocloud` image                                                                           | Settled by the owner: the full `linux-image-amd64`, no cloud-init, and nothing on the host to build a cloud-init seed. Its first boot runs systemd-firstboot on the console, which locks root when its password prompt is skipped, hence the SMBIOS credentials on that boot                                                                                                                                      |
| Linux 6.12, or 6.19+ from backports                     | Linux **7.2.11** from trixie-backports                                                        | Backports' newest on 2026-10-31. | `video=320x240`                                         | **`video=320x240M`**                                                                          | A bare size asks for a GTF mode, and Linux 7.2 refuses the one GTF makes at 320×240: `[drm] User-defined mode not supported: "320x240": 60 5263 320 304 336 352 240 241 244 249 0x20 0x6`, its sync starting at 304, inside the 320 visible pixels. fb0 then came up at the EDID's 1280×800 (1280×1600 virtual). `M` asks for CVT, whose blanking is at least 20 % of the line, and gives 320×240 with 320×480 virtual |
| `drm_kms_helper.drm_fbdev_overalloc=200`                | Same name on 7.2                                                                              | `modinfo -k 7.2.11+deb13-amd64 -p drm_kms_helper` lists it; `/sys/module/drm_kms_helper/parameters/drm_fbdev_overalloc` reads 200                                                                                                                                                                                                                                                                                 |
| A USB controller at a fixed address                     | qemu-xhci at 00:04.0                                                                          | The address the Core's provisional links already name, so they stay right                                                                                                                                                                                                                                                                                                                                        |
| HDA controller                                          | `intel-hda` (ICH6, 8086:2668)                                                                 | The owner's command line; the Core's `oss.c` comment says ICH9. | FluidSynth connected to the virtual MIDI port           | A system service on `plughw:0,0`, gain 1.0, all four ports connected                          | So that its sound reaches the HDA card and the recording (Debian's default gain of 0.2, under Master's −20 dB, was too faint to analyse). ## Reproducing it

```sh
cd packages/asm-editor/scripts/reference-guest
python3 guest.py setup          # download, check, provision (about 30 minutes under TCG)
python3 guest.py probe          # boot, probe, inject, record, write facts.txt (about 10 minutes)
node core-run.mjs "$CACHE/www/probe" core.txt    # the same probe in the Core, as built
python3 guest.py compare core.txt               # guest against Core, device by device
```

`README.md` beside the scripts has the details and the commands for poking at the guest by hand. The facts below are from the run that wrote `facts.txt`.

## Surprises

- **A pan waits for the vertical blank on Linux 7.2.** bochs-drm gained a vblank timer after 6.12, and the fbdev emulation's pan is an atomic commit that waits for it. So the frame loop the design teaches, `FBIO_WAITFORVSYNC` then `FBIOPAN_DISPLAY`, runs at 30 frames a second on the reference, and a loop that only pans runs at 60.
- **`video=320x240` does not work.** It is GTF's mode, illegal at small heights at 60 Hz; the design's "the guest builds video= as a GTF mode" holds only for heights from roughly 345 lines up (worked out from `drm_gtf_mode_complex()`, not booted). With `M`, CVT gives any size down to 8×8; CVT rounds the width down to a multiple of 8 (from the code, not booted).
- **FluidSynth and `/dev/dsp` cannot share the guest's card.** The HDA codec has one playback substream.
- **The ALSA minors are dynamic** (`CONFIG_SND_DYNAMIC_MINORS=y`), so `/dev/snd/midiC1D0` is 116:2, not the static scheme's 116:40.
- **udev gives the tablet's `…-mouse` links to `js0`**, the joystick node joydev makes for any device with absolute axes, not to `mouse1`; `mouse1` has no link.
- **atkbd in 7.2 maps F13 to F24** at set-1 scancodes 0x64 to 0x6e and 0x76, taking 0x76 from `KEY_ZENKAKUHANKAKU`.
- A probe-order artifact worth knowing: the `EV_REP` events `EVIOCSREP` queues stay in the keyboard's packet until something closes it, and the first run's first key press arrived with them in front of it (`EV_REP REP_DELAY 0, EV_REP REP_PERIOD 0, MSC_SCAN, KEY_A 1, SYN`), stamped with the time of the `EVIOCSREP`. The probe now closes the packet itself; the Core models this the same way.

## Not checked

- KVM, and timings under it: every duration here is under TCG on a loaded host.
- A QEMU front-end's own key repeats and pointer scaling: QMP sends neither repeats nor window pixels, only the values given.
- Linux 6.12 with this configuration (the vsync and pan behaviour the design first described for it): the guest boots 7.2.
- `video=` sizes other than 320×240 and 8×8, widths that are not multiples of 8, and 1024×1024.
- Events in the Core: `core-run.mjs` injects nothing, so the event tables compare the guest with the Core's README and code.
- `/dev/dsp` underruns, `GETODELAY` during playback, `POST`, the plugin chain at rates other than those probed; MIDI SysEx, running status and real-time bytes on FluidSynth; `EVIOCSCLOCKID` event times; `poll` on input devices with events queued.
- Stock Debian's mixer, whose levels persist across boots through `alsactl store`; the pinned guest does not keep them.

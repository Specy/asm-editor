# x86 Run speed — 2026-10-31

The x86 Core spent most of a recorded step on the Undo history rather than on the instruction. With the default 200,000-entry history it ran about 2,000 instructions a millisecond, and without history about 8 times that. This records what was changed in `@specy/x86` (its CHANGELOG has the list) and how the editor's x86 scheduling was set again for the faster Core.

## Where the time went

V8's sampling profiler on a build with function names (`--profiling-funcs`), an integer loop with the history on:

- **`Finish`, the end of a recorded step: 39%.** It compared and wrote every step's packet.
- **The 17 register reads through a switch, twice a step: 13%.**
- **The run loop: 12%.**
- **Copying the 612-byte FPU, SSE and AVX state, twice a step, and comparing it: 8%.**
- **The instruction handlers themselves: about 5%.**

The changes:

- **The FPU state is taken only for an instruction that can change it.** A build with `-DDEBUGHISTORY_CHECK_FPU` checks the list against every instruction the Core's suite runs.
- **An entry keeps its registers as one raw block.** Its packet is built when it is asked for.
- **Copies and comparisons are a word at a time.** A `memcpy` of a block this small compiles to V8's `memory.copy`, a call out of the module, and the C library's `memcmp` is a call too. Keeping them was the difference between an 8% gain and a 20–40% one.
- **The run loop decodes each instruction once rather than twice.** The breakpoint and timer checks are skipped when there are none.
- **A native slice is 200,000 instructions** rather than 50,000.

## The editor's scheduling

### Why not a longer slice with Undo

- **60,000 and 40,000 were tried with Undo.** Both left the SSE loop's Stop at 108–121 ms under the 4× slowdown.
- **Stop with a history has two parts:**
    - waiting for the slice in progress;
    - 30–55 ms for the Core to free every entry of the history.

    The second part does not shrink with the slice, so it leaves the slice about half of the 100 ms target.

- **Stop is the next thing to speed up here.** A history that freed its entries more cheaply would allow longer slices with Undo too.

A Build's startup code runs with Undo recording paused. The Core records it all the same, at the same cost, so its slices keep the with-Undo cap.

## Caveats

- **The machine was shared.** Other sessions ran test suites during part of the day. Numbers taken under load were discarded, and each table above comes from a run with a load average below 2 at its start.
- **The raw JSON results were not kept.** They were lost when the machine restarted.
- **These are local measurements,** not bounds for every device or instruction mix.

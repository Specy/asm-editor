# Programs

Status: decided in a grill on 2026-10-21; implemented 2026-10-21, browser-checked and reviewed, uncommitted. Plan in [programs-plan.md](./programs-plan.md). Terms are in [CONTEXT.md](../../CONTEXT.md) (**Program**, **Selected program**, **Entry path**, **Entry file**, **Settings**); the model is [ADR 0054](../adr/0054-a-project-holds-programs-identified-by-their-entry-file.md).

## What it is

A rework of the Entry concept. Today a Project has one Entry path, every other assembly File offers "Set file as entry", Build is labelled "Build entry" wherever the displayed File is not the Entry, the Explorer flags and offers the Entry on every row, and Compile silently moves the Entry to its Generated assembly. Instead a Project holds **Programs**, one per Entry file, and a picker beside the Terminal chooses among them.

## Decisions

1. **Name.** The new unit is a **Program**; **Project** keeps meaning the record the editor saves, opens and shares. Renaming today's Project to "workspace" would touch `/projects`, the IndexedDB store, archives, share links, exams, courses and about twenty ADRs, and change a word people already have saved work under.
2. **Identity.** A Program is identified by its Entry file: a File is the Entry of at most one Program, and a Program has no name of its own. Renaming the File renames the Program and deleting it deletes the Program. A named Program pointing at an Entry path (several per File, as IDE run configurations) was rejected for now: it needs naming, renaming and a rule for what deleting the File does to each. An optional name can be added later without breaking this; taking names away could not.
3. **What a Program owns.** Its **Settings** (all of them: assembler profile, Runtime library link, undo history, the Screen and FileSystem undo budgets, Arguments), its **Display configuration** and its **Testcases**. The Project keeps its **Target**, **Files**, Compilation records, name, description, exam metadata and editor state (open tabs, active tab, File views). A Testcase checks what one program does with an input, so Project-wide Testcases would run against whichever Program is selected.
4. **Target stays on the Project.** See Deferred.
5. **What Build builds.** A pane's Build button builds the Program whose Entry file the pane shows, and selects it. The pane's Test, beside it, does the same: it tests and selects that pane's Program, and shows while that Program has Testcases (`hasTests`), since a Test beside a Build of `sort.c` that ran `main.s`'s Testcases would be the old ambiguity again. What has no Entry file to go by uses the **Selected program**: the Build shortcut (Shift+B, `BuildCode`) and the Testcases panel's Run. A pane showing any other File (an included File, a linked unit, a header, C source) has no Build outside a Debug session; Shift+B still builds from there. The "Build entry" label is gone: the button on a File always runs that File's Program. Rejected: Build only on the Selected program's Entry (a second way to say the same thing, and an Entry file with no Build until the picker changes), and Build on every Entry building the Selected program (today's "Build entry" again).
6. **Making a Program.** A new Project starts with one Program, `main.<ext>`; Compile makes one for C and C++ (see below). Any other File becomes a Program through the Explorer's context menu, "New program from this file", which takes the place of "Set as entry file" and is offered on assembly Files and Executables that are not already an Entry; it makes the Program and selects it. The Explorer rows lose their hover flag and the dock loses "Set file as entry". The x86 import question "Make X the Entry file?" becomes "Create a program for X?". Rejected: a Build on every assembly File no Program reaches (x86 follows only `%include`, so a unit `main.asm` links as an archive member would read as unreached and offer a Program it must not be; a MIPS File meant to be included would too), and a "New program…" item in the picker (hidden while there is one Program, when it is needed). Not taken up: a "New program" flow in the Explorer's New file.
7. **Losing a Program.** Apart from "Remove program" (11), only a host deletion of the Entry file deletes its Program: the Explorer, the Coding agent, a delete before an upload. A running program that removes or renames its own Entry through the FileSystem leaves the Program in place with its Entry missing, because instruction Undo restores the File and would otherwise bring it back without its Settings and Testcases; a host rename moves the Program, a program's rename does not. A missing Entry can also arrive in an old archive or share link, so it stays a shown state (in the picker, and as the Build error) rather than an impossible one. The delete prompt names what goes with the File when the Program has decided Settings or Testcases ("Delete main.s? This also deletes its program: its Settings and 3 Testcases."). Deleting the Selected program selects the first one left. A Project may have no Program: Shift+B, Test and the Settings and Testcases panels then say how to make one. Forbidding it would block deleting `main.s` to upload its replacement.
8. **The first Program makes itself.** While a Project has no Program, a host action that adds a qualifying File, or renames one into qualifying, makes it the Entry of a new Program and selects it: New file, upload, drop, a rename such as `notes.txt` to `a.s`, the Coding agent. Qualifying means an assembly extension other than `.inc` (`.s`, `.asm`, `.mips`, `.riscv`, `.m68k`, `.z80`) or a supported Executable in an x86 Project; an extension-less File, an `.inc` and C or C++ source never qualify, although the editor routes the first two as assembly. When one action adds several, a File named `main.<ext>` wins, else exactly one qualifying File does, else none is made and the person uses "New program from this file"; an alphabetical guess would pick one of `bubble.s` and `quick.s` for no reason. A running program's writes never make a Program (7), and once a Project has one, new Files never make one on their own.
9. **Programs from C and C++.** Compile makes a Program whose Entry is its Generated assembly when none has it and that assembly defines a global `main`, and selects it; a recompile of a source whose Program exists selects that Program, `main` or not, since its identity is the Entry. A companion File without `main` (an `add.c` that a hand-written `main.asm` links as needed on x86, or that `main.s` includes on MIPS) compiles and leaves the Programs and the selection alone, which also retires the Playground's own keep-the-authored-entry rule (`PlaygroundSession.compile`). Compile no longer sets a Project-wide Entry (`project.entry = outputPath` in `compileProjectSource`). The Program needs no Setting for its library, as its Compilation record pins its Runtime ABI whatever `linkRuntimeLibrary` says. The picker names it by its source, `sort.c`, while the Compilation record names a source File that exists, else by its Entry path, `sort.c.mips`, so `main.c` and `main.s` stay apart and the label matches the Command line's `./main`. Deleting the source leaves the Program (its identity is the Entry, 2), whose assembly goes stale as today; deleting the Generated assembly deletes the Program with 7's prompt, and the next Compile makes a fresh one with default Settings and no Testcases. The C or C++ pane keeps Compile and has no Build, since it is no Entry; after a Compile the assembly opens beside it with Build, as today, and Shift+B builds the Program just selected. Rejected: Build on a C pane whose Program exists, as compile-if-stale-then-build, which bends 5 and adds a third state to the dock. Rejected for companions: a Program on every Compile (an `add.c` Program that cannot run, and the selection moved off `main.asm` each time, today's mess moved), and no Program when an existing one already reaches the File (x86 follows only `%include`, so whether `main.asm` links `add.c.asm` is known only after a link).
10. **The picker.** At the right end of the bottom panel's tab strip, before the run info (`BottomPanel.svelte`), on every tab, hidden while the Project has fewer than two Programs; on a phone, where the strip already has no room for the run info, it shows the label alone. It lists each Program by its label (9), a missing Entry marked missing. During a Debug session it shows the session's Program and is disabled, as the Files are locked: Stop, then switch. Picking leaves the panes as they are, since the Selected program is chosen independently of the Displayed file, so a pane showing `main.s` still builds `main.s` (5) and selects it again; opening the Entry on a pick was rejected because for C it would open `sort.c.mips` over the `sort.c` being edited, and it would take away a header being worked on. The Terminal's Command line, which already edits the Arguments, is the Selected program's (`./sort …`). The Settings and Testcases panels name the Program in their header (`Settings · sort.c`) whenever there is more than one, so whose Settings are being edited shows with the bottom panel folded.
11. **The Explorer.** Every Entry file's row carries a mark, with one Program too so a learner sees what runs, in the accent colour for the Selected program; no row has a hover button. An Entry file's context menu offers "Remove program", which removes the Program and keeps the File, with 7's prompt when Settings or Testcases go with it; without it a File made a Program by mistake would stay one until deleted. The missing-Entry warning at the top stays, one line per Program whose Entry is missing ("Program entry missing: main.s"), since with one Program the picker is hidden and only the Build error would say it otherwise.
12. **The Interactive editor.** A Playground has exactly one Program, its authored entry: Build is on every assembly tab and labelled "Build", never "Build entry", C and C++ tabs keep Compile, and there is no picker, "New program" or "Remove program". The Workbench's Build-only-on-Entry rule (5) exists to tell Programs apart, and a Playground has one; with no Build shortcut there, a reader on `macros.inc` would otherwise have no way to build. Several Programs in one Playground, for a lecture comparing two, is an authoring feature left out of scope.
13. **Stored shape.** `ProjectData` replaces its top-level `entry`, `settings`, `testcases` and `display` with `programs`, a map from Entry path to `{ settings, testcases, display? }` like `files`, so two Programs with one Entry cannot be written down (2), and `selectedProgram`, an Entry path saved like `activeTab`. The picker orders Programs by label, not key order, and "the first one left" (7) is the first in that order. `normalizeProjectData` turns the old top-level fields into one Program, an Entry naming a missing File included (7), so IndexedDB records, share links, exported files and archives of every earlier version load with no database upgrade step; an old Project's other Files are made Programs from the context menu. IndexedDB stores the new shape; archives and the single exported file keep the oldest-version rule archives already follow (`projectArchive.ts`): a Project with one Program is written in the earlier shape, so older editors keep reading the common case, and only several Programs take a new archive version. The single-file export stays offered exactly when the only File is the only Program's Entry. Rejected: always writing the new shape, one writer fewer but no archive readable by an older editor.

## What follows without a decision

- **Coding agent.** Its effective Entry (`effectiveEntry` in `DefaultCodingAgent.svelte`, read by the tools through `getEntryPath`) is the Selected program's; its deletions and creations are host actions, under 7 and 8.
- **Exams.** A v2 exam's coding section is one `starterCode` string and its Testcases (`exam.ts`), so an exam's Project has exactly one Program and nothing changes for it.
- **Earlier records.** [ADR 0013](../adr/0013-project-is-a-record.md) lists Settings, Testcases and Display configuration as parts of the Project record; they are now parts of its Programs, still structured fields and still never Files. [ADR 0014](../adr/0014-settings-split-by-effect.md)'s Settings move from the Project to the Program unchanged otherwise. [ADR 0033](../adr/0033-x86-links-the-entry-and-takes-other-files-as-needed.md)'s "two programs can share a Project with the Entry choosing which runs" becomes two Programs, with no change to linking.
- **Build beside a document.** [workbench.md](./workbench.md)'s "No Build beside a document" (`offersBuild`) is subsumed: an Entry is assembly or an Executable, so a pane showing a document is never an Entry's pane and has no Build either way.

## Deferred

- **A Target per Program** (several ISAs in one Project, the picker switching the machine). Deferred by the owner on 2026-10-21, not rejected. It needs, first, a language of its own for every assembly File: today any `.asm`, `.s`, `.inc` or extension-less File is the Project's Target's assembly (`editorFileRouting.ts`), `.s` and `.inc` belong to no one Target, and RISC-V and RISC-V-64 share `.riscv`. Then a picker change would rebuild the Emulator, the language service worker, the register and memory views, the Screen, the Documentation panel and C/C++ language help, which are each created once per Project language today (79 reads of `project.language` in 26 files), and the `/projects` badge, templates, archives, share links, exams, course embeds and agent tools would stop treating the Target as the Project's. The C side is nearly ready: Compilation records are keyed by source path and Target, and Generated assembly paths differ per Target. Done later, a Program gains an optional Target defaulting to the Project's.
- **Named Programs.** Several Programs over one Entry file, as IDE run configurations (`main.s` with two sets of Arguments). An optional name added to a Program would allow it without breaking 2.
- **Several Programs in one Playground** (12), for a lecture that compares two.

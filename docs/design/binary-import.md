# Binary import

Status: implemented on feat/binary-import, locally, in both repositories: M1 to M13 are done and verified in the browser (see the [Implementation report](#implementation-report)); the x86 Core's 7.0.0 is prepared but not released, and nothing is pushed. The spike (2026-10-12, [Spike results](#spike-results)) confirmed decision 3's precondition and revised decision 6; the [implementation plan](./binary-import-plan.md) is what was built. Terms are in [CONTEXT.md](../../CONTEXT.md) (**Executable**, **Listing**, **Invented name**, **Bundled library**, **Library code**, **Patch**, **Command line**, **Arguments**); the model decision is [ADR 0044](../adr/0044-an-executable-is-a-project-file-a-build-loads.md) and the naming one [ADR 0045](../adr/0045-invented-names-are-frozen-words-from-file-addresses.md). The user Documentation is the x86 **Executables** Chapter (`packages/asm-editor/src/lib/documentation/x86/executables.md`).

## What it is

Opening a compiled program, for which there is no source, in the editor: reading its machine code as assembly and running it under the debugger. The use cases are CTF challenges (rev: understand a binary to find the flag; pwn: debug a vulnerable binary locally) and learning how compiled programs look from the inside.

## Decisions

1. **Purpose.** A place to learn reverse engineering, good enough for beginner-to-intermediate CTF rev challenges and for debugging pwn challenges locally. It sits beside Ghidra, IDA and Binary Ninja rather than replacing them: what it adds is what the editor already has (the **Documentation**, the Courses, stepping back through the Undo history, an approachable debugger). Practitioner features those tools are built around (cross-references, renaming, control-flow graphs, scripting, a decompiler) are not goals; any of them can be added later on its own merits.
2. **Accepted binaries.** x86-64 Linux ELF only, both `ET_EXEC` and position-independent (`ET_DYN`) executables, read and run on the x86 **Core**: it is most CTF binaries, it is the x86 **Reference environment** (a Linux process on a tty) the **Documentation** and the x86 Language course already describe, and Blink already loads it. Not now: 32-bit i386 ELF (Blink refuses it, `loader.c:325`; running it needs the i386 loader and the `int 0x80` syscall ABI in the Core), other architectures (MIPS and RISC-V have no ELF loader and their Cores speak MARS and RARS syscalls, not Linux's; ARM and AArch64 live in unicorn-edu, outside the editor), and other formats (PE, Mach-O). The design does not assume every binary it may one day show can run, so a read-only view of those can be added without reshaping it.
3. **Linking.** Statically and dynamically linked binaries both run. A dynamic binary names its dynamic linker in its `PT_INTERP` header (`/lib64/ld-linux-x86-64.so.2`), which loads `libc.so.6` and fills in the addresses its PLT stubs jump through; Blink already follows `PT_INTERP` and opens the linker from the program's filesystem (`loader.c:437`). Five libraries from one recent Ubuntu release are bundled (shipped and resolved by the x86 Core package, [the plan](./binary-import-plan.md)'s planning decision 1), each fetched only when a binary needs it and put where the binary expects it: glibc's dynamic linker, `libc.so.6` and `libm.so.6` (LGPL-2.1), and GCC's `libstdc++.so.6` and `libgcc_s.so.1` (GPL-3.0 with the GCC Runtime Library Exception), which C++ binaries need (spike result 8; confirmed 2026-10-12). A binary built against a newer glibc than the bundled one stops in the dynamic linker (`version 'GLIBC_2.xx' not found`), so the bundle tracks a recent release. Most CTF binaries are dynamically linked against glibc, so without this the feature would open few real challenges. This glibc is unrelated to the x86 **Runtime library**: an imported binary was linked elsewhere, against glibc, and cannot use the editor's library. Precondition: a spike shows glibc's startup (its setup syscalls and its CPU feature checks) works in Blink's browser build, which disables threads, MMX and BMI2; if it does not, the first version is static only and this decision records why.
    - **First probe (2026-10-12, not the spike).** A 20-line crackme built with the host's GCC against glibc 2.43, run through `X86Emulator.loadElf` in Node. As a static PIE it loads at `0x88000000`, prints nothing yet (stdout is buffered) and asks for input after 27,550 instructions, then dies with `SIGSEGV` (`SEGV_ACCERR`) 584 instructions after the input arrives, before its output is flushed. As a dynamic PIE, with the host's `ld-linux-x86-64.so.2` and `libc.so.6` written into the module's filesystem by hand, it fails to load (`load-fail`), possibly because the runtime resets its filesystem at each start. So even static glibc does not run cleanly yet, and the spike has real work in it.
    - **Spike (2026-10-12).** See [Spike results](#spike-results). Dynamic glibc programs run unchanged on today's Core once the libraries survive the runtime's per-start filesystem reset; static ones need a one-line Core fix. The precondition holds.
4. **Place in the model** ([ADR 0044](../adr/0044-an-executable-is-a-project-file-a-build-loads.md)). The binary is an **Executable**: a **File** of an x86 **Project**, named by the **Entry path**. A Build of a Project whose Entry file is an Executable loads it instead of assembling, and the **Debug session** that follows is an ordinary one. Everything a Project carries keeps working around it, and that is what a CTF workflow needs: the **FileSystem** gives the program the files it opens (a `flag.txt` beside it), the **Terminal** the input it asks for, **Testcases** check a solution (input `hunter2`, expected output `Correct!`), other Files hold notes, and saving, archives and sharing are unchanged. Files already hold bytes (base64, `projectFiles.ts`), within the 16 MiB a Project's Files may take together (`FILE_BYTE_LIMIT`, checked as a running total in `cleanFiles`): a typical CTF binary is tens of kilobytes, a static glibc one about 1 MB and a static Go one 2 to 10 MB. Rejected: a separate inspector outside Projects, which would duplicate the Terminal, the FileSystem, saving and sharing; and a new **Target**, since the machine and environment are the x86 ones and only the input differs.
5. **The Listing is a view.** Opening an Executable shows its **Listing**: the disassembly of its code, one line per instruction, generated when it is shown and never saved. It is read-only but an ordinary editor text model, so search, highlighting and **Documentation** on hover work, and so should the label navigation assembly Files get (`assemblyLanguageRegistry.ts` registers definition and reference providers): go to a label from `call FUN_brave_otter`, and list the lines that name it, which gives cross-references within the Listing as text, without the analysis decision 1 leaves out. A **Breakpoint** on it is held as an address in the Executable (its link-time virtual address, relocated to where the program is loaded), not a line, as debuggers do for binaries (`break *0x401136`), so it survives a Listing whose lines move when its format improves. Rejected: writing the Listing out as a generated File (like **Generated assembly**), which saves derived data into the Project (a static binary's Listing runs to megabytes against the 16 MiB File limit), goes stale when the Executable is replaced, and invites edits that cannot be built, since a disassembly does not in general reassemble into a working program. Same reasoning as [ADR 0028](../adr/0028-persist-compilation-records-with-transient-source-maps.md): keep the record, derive the rest.
6. **Syntax and decoder** (revised 2026-10-12 after the spike). The Listing, the History and the Call stack show instruction text from Zydis (MIT, C99, every x86 extension through AVX-512) built into the x86 **Core**, formatted as NASM-flavoured Intel syntax, the syntax the x86 **Target** assembles, teaches and documents; Blink keeps executing. The spike (result 7) showed Blink's own disassembler cannot carry a Listing: `endbr64`, the first instruction of every function in a modern binary, prints as `pause edx`, RIP-relative operands print an absolute address after `rip+`, AVX and AVX-512 instructions decode as unrelated legacy ones (and can desynchronise what follows), and vector registers keep AT&T's `%`. The Listing therefore shows what a real CPU decodes, and the two decoders can disagree only where Blink executes wrongly or cannot execute (AVX, which Blink's CPUID does not offer); there the Listing is the right one to read, and the **Log** names an instruction Blink could not run (decision 17). Rejected: fixing Blink's printer (an x86 decoder to maintain, and AVX would still show no names), and Zydis for the Listing only, which would print one instruction two ways in two panels. An AT&T option is not planned.
7. **Invented names** ([ADR 0045](../adr/0045-invented-names-are-frozen-words-from-file-addresses.md)). The Listing labels what the symbol table names, library calls by their dynamic symbols (`call strcmp@plt`, which survive `strip` because the dynamic linker needs them), and, where the binary has no name, invents one: a function at every call target and `main` from the `__libc_start_main` pattern in `_start` (its address is passed in `rdi`). One pass over the decoded instructions; no control-flow graph or recursive-descent analysis (decision 1). Invented names use Ghidra's prefixes (`FUN_` for functions) followed by made-up words rather than an address (`FUN_brave_otter`, not `FUN_00401136`), because words are quicker to spot and to talk about than hex. The address stays visible in the Listing's address column and in the label's hover. Consequences:
    - **Deterministic.** The Listing is never saved (decision 5), so a name must come out the same on every open and for everyone opening the same Executable: it is derived from the function's address in the file (its link-time virtual address, so it does not depend on where decision 10 loads the program), not drawn at random, and two addresses that land on the same name are resolved in ascending address order, the later one taking the next name in a fixed sequence.
    - **Frozen words.** Changing the word lists or the derivation renames every function in every saved Project, breaking any note that mentions one. The lists and the derivation are versioned and never edited in place.
    - **Obviously meaningless.** The words must never read as a finding: adjective and animal pairs, with nothing that sounds like analysis (`check`, `key`, `secret`, `flag`, `crypt`, `init`, `main`, `exit`, `error`) and nothing that reads as an instruction or register (`push`, `call`, `test`, `loop`, `ret`).
8. **Block labels.** A jump target inside a function is a numbered local label, `.LAB_1`, `.LAB_2`, … in address order within its function, in NASM's local-label syntax: `jz .LAB_3` inside the function, `FUN_brave_otter.LAB_3` from outside it. A function has many more jump targets than there are functions, and what a reader needs from one is where it goes: a number written below its own label jumps backwards, which is how a loop reads, and the leading `.` says the jump stays in the function. Words are kept for functions, which are what people remember and talk about. Rejected: words for blocks too (a dozen unrelated animals per function, saying nothing about direction) and Ghidra's `LAB_<address>`.
9. **Data.** The Listing resolves references to data and lists the data sections after the code. A RIP-relative operand (`[rip+0xe9e]`) is shown as the label it reaches (`lea rdi, [rel s_Enter_password]`), with the text as a comment when the target is a string (`; "Enter password: "`). `.rodata` and `.data` are listed as data lines (`s_Enter_password: db "Enter password: ", 0`, bytes otherwise) and `.bss` as reserved space. A string is named from its own text with Ghidra's `s_` prefix (`s_Enter_password`, truncated, a clash taking a number), which is not invented since it is what the bytes say; any other data label gets words with `DAT_` (`DAT_calm_lynx`) under decision 7's rules. Strings are what a reverser looks at first (`"Correct!"` leads to the comparison before it), and with them in the Listing as text, the editor's search does what the `strings` tool does. Not now: a Strings panel, whose natural next step, the code that uses a string, is a cross-reference (decision 1).
10. **Addresses.** An Executable runs at gdb's addresses with randomization off, the layout of practically every pwn tutorial and writeup: a PIE at `0x555555554000`, the dynamic linker and libraries just under `0x7ffff7ffe000`, the stack under `0x7ffffffff000`; a non-PIE `ET_EXEC` where its headers say (usually `0x400000`). The Listing shows these runtime addresses, so the program counter, Breakpoints and the Listing agree, and a learner following a gdb writeup sees the same numbers and learns what program, library and stack pointers look like (`0x55…`, `0x7f…`). A fixed layout keeps Breakpoints, invented names and notes stable from run to run. Core change: Blink's browser build loads a PIE at `0x88000000` today (its default layout scaled into the host's 32-bit address space, `map.c:133`), with no randomization because it has no linear mapping; it keeps its own page tables, so the higher addresses should be reachable, which the spike checks. Not now: randomization (ASLR) as a Setting, which could later demonstrate the defence pwn challenges defeat. Rejected: Blink's own layout (matches no other tool) and Ghidra's `0x100000` PIE base (matches Ghidra's listing but not a real run's libraries and stack).
11. **Start and library code.** Code outside the Executable (the dynamic linker, libc and any other shared library) is treated as **Runtime library** code is for a compiled program today. The dynamic linker and the program's start code run outside the Undo history, and a Build stops at `main` when the Listing knows it (a symbol, or the `__libc_start_main` pattern of decision 7), at the Executable's entry point otherwise; that is gdb's `start` and the editor's own compiled programs. A Step over a call into a library runs until control is back in the Executable: the call returns, or the library calls into it (`__libc_start_main` calling `main`, `qsort` calling a comparison function). A Breakpoint is only ever in the Executable. The existing Preference that steps into Runtime library code also steps into these libraries, and its label has to stop naming the Runtime library, since glibc is not it. The `_start` → `__libc_start_main` → `main` path stays in the Listing, and a Breakpoint on `_start` still stops there. Not addressed: in a static binary libc is part of the Executable, so its functions are ordinary (and, stripped, invented) code; telling them apart needs signature matching (Ghidra's Function ID), which is out of scope. Rejected: stopping at the dynamic linker's first instruction and stepping into everything, which buries the program under library code the Listing cannot show and can fill the 200,000-step Undo history before `main`.
12. **Arguments.** A program's command-line arguments (`argv[1]` onwards; many crackmes take the password as `./crackme hunter2`) are a **Setting** of every x86 Project, not only of one whose Entry file is an Executable, since an assembled x86 program is a Linux process too and the x86 course can then teach `argc` and `argv`. They are edited on the **Terminal**'s **Command line**, its first line, `$ ./crackme hunter2`: the program's name is fixed and the rest is typed as in a shell (quotes keep spaces). Each run's output follows the command it started with, as in a shell session. During a **Debug session** the line is locked and shows what that run started with; an edit applies from the next Build, as with Files. It is not a shell: Build and Run start the program, and no other command is accepted. Saved with the Project, also listed in the Settings dialog, and a **Testcase** can bring its own Arguments (`./crackme hunter2` prints `Correct!`). `argv[0]` is the program as typed in a shell: the Executable's path (`./crackme`), or for an assembled program the Entry path without its extension (`./main`), instead of today's `/program`. The Core already takes arguments (`setEmulationArgs`); the editor has never passed any. Not now: editable environment variables; a program gets a small fixed set.
13. **Patching from the Listing.** During a **Debug session** a person can retype an instruction of the Listing (`jne .LAB_2` as `je .LAB_2`): the editor assembles it with the NASM the x86 **Core** already ships and writes the bytes into memory as a **Poke**, filling a shorter encoding with `nop` and refusing a longer one with the reason (the instruction after it would be overwritten). It is undone like any Poke and gone at the next Build, and the Listing marks the patched line. This is the one way the Listing is editable, a narrow exception to decision 5: only during a session, only as Pokes, never into the Executable File. Flipping the jump after a `strcmp` is among the first things a crackme teaches, and Undo makes it safe to try. Poking raw bytes in the memory view keeps working, but asks the person to know that `jne` is `75`. Not now: permanent patches (a list saved in the Project and applied on top of the untouched Executable at each Build, with a download of the patched binary); since the File is never modified, they can be added later.
14. **Decompiler: later, with a set direction.** Not in the first version, which teaches reading assembly; a decompiler lets a beginner solve a crackme without ever reading it, and it is a large dependency on an alpha port before the basics are proven. The direction, so the first version does not make it hard: an optional pane of C-like pseudo-code for the function the person is in, from Ghidra's decompiler (C++, Apache-2.0) compiled to wasm with its SLEIGH processor descriptions (Pyre shows this runs in a browser, as an alpha), fetched only when opened, and linked line by line to the Listing the way the Workbench already pairs a C File with its **Generated assembly** (`mappingPair.ts`). The Listing's lines therefore keep a stable address range each, which is what such a map needs.
15. **Getting a binary in.** An ELF is recognised by its first bytes (`\x7fELF`, then its class and machine), never by its name, since CTF binaries rarely have an extension (`crackme`, `chall`, `vuln`). The Projects page's Import, which takes Project archives and text sources by extension today (`routes/projects/+page.svelte`), also takes an ELF and creates an x86 Project named after the file with it as the Entry file. Uploading an ELF into an x86 Project, which the Explorer already does for any bytes, offers to make it the Entry file. Both places explain an ELF the editor cannot run when it arrives (32-bit, another machine, not an executable) instead of leaving it to a failed Build. Not now: a challenge archive (a zip or `.tar.gz` that is not a Project archive) opening as a new Project of its files, which needs a rule telling it from a Project archive; dragging the extracted files into the Explorer works meanwhile.
16. **Safety and the Executable's own File.** A running program is interpreted by Blink inside the browser's WebAssembly sandbox, with no sockets (`config.h:18`) and no files but the Project's and the bundled glibc, so a CTF binary cannot reach the person's computer; it is not a malware lab (most malware targets Windows, needs the network and checks for emulation). Sharing hosts nothing: a share link carries the Project in its URL, capped at 32,000 characters (`utils.ts`), so most Executables travel as `.asmproj` archives. An interactive run shares the Project's Files as any program's does, with one exception: the running Executable's own File can be read (some challenges check their own bytes) but not written, which fails with `ETXTBSY` as on Linux, nor deleted or renamed, which fails although Linux allows it, a documented deviation under [ADR 0035](../adr/0035-environments-match-their-reference.md) so that a challenge that deletes itself does not take itself out of the Project. Rejected: running Executables on a throwaway copy of the Files as Testcases do, which would treat the same Project's Files differently by whether its Entry is assembled or loaded, while Undo already reverses a session's file changes within the FileSystem budget.
17. **Invisible debugger, named missing syscalls.** A program cannot tell it is being debugged: it runs as a Linux process nobody traces, which is the x86 **Reference environment** ([ADR 0035](../adr/0035-environments-match-their-reference.md)). The editor's debugger sits outside the emulated machine, its Breakpoints are not `int3` bytes in memory and nothing uses ptrace, so the classic checks already miss it except one: Blink has no `ptrace`, so `ptrace(PTRACE_TRACEME)` fails with `ENOSYS` (`syscall.c`, the `DefaultCase`), which reads as "a debugger is attached". Core change: `PTRACE_TRACEME` succeeds the first time and fails with `EPERM` after, as on Linux. Timing checks still see host time (**Program time**), so single-stepping through one can trip it, as it would under gdb on real hardware. A learner who wants to practise a bypass reads the check in the Listing and patches it (decision 13). Separately, the first time a run calls a syscall the **Core** does not implement, the **Log** names it (`ptrace` is not implemented; the call returned `ENOSYS`); the program's view is unchanged, since Linux answers `ENOSYS` silently too. Rejected: failing like gdb, which forces a bypass on every anti-debug challenge although nothing traces the program, and leaving `ENOSYS`, an error Linux never gives for this call.
18. **Library Listings.** When execution is inside a shared library (stepping in with the Preference on, a Pause, or most importantly a crash, as when overflowed data reaches `strlen` or `printf` in a pwn challenge), the editor shows that library's Listing, read-only, under a path outside the Project (`@lib/libc.so.6`), as the **Start unit**'s `@runtime/` Files are shown today, with the current instruction highlighted. A library is an ELF with every exported function named by its dynamic symbols, so the same Listing machinery reads it; its Listing is generated the first time execution needs it. Breakpoints stay in the Executable (decision 11): stopping at `strcmp` to read the password from its arguments is a Breakpoint on the `call strcmp@plt` line, where `rdi` and `rsi` are already set. A library's code is far larger than a challenge's (libc's is about 2 MB), so generating and showing its Listing quickly is a planning concern. Rejected: no view, which leaves "where did it crash?" with only the History and the Call stack's function name.

## Deferred

- **Export to an assembly File.** Writing the Listing out as a NASM File a person edits and builds. Once an edit moves code, every reference to what moved must be a label, and machine code does not say which numbers are addresses (`mov edi, 0x404040`), nor where `switch` tables of addresses sit in `.rodata`; a dynamic binary also needs its dynamic-linking metadata recreated. This is reassembleable disassembly, a research problem (GrammaTech's ddisasm is the reference tool and still has failure cases), and a rebuilt program that breaks far from the person's edit is a failure a learner cannot diagnose (decision 1). An export with no promise to rebuild was also rejected: as a modify-and-rebuild workflow it would fail often and mysteriously. If wanted later, a real round trip is a project of its own, starting from ddisasm's approach and linking against the bundled glibc. Decision 13's patches cover the classic crackme moves meanwhile.
- **Permanent patches** (decision 13).
- **The person's own `libc.so.6` and dynamic linker** taking precedence over the bundled glibc, which pwn challenges ship because exploits depend on one exact libc (decision 3).
- **Randomization (ASLR)** as a Setting (decision 10).
- **A Strings panel** (decision 9).
- **Editable environment variables** (decision 12).
- **Recognising libc in a static binary** by signature (decision 11).
- **i386, other architectures, PE and Mach-O** (decision 2).
- **Challenge archives** opening as a Project (decision 15).
- **DWARF debug info.** A binary built with `-g` names the source file and line of each instruction, and the x86 Core already reads DWARF lines for the editor's own builds, so an Executable's source Files, when the Project holds them, could be paired with its Listing and take Breakpoints. CTF binaries almost never carry it, the compile-and-read lesson already exists through **Source compilation**, and the decompiler (decision 14) needs the same pairing of C with the Listing, which is better built once. The symbol table's names are used meanwhile (decision 7).

## Spike results

Run on 2026-10-12 in Node against `@specy/x86` 6.3.0's `dist`, with test binaries built by the host's GCC 15 against Ubuntu's glibc 2.43 (a 20-line crackme, a hello with `atexit`, a `libm` program and two C++ programs, each static PIE, static non-PIE or dynamic PIE as noted). Core changes were tried in a scratch copy of `libblink` rebuilt with emsdk 6.0.9 and swapped into a copy of `dist`; nothing in the repository or the submodule changed. Scripts and binaries were in the session scratchpad and are not kept.

1. **Dynamic glibc programs run on today's Core**, once `ld-linux-x86-64.so.2` and `libc.so.6` are written after `startProgram`'s `resetFileSystem` (the runtime wipes everything but `/dev`, `/proc` and `/tmp` at each start, which is why the first probe failed to load). The crackme prints `Enter password: Correct!` for `hunter2` and `Wrong!` otherwise; the hello prints, runs its `atexit` handler and exits 3. The dynamic linker's startup costs about 100,000 instructions (`hello-dyn` runs 103,515 in all); stepping all of them one at a time from JavaScript took 0.56 s.
2. **Static glibc programs crash at exit on today's Core; one line fixes it.** Linux starts a process with `rdx = 0`, which `_start` passes to `__libc_start_main` as the dynamic linker's finaliser (`rtld_fini`), registered with `__cxa_atexit` when non-zero. Blink sets `rdx` to the address of the program path string (`argv.c`, `Write64(m->dx, dx)`, a Cosmopolitan convention), so glibc registers that string as an exit handler and jumps into the stack at exit (`SIGSEGV`, `SEGV_ACCERR`). Setting `rdx` to 0 except for Cosmopolitan programs (`m->system->iscosmo`) makes static PIE and static non-PIE programs, including the crackme, run to a clean exit. Dynamic programs were unaffected because the dynamic linker sets `rdx` itself.
3. **Any second shared library aborts Blink, on today's Core and with the layout change alike.** A C program linking only `libm`, and C++ programs (`libstdc++`, `libm`, `libgcc_s`), stop with a wasm trap (`Aborted()`) inside the dynamic linker's `mmap` of a library's segment: `mmap(addr, 0x2000, PROT_READ|PROT_WRITE, MAP_PRIVATE|MAP_FIXED|MAP_DENYWRITE, fd, 0x2c000)` for `libgcc_s`, the same call site for `libm`. Root cause, from a scratch build that sends Blink's log to the program's stderr: `blink/memorymalloc.c:677 assertion failed: !Munmap((void *)mug, real - mug + size) (EINVAL)`. In the browser build Blink backs each 4 KB page of a file mapping with its own Emscripten `mmap` of the file (a "mug", `memorymalloc.c` `PAGE_MUG`), each placed 128 KB apart in the wasm heap. The dynamic linker first maps a library's whole span from the file, a span that ends past the end of the file when the last segment has `.bss`, then maps the writable segment over it with `MAP_FIXED`; replacing the span's last page unmaps its mug, and Emscripten refuses that unmap with `EINVAL` for the page lying past the end of the file. libc escapes only because its file has section data after its last segment. The same design costs 32 times the memory it maps: libc's 535 pages take about 68 MB of wasm heap, the C++ program's 1,332 about 170 MB. Fix in the browser build: copy a private file mapping's bytes into ordinary Blink pages (read, zero-filled past the end of the file) instead of mapping the host file per page; nothing an ELF load does needs `MAP_SHARED` file pages. Most CTF binaries link only libc, but `libm` and C++ are common enough that this blocks decision 3 until fixed.
4. **gdb's layout works** with the constants in `tunables.h` changed (image start `0x555555554000`, stack top `0x7ffffffff000`, dynamic linker at `0x7ffff7fc3000`, `mmap` area from `0x7ffff7800000`), `map.c`'s `InitMap` not scaling them into 32 bits under Emscripten, and the dynamic linker always placed at `FLAG_dyninterpaddr` instead of 16 MB below a PIE (`loader.c`). The browser build keeps its own page tables (no linear mapping), so 47-bit addresses work; the stack was already at `0x4fff…`. A PIE then runs at `0x5555555…`, libc at `0x7ffff78…`, the stack under `0x7ffffffff000`. The `mmap` area needs a real design (Linux allocates it top-down below the stack; a window between `0x7ffff7800000` and the dynamic linker is too small for large allocations). The Core's `dist-smoke.mjs` passes on the changed build (assembled programs, a breakpoint, SSE and x87 undo, standard input, compiled C with the Start unit). Tests that pin the old layout: `blink-js/tests/memory-regions.test.ts` (`mov rsp,0x4fffffff0000`, stack top `0x4fffffff0000n`) and `tests/undo-capture.test.ts` ("Blink's own mmap() puts anonymous pages at 0x80000000").
5. **The layout change also fixes reading and undoing PIE memory.** `blinkenlib.c`'s `IsShadow` refuses every guest address in `[0x7fff8000, 0x100080000000)` as AddressSanitizer shadow memory, for reads and for undo capture. Today's PIE base (`0x88000000`) and `mmap` area (`0x80000000`) are inside it, so `readMemoryBytes` fails on a PIE's own code ("virtual address is not mapped") and its stores cannot be undone. gdb's addresses are all above the range, `0x400000` below it.
6. **Two syscalls every glibc program calls are missing**: `set_robust_list` (273) and `rseq` (334), each once at startup; glibc carries on after `ENOSYS`. Implemented as Linux does for one thread on one CPU (record the list head; register the `rseq` area and write CPU 0 into it), they keep decision 17's Log note for real gaps. The rest of the startup (`brk`, `arch_prctl`, `set_tid_address`, `mmap`, `mprotect`, `openat`, `pread64`, `fstat`, `prlimit64`, `getrandom`, `access`, `ioctl`) is implemented.
7. **Blink's disassembler is fast but not good enough for a Listing.** Decoding all of libc's `.text` (1.67 MB, 406,844 instructions) one address at a time from JavaScript took 0.94 s. But in the crackme's 118 instructions, the 10 `endbr64` that start its functions print as `pause edx`, and 22 RIP-relative operands print the absolute target after `rip+` (`jmp *[rip+0x555555557fb8]`). In libc, 4,750 AVX (VEX) and 1,638 AVX-512 (EVEX) instructions decode as unrelated legacy ones (`les`, `lds`, `bound`), which can also desynchronise the instructions after them, and 14,409 lines name vector registers AT&T-style (`movaps [rbp-0x80], %xmm0`). Blink executes no AVX, so it cannot run those either, but a Listing must still show them correctly. See the open question on decision 6.
8. **Libraries C++ and maths programs need**: `libm.so.6` (1.2 MB), `libstdc++.so.6` (2.7 MB), `libgcc_s.so.1` (0.2 MB), beside `ld-linux-x86-64.so.2` (0.25 MB) and `libc.so.6` (2.2 MB), all from the same distribution build. A binary built against a newer glibc than the bundled one fails in the dynamic linker with `version 'GLIBC_2.xx' not found`, so the bundle should be a recent glibc.
9. **Zydis works as decision 6 needs.** Zydis 4.1.1 (MIT) amalgamated into one `Zydis.c` (11.9 MB of source, Zycore included) and built with emsdk 6.0.9 at `-O2` with a 40-line wrapper is a 392 KB wasm (129 KB gzipped), built in 4 s. Decoding libc's `.text` in one call took 0.31 s for 392,385 instructions with no undecodable byte; Blink's count over the same bytes, 406,844, includes the instructions its misread VEX and EVEX prefixes split off. `endbr64`, AVX (`vpbroadcastb ymm0, xmm0`), AVX-512 (`vpbroadcastb zmm17, esi`) and vector registers (`movaps [rbp-0x80], xmm0`) print correctly. Zydis's Intel style is MASM-flavoured (`qword ptr`, upper-case hex) and needs formatter hooks for NASM's spelling.
10. **Upstream Blink has nothing to merge.** The fork merged jart/blink up to `4980d2c` (2025-03-14, robalb's merge `e6156ff`); upstream `master` (`f006a4f`, 2025-12-10) is 7 commits ahead, none relevant: Blinkenlights UI, exit-code constants, Fil-C support. Open pull requests carry what matters: #207 is the `rdx` fix of result 2 (upstream issue #179), bundled with ~500 unrelated AI-written lines, so the idea is taken, not the patch; #216 fixes LZCNT, which in the fork computes `bsf` and TZCNT `bsr` (`machine.c`, `AluLzcnt`/`AluTzcnt`), and is worth taking; #214's `mmap` fix is for the linear-memory path the browser build does not use; #217 (FUCOMPP) the fork already has; #210 adds SSE4.1 instructions Blink's CPUID does not advertise. Upstream issue #172 ("CPU does not support x86-64-v2") is a reminder that the bundled glibc must be a baseline x86-64 build: Blink advertises neither SSE4.1 nor SSE4.2 (`cpuid.c`). The wasm port itself is upstream issue #8, still open, so the browser-side problems found here (results 3, 5, 7) are this fork's to fix.

- Function starts add two kinds to the plan's list. The first instruction of each executable section starts one, so PLT0 and a stripped `.init` belong to a function. Code addresses the dynamic linker relocates into (RELATIVE and IRELATIVE addends, RELR slots) or `.init_array`, `.fini_array` and `.preinit_array` hold start one too: they are function pointers, and they give a stripped binary's constructors, destructors and C++ virtual functions names of their own instead of merging them into the function before.
- The `main` pattern also accepts a call immediately followed by `hlt` whose target has no name at all: glibc's `_start` in a stripped static binary, whose `__libc_start_main` is unnamed (and, with today's analyser, a binary without section headers). The scan stops at the first call, and a write to `rdi` other than `lea` or `mov` of an immediate clears the candidate. A `main` symbol wins over the pattern.
- PLT stubs are named from each stub's own `jmp [rel slot]` and that slot's relocation (`<symbol>@plt`; an IRELATIVE slot takes the name of the ifunc symbol at its addend), and lazy `.plt` stubs, when `.plt.sec` exists, from the slot whose initial value points at them (`<symbol>@plt_resolver`), rather than from `ElfAnalysis.plt`, whose names are shifted in the bundled libc (Core gap 1 below). Without section headers the analyser's stubs are used, checked against their slots the same way. GOT slots with a GLOB_DAT, JUMP_SLOT or IRELATIVE relocation are labelled `<symbol>@got`, so `call [rel __libc_start_main@got]` reads as what it calls.
- The editor reads the relocations the analyser leaves out (Core gap 2): RELA tables not linked to `.dynsym` (a static binary's `.rela.plt`, which holds its ifunc slots, so static glibc's stubs read `strlen@plt`) and RELR (`.relr.dyn`, libc's relative relocations).
- Decoding is linear, piece by piece. Object symbols inside code are listed as data, and decoding restarts at every trusted address linear decoding ran across (a symbol, the entry point, a function pointer, `main`, and without section headers the analyser's PLT stubs); the bytes before it are listed as `db`. A call target inside an instruction starts no function and prints as `function+offset`, as does a jump target there.
- Every name of an address is printed, aliases first and the name operands use last, next to the code, so a `.LAB_n` below belongs to it as NASM would read it. The name operands use has the fewest leading underscores (`puts` over `_IO_puts`), then global over weak over local, typed over untyped, the shorter, then code-unit order. A name already used at another address takes `_2`, `_3` in ascending address order (static glibc has 56 `__PRETTY_FUNCTION__.0`). Characters a NASM name cannot hold become `_`. TLS, absolute, undefined, file and section symbols name nothing. Symbol versions are not told apart (Core gap 3), so two versions of one name read `memcpy` and `memcpy_2`.
- Every allocated section is listed, ELF metadata included (`.dynsym`, `.rela.dyn`, `.eh_frame`), except `.tbss`, which takes no address space of its own. Strings are written as NASM writes them, `db "Wrong!", 10, 0`, since NASM's double quotes read no escapes; comments use C's (`; "Wrong!\n"`). A string line ends after a `\n` or at 64 bytes; a run of at least 64 zero bytes is `times N db 0`; `db` lines end at 16-byte addresses so the gutter's addresses line up, and at the end of an object symbol. A data label stands on its first data line, as the design shows (`s_Enter_password: db "Enter password: ", 0`), with any aliases on lines above it.
- Strings are looked for in `PROGBITS` data sections except `.eh_frame*` and `.gcc_except_table`, and inside an object symbol only at its start. A RIP-relative target that starts a printable NUL-terminated run shorter than the scan's 4 bytes is a string too (crackme's `"\n"`, which is `DAT_nimble_sandpiper` because its text folds to nothing). A string the code reaches only part way in starts where it is reached: static glibc's `@@atexit handler`, whose `@@` are the end of a constant before it, is `s_atexit_handler`.
- In a position-independent file only a slot the dynamic linker relocates is a `dq` pointer, since small numbers in its data look just like its link-time addresses; a relocated slot without a label prints its value (`__libc_start_main@got: dq 0`). At fixed addresses an 8-aligned value equal to a label's address is a `dq` too, as planned.
- Instruction comments: the text of a RIP-relative string target, and in a binary at fixed addresses the label an immediate or a bare `[0x…]` displacement equals (`mov rdi, 0x4018bf ; main`).

- Core futexes (C1). The browser build runs one thread, so a `FUTEX_WAIT` whose word matches can only time out: with a timeout it waits through `GuestWaitHalt`, as `nanosleep` does (a wait request on the host's or a Testcase's virtual clock), then answers `ETIMEDOUT`; `FUTEX_WAIT_BITSET` takes an absolute deadline on `CLOCK_MONOTONIC`, or `CLOCK_REALTIME` with `FUTEX_CLOCK_REALTIME`. Without a timeout it still returns 0 at once. Checked against the host kernel with the same probe ELF: `FUTEX_CLOCK_REALTIME` on anything but `FUTEX_WAIT_BITSET` is `ENOSYS` (the man page says `FUTEX_WAIT` takes it since 4.5; Linux 6.18 refuses it), a zero bitset and a misaligned word are `EINVAL` (Blink said `EFAULT` for the latter). - Private file mappings (C2) copy only the pages holding file bytes, read before the existing mapping is removed; pages wholly past the end of the file are lazy zero pages counted as reserved. Linux raises `SIGBUS` on those pages; they read as zeros here, as they did since M1.3, which the dynamic linker never notices since it maps anonymous memory over them. Mapping 1 GiB and 2 GiB of a 100-byte file now grows the wasm heap by 0 bytes (was 1.28 GiB, and an `exit(250)` panic for 2 GiB). Allocation failures in `ReserveVirtual` (pages, page tables, a shared file's host pages) roll back and answer `ENOMEM`; the remaining `exit(250)` paths are for Blink's linear-memory mode only. As a safety net, a native `exit()` thrown out of any run entry point becomes a `host-error` stop: `blinkenlib_recover_native_exit` releases what the halt path releases, the C stack pointer is restored (`stackSave`/`stackRestore`, newly exported), and Node's `process.exitCode`, which Emscripten's glue sets, is put back (also for the loader's `exit(127)`, the existing load-fail path).

It never throws (fuzzed by truncation and byte corruption of every fixture and library), and every count is capped by what the file can hold. A file cut after everything Linux maps is now supported. The `.symtab` reader is its own lenient one, so `readElfSymbolTable` keeps throwing for its other callers. libc analyses in about 3 ms (5 ms without sections). 1. **The invented-name word lists** (`packages/asm-editor/src/lib/listing/words-v1.ts`, checked by `words.test.ts`, pinned by `names.test.ts`) need your review before the first release that shows them: once shown they freeze, since changing them renames every function in every saved Project (ADR 0045).
2. **Empty Testcase Arguments** mean "use the Project's" (M10), so a Testcase cannot ask for no Arguments while the Project has some. The alternative, an empty field meaning no Arguments, would make every new Testcase ignore the Project's; a "none" toggle would allow both.
3. **NASM 3.00 encodes some instructions wrongly in ordinary Project assembly** (review fixes notes): `cmpxchg` with a 64-bit or 16-bit register loses its REX.W or `66` prefix (`cmpxchg [rdx], rbx` assembles as the 32-bit form), `kunpckbw`/`kunpckwd`, `smsw` and `bswap` of a 16-bit register are mis-encoded, a memory operand without a size is silently given one (`add [rax], 1`), a displacement beyond 32 bits is truncated, `notrack` is dropped, and `sgdt [rax]` makes NASM assert. Patches are guarded (`assembleInstruction` works around or refuses them); a Project's Build is not.
4. **Undo of a patch across irreversible steps.** Undo cannot go back past a step the Core records as irreversible (reading standard input, growing the heap with `brk`), so a patch made at `main` and followed by a Run that reads a password stays until the next Build (M11). The Documentation says to patch after the input is read; a patch could instead be reapplied or reverted on its own, outside the history, if you want it always undoable.
5. **Release `@specy/x86` 7.0.0**: the Core's changelog is written; tag, publish and push the submodule (`feat/binary-import`, ten commits from `cab3770` to `479aa4c`), then pin the editor's dependency if it should not stay `workspace:*`. Both branches are local.
6. **A symbol at the end of a section** followed by an alignment gap is not printed, so an operand reaching it shows its address (cpp's `__TMC_END__`, `lea rdi, [rel 0x55555555a020]`; M13 notes).
7. **Touch and phones**: the long press was checked in Chrome's touch emulation, not on a real phone (iOS Safari's own long-press callout could interfere); the Listing's notice says "Space or the context menu" on a touch screen too; the 12-character address gutter takes about 37% of a phone's editor width.
8. **Still open from earlier milestones**: Go programs were never run (no toolchain); libraries other than the five, newer glibc versions and a challenge's own libc fail with the dynamic linker's message (deferred); threads, sockets and `fork` are unavailable in the browser build; libc's and libstdc++'s Listings are shown unhighlighted (Monaco's large-file mode); the Listing's header comment lines have no address in the gutter, by design.
9. **Review**: separate reviewers are reviewing the whole change in parallel with M13 (plan M13.4); their findings are not in these commits.

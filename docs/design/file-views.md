# File views

Status: decided 2026-10-15 (grill) and planned the same day ([the plan](./file-views-plan.md), in two batches). Batch 1, everything but the decompiler (E1 to E7 and E10's share of them), is implemented on `feat/file-views` as of 2026-10-16; Batch 2 (the decompiler package's submodule and release, Pseudocode, its Breakpoints, and their Documentation and verification) is under way on `feat/pseudocode`: D1.6, E8, E9 and the Pseudocode's share of E10's Documentation and browser verification are done as of 2026-10-18; Batch 2's code review is done and its findings fixed (E10, Batch 2 review fixes, below); D4, the decompiler's 1.0.0, is prepared in its submodule (`c20651e`, with its CD workflow and changelog) but not tagged or published, which is the owner's. How the **Workbench** shows a **File** that is not text: the **Hex editor**, the browser's own preview of images and PDFs, an **Executable**'s **Listing** and decompilation, and the x86 **Build output** they can all be pointed at. Terms are in [CONTEXT.md](../../CONTEXT.md). This revisits three decisions of [the binary import design](./binary-import.md): 5 (an Executable is displayed as its Listing), 13 (permanent patches deferred) and 14 (the decompiler deferred, as a pane beside the Listing).

## Decisions

1. **Which Files.** An Executable, and any File stored as bytes that the browser cannot preview, opens in the Hex editor, in every **Target**'s Project, replacing today's "Binary file" notice (`EditorPane.svelte`). Images and PDFs open in the browser's own preview. Only an Executable offers Disassemble and Decompile, so for now only in x86 Projects, the only ones with Executables.
2. **What a hex edit changes** ([ADR 0047](../adr/0047-byte-edits-are-kept-apart-from-the-original-bytes.md)). The interface edits in place, as HxD and ImHex do: every reader of the File sees the edited bytes, and there is no list of changes. The Project saves the original bytes and the **Byte edits** apart, so a later version can show, revert or undo them without a format change. The memory-only **Patch** of a **Debug session** is unchanged.
3. **Overwrite only.** Typing replaces bytes and a File keeps its length: an insertion or deletion would move every later byte, which breaks an Executable's addresses and offsets, and most forensics fixes (magic bytes, a chunk length) are overwrites. The saved Byte edits can still express insertions and deletions (ADR 0047), so adding them later changes no format.
4. **The view switch.** A switch with one button per view sits in the execution dock's left group, beside Build, where a C File already shows Compile and its compiler pickers (`ExecutionControls.svelte`): **Hex · Disassemble · Decompile** for an Executable, **Preview · Hex** for an image or a PDF, none for any other byte File, which has only the Hex editor. The pressed button is the view shown. "Disassemble" names the action that produces the **Listing**; the glossary keeps "Listing" for the view. _Revised 2026-10-18:_ the switch is `SegmentedControl`, the pill whose highlight slides to the view shown, at the dock's height and in its words, which drop as the dock narrows as before; the Hex editor's byte order (Little · Big) and Find kind (Hex · Text) are the same control. This follows the Workbench's "Choices are one control everywhere" ([workbench.md](./workbench.md)), which the first version had set aside for buttons sunk into the tray like pressed keys.
5. **Views, not Files** ([ADR 0048](../adr/0048-decompiled-code-is-a-view-not-a-file.md)). The Listing and the decompiled code are generated from the File's current bytes whenever shown and never saved, as in Ghidra, IDA, Binary Ninja and Cutter. Decompile shows the code beside the Listing, linked line by line by address, reusing the pairing of a C File with its Generated assembly (`resolveMappingPair` in `lib/workbench/mappingPair.ts`, which already pairs a non-Project path through its `libraryMap` hook). Rejected: saving them as Files tracked like Generated assembly (the user's first idea), since nothing builds from them, they go stale at the next Byte edit and decompiler output does not compile. Not now: exporting the decompiled code as a File, labelled as a snapshot.
6. **One function at a time, following the Listing.** Decompile turns its pane into the **Pseudocode** of the function the Listing's cursor is in, and opens the Listing in a second pane beside it when none shows it; moving in the Listing changes the function, following a call in the Pseudocode moves both, and during a **Debug session** both follow the program counter. On a phone the two panes stack, as every split already does there (`EditorArea.svelte` stacks panes under 700 px; corrected while planning, the design first assumed a phone shows one pane). Ghidra's model: only the function shown is decompiled, so it scales to a static glibc binary's thousands of functions. Rejected: the whole program as one document (minutes for a large binary) and a function picker of its own (C and assembly drift apart). The view is called Pseudocode, after IDA, because "decompiled C" promises C that compiles; the button says "Decompile".

7. **The Hex editor is a scrolling grid, not Monaco.** It draws only the visible rows from the File's bytes, which the Project already holds in memory (16 MiB of Files at most), over the File's whole length with an offset column. It looks like the memory view (`MemoryRenderer.svelte`: its cells, font, colours, region outlines and hover) and reuses its pure helpers, but it types as hex editors do, inline: a caret moved by the arrow keys overwrites a nibble at a time in the hex column or a character in the text column. The memory view has neither (corrected while planning): it switches every cell between hex and characters instead of showing both, and a Poke is typed into a popup over the selection. Monaco is ruled out: a 16 MiB File as hex text is about a million lines and 70 MB, and Monaco inserts text where a hex editor overwrites cells. The memory view as it is was rejected because it moves a page at a time. Planning concern: browsers cap an element's height (Firefox near 17.9 million pixels), below what a 16 MiB File's rows need, so the scrollbar is scaled for the largest Files. The Listing keeps Monaco and its large-file mode as [the binary import design](./binary-import.md) measured it (libc: 473,000 lines, about a second in the worker); any further Monaco tuning is deferred.
8. **Views during a Debug session.** A Build moves a pane showing the Executable in Hex to Disassemble, since the program counter, Step, Breakpoints and Patches all work on the Listing, as VS Code opens the file a debugger stops in and x64dbg and IDA switch to disassembly when a session starts; the switch's pressed button is the cue. When no pane shows the Executable, the execution pane opens it on Disassemble, as the debugger already opens the File it stops in. A pane on Decompile stays there, and both it and its Listing follow and highlight the program counter. Hex stays available, read-only like every File during a session, under a notice: "The File's bytes. Patches and the program's writes are in memory: see the memory view.", so a **Patch** missing from the File's bytes does not read as a failed one. Stop changes no view. A pane remembers its view per File, and the Project saves the last view chosen for each File beside its open tabs (corrected while planning: open tabs are saved as one list for the Project, not per pane, and a reopened Project restores them into one pane).
9. **What the first Hex editor has.** The basics: an offset column, 16 bytes a row, hex and text columns (bytes outside printable ASCII as `.`; the memory view's character mode does this only for its default value), overwrite typing in either column, Undo and Redo, selection and copy as hex or text, go to offset, find by hex bytes or text, and a status line with the cursor's offset and the selection's length. For reverse engineering and forensics, each reusing data the editor already has: a data inspector (the value at the cursor as signed and unsigned 8, 16, 32 and 64-bit integers, single and double precision, in both byte orders); for an Executable, tints like **Memory regions** for the ELF header, the program headers and each section, named on hover, from the ELF analysis the Listing uses; and Show in Listing / Show in Hex between a code byte and its instruction, through the file offset the Listing's line table keeps for each line (`offsets` in `lib/listing/listing.ts`). Not now: structure templates and tints for other formats (PNG chunks), an entropy graph, diffing two Files, bookmarks, encodings other than ASCII.

10. **Breakpoints on Pseudocode lines.** A Breakpoint set on a Pseudocode line places address Breakpoints on the first instruction of each block mapped to that line, by the rule a C File's lines already follow, and those are ordinary Breakpoints of the Executable's Listing ([the binary import design](./binary-import.md), decision 5), visible in the Listing beside it. The Pseudocode marks every line whose instructions carry one, and removing it there removes those addresses. Nothing new is saved, so a Breakpoint survives the Pseudocode being printed differently after a Byte edit or a decompiler update. Rejected: Breakpoints set only in the Listing, since a beginner reading the Pseudocode wants to stop on the `if` that compares the password.

11. **Decompile is always available.** This reverses [the binary import design](./binary-import.md)'s decision 1, which left a decompiler out so that a beginner could not solve a crackme without reading assembly. The Pseudocode never appears without its Listing beside it and linked (decision 6), so the C leads to the assembly rather than replacing it. No Setting or Preference turns it off: a switch on a shared Project protects nothing, since whoever opens it can turn it back on. Executables are not in Exams yet; if they come, that design decides whether an Exam hides Decompile, as an Exam's search already leaves out Examples.
12. **Our own build of upstream Ghidra's decompiler** ([ADR 0049](../adr/0049-pseudocode-comes-from-our-own-ghidra-decompiler-package.md)), at a pinned release, with a host layer that feeds it the Listing's analysis (function starts, every name including invented ones, strings, read-only ranges) and returns Ghidra's markup for the line links, so the Pseudocode names what the Listing names. Pyre's host layer (MIT) and rz-ghidra's are borrowed from where they help. Rejected: forking Pyre (alpha, dormant, plain text, its own names), Kuna (a diverged Rust port, about four times larger, reads the ELF and names things itself) and any server (dogbolt has no API and keeps uploads; binary import decision 16 keeps a binary in the browser).
13. **A package of its own, `@specy/decompiler`** (ADR 0049): a new repository and sixth submodule, architecture-neutral, the caller naming the architecture and each processor description loaded when first needed, x86-64 first, so unicorn-edu's ARM and AArch64 and later Executables of other Targets can share it. Rejected: `@specy/x86/decompiler` beside the disassembler, which reuses the x86 Core's emsdk scripts and release but ties the decompiler to one Core; a workspace package of the monorepo, which would add emsdk to the editor's toolchain.
14. **Preview.** A byte File is recognised by its first bytes, never its name, as an ELF already is ([the binary import design](./binary-import.md), decision 15), since forensics files often carry a wrong extension or none; the type handed to the browser is always the one whose signature matched, so a File is never shown as a web page. Images (PNG, JPEG, GIF, WebP, AVIF, BMP, ICO, JPEG XL) show in `<img>`, falling back to Hex with a one-line note where this browser cannot decode the format. A PDF shows in a frame where `navigator.pdfViewerEnabled` holds, unsandboxed since the `sandbox` attribute stops Chrome's viewer; elsewhere (Android) a notice offers "Open in a new tab" and "Download", and iOS, which shows only the first page in a frame, offers "Open in a new tab" too. Audio and video play in `<audio>` and `<video>`, for the CTF stego that hides things in sound. Not now: a preview of SVG, a text File that opens as text; it would have to use `<img>`, since in a frame its scripts would run as the site.
15. **A program's write replaces the original** (ADR 0047). When a run's program writes a byte File, the **FileSystem** stores the whole new content (`writeBytes` in `lib/languages/peripherals/FileSystem.ts`), which becomes the File's original, and its Byte edits are dropped, as when a File is uploaded over. Byte edits are what a person types in the Hex editor, and text Files keep no history of program writes either. Rejected: recording the write as Byte edits against the original, which mixes the program's changes into the person's own and needs insertions and deletions for a program that appends or truncates.
16. **The built program, for x86 only.** An x86 Build already links a real Linux executable (`ld … -o /program`, `packages/x86/blink-js/src/assemblers.ts`), which the editor now shows: what a real toolchain does and what the **Command line** already claims (`$ ./main`), a loop back into this design (open your own program in Hex, Disassemble and Decompile, and compare the Pseudocode with your source), and a genuine Linux executable a person can download and run, since the x86 **Reference environment** is a Linux process. Not now for the others: MARS and RARS assemble into memory with no executable (their nearest output is "Dump Memory", raw `.text` and `.data` images, `MemoryDump.java`), and an invented MIPS ELF would run nowhere, MARS's syscalls not being Linux's; s68k writes no S-records, EASy68K's output; the Z80's assembler can already write a raw binary, Intel HEX or a TRS-80 `.CMD` (`trs80-asm/src/Main.ts`), the likeliest second candidate.
17. **A Build output, never saved** ([ADR 0050](../adr/0050-the-built-program-is-a-build-output-never-saved.md)). The built program is listed in the Explorer as built and read-only, present in the program's FileSystem at its path (readable but not writable, as a running Executable's File), and opens in Hex, Disassemble and Decompile like any Executable, or downloads. Each Build replaces it; it is never saved, archived or shared, and "Keep as File" copies it into the Project as an Executable, as the `@lib/` and `@runtime/` Files are already shown without being the Project's. Rejected: a Project File written by every Build, which would push most x86 share links past their 32,000 characters, autosave on every Build, go stale, and overwrite any File at its path.
18. **The Build output's path.** One File, the linked executable, at the Entry path without its extension (`main.asm` and `main.c` give `main`, `src/game.asm` gives `src/game`): the name `argv[0]` and the Command line already give the program ([the binary import design](./binary-import.md), decision 12), so `$ ./main` names a File that exists. A Project File at that path wins: the Build output is not placed, and the **Log** says why ("main is already a File of the Project, so the built program is not shown; rename one of them"), where `ld` would overwrite it and hide a File the person owns. An Executable Entry has none, being a File already. Not now: object files (`main.o`), which would teach assembling and linking as separate steps.
19. **Text Files by their name** (added 2026-10-18 at the owner's request, after the plan). A text File's name, as already for C, says what it is: Monaco highlights Markdown, plain text, Python, JSON, JavaScript and TypeScript, shell, YAML, INI and TOML, XML and SVG, HTML, CSS, Rust, Go, Java, Ruby, Lua, SQL, PowerShell and batch files as themselves (`lib/textFileLanguages.ts`), where every text File that was not C was the Target's assembly before; an extension not listed stays assembly, since an include File's is anyone's guess, and only the text view changes, a Listing and a Pseudocode keeping theirs whatever the Executable is called. A Markdown File (`.md`, `.markdown`) is the kind `markdown`, opening as its text with the switch **Text · Preview · Hex**, its Preview rendered as a Lecture is and its Hex read-only, as any text File's. A PDF frame runs to the pane's bottom edge under the floating dock, as code does.
20. **A text File's bytes are typed over as its text** (added 2026-10-18 at the owner's request; supersedes "its Hex read-only, as any text File's" in decision 19). The Hex editor of a File stored as text, a Markdown File or a PDF written in ASCII, takes typing as a byte File's does, but the File keeps no Byte edits and ADR 0047 is unchanged: each run of typing changes its text (`FileSystem.overwriteText`, with `overwriteText` in `lib/projectFiles.ts`), as typing into its Text view does. The text must stay UTF-8: a run that would leave it otherwise is refused, with a toast saying why, and a pause halfway through a character typed byte by byte in hex waits for the rest instead of refusing it. The Hex editor's Undo writes back the bytes a run wrote over (`ByteEditHistory.recordText`) while the text still holds what the run wrote there; typing into the Text view that moves those bytes starts its stack again. The Text view's own Undo does not reach a change made in hex, since a change from outside resets a Monaco model's history, as a program's write does. Rejected: turning the File into a byte File at its first Byte edit, which would take away its Text view and its Markdown Preview.

## Deferred

- Monaco tuning for very large Listings (decision 7).
- Exporting the Pseudocode as a File, labelled as a snapshot (decision 5).
- Inserting and deleting bytes in the Hex editor (decision 3).
- A visible list of Byte edits, reverting one, or downloading the original (decision 2).
- Structure templates, tints for formats other than ELF, an entropy graph, diffing, bookmarks and other text encodings in the Hex editor (decision 9).
- A preview of SVG Files (decision 14).
- Build outputs for the other Targets: MARS and RARS memory dumps, M68K S-records, Z80 binaries, Intel HEX and TRS-80 `.CMD` files (decision 16).
- Object files as Build outputs (decision 18).

## Implementation notes

- **D1** (2026-10-15, `Specy/decompiler-js` commits `084b545`..`0774b32`, local, not pushed; our code Apache-2.0, confirmed by the owner): Ghidra `Ghidra_12.1.4_build` (`8b6bbb8`) vendored by `scripts/vendor-ghidra.sh`; the build scripts live in `scripts/`. The wasm needed no patches: `-O2`, `-fwasm-exceptions` in Emscripten's default legacy encoding (Chrome 95, Firefox 100, Safari 15.2; the owner chose it over the standard encoding, which needs Chrome 137, Firefox 131, Safari 18.4), no threads, a 4 MB stack, an ES module factory, specs written into the in-memory filesystem. Sizes: `decompiler.wasm` 2,015,453 bytes (676,311 gzipped), glue 63,353, `x86-64.sla` 501,178 (compiled by Ghidra's C++ SLEIGH compiler). crackme's `main` decompiles identically natively, in wasm and in Ghidra's own console (`consolemain` fed an XML load image); in Node the architecture takes 120-160 ms to build, the first decompile 28-40 ms and a warm one 3-4 ms. The host's load image reads zeros past a region's end, as Ghidra's loaders do, since SLEIGH fetches 16 bytes at a time. Until D2 passes names, types and prototypes, the output prints Ghidra's core type names (`xunknown8`, `int4`) and string arguments as addresses (`puts(0x201f)`).

- **D2** (2026-10-15, commits `69790b1`..`f053c5a`): core types as Ghidra's Java side generates them (`PcodeDataTypeManager.generateCoreTypes`, sized by the cspec), `readonly` on as `DecompileOptions` sends it, data names as name-locked symbols, a named string as a type-locked `char[]`, so crackme's `main` reads `printf("Enter password: ")`, `strcmp(acStack_98,"hunter2")`, `puts("Correct!")`. Prototypes are parsed one declaration at a time with Ghidra's `CParse` and bound by name, PLT stubs included; `_Noreturn`, `[[noreturn]]` and `__attribute__((noreturn))` mark noreturn; a bad declaration is a warning on the program. CParse's limits for D3's `glibc.h`: `(void)` rather than `()`, no unsized arrays, a struct defined before use; its lexer crashes on an identifier ending a line (declarations are rejoined; worth reporting upstream). The markup comes from an `EmitPrettyPrint` subclass driving Ghidra's `EmitMarkup`, its text byte-identical to the console's; crackme's `if (iVar1 == 0)` maps to its `test` and `jne`. 1,339 of `hello-atexit-static`'s 1,340 functions decompile (one fails on unmapped bytes); `printf_positional` takes 14 s. The wasm is 2,112,834 bytes (711,774 gzipped); the first program opens in 126-136 ms, later ones in about 5 ms (the SLEIGH translator stays cached, about 18 MB); crackme's `main` decompiles in 31-34 ms first, 3-5 ms warm. API additions: `decompiler.memory()`, `warnings` on the program; label tokens carry a `target`. Unnamed globals print the decompiler's own names (`cRam0000000000004018`), and stack locals `acStack_98` rather than the Ghidra GUI's `local_98`, which comes from Java-side stack analysis.
- **D3** (2026-10-15, commits `f6d9aec`..`9ecde86`): `prototypes/glibc.h` declares 537 functions (50 `_Noreturn`) and 8 globals, checked against the bundled libc, libm, libstdc++ and libgcc_s exports, including the `__isoc23_` functions GCC 15's C23 mode calls; `stat` and `sigaction` take `void *` (their structs share the functions' names), and `strtold`, `div`/`ldiv` and static glibc's internal aliases are left out. It is exported as the file and as a string (`@specy/decompiler/prototypes/glibc`). The guards are a patch (`0001-action-checkpoint`) calling a hook before each action, through which the host enforces a deadline, `timeLimitMs` per call (30 s by default), stopping within 50-250 ms of it, and `maxInstructions`. Measured on a shared machine: load 24 ms, first program 127 ms, later ones 14-23 ms; crackme's `main` 9.6 ms first and 3.7 ms warm; 1,086 of `hello-atexit-static`'s 1,087 functions decompile (median 8.3 ms, 99th percentile 1.2 s), the slowest `printf_positional` at 14.3 s (23-26 s under heavy load, so slow devices may reach the limit). Two bugs found while measuring were fixed: each function's analysis was kept (944 MB), and two open programs shared one SLEIGH translator (patch `0002-sleigh-resume`). The one failure is the decompiler's own: a jump table in `uw_update_context_1` it cannot bound. Calls through an `.plt` stub the caller does not name print Ghidra's `func_0x…`, and a call through a GOT slot (`_start`'s call of `__libc_start_main`) gets no prototype, which E8.1 has to address. The wasm is 2,116,887 bytes (713,132 gzipped).

- **E1** (2026-10-15, commit `992fb3ad`): Byte edits as the plan's decision 9 has them, settling the open items on their shape, the record that carries them and the archive version. `cleanFiles` refuses edits on a text File, an empty or length-changing edit and one past the original's end, drops an empty list, and counts each edit's bytes beside the original toward the 16 MiB. `fileText` refuses an edited File (an assembler then gets its bytes), so a byte File stays one when its edits decode as UTF-8; an unedited byte File that decodes is still read as text, as before. `fileFingerprint` appends `\0` and the edits only when a File has some, so a File without edits keeps the fingerprint saved Compilation records hold. `fileHead(file, n)` reads a File's first bytes, edits applied, without decoding it whole (the ELF magic, recognition). The ELF analysis cache keeps one version of each content (an edit and its Undo analyse the original again); Listing documents are keyed by content and `byteEditsKey`. `FileSystem.editBytes` merges every edit into sorted runs with `mergeOverwrites`, and an edit that writes a byte's original value back stays an edit, since nothing compares with the original yet. Archives are version 2 only when some File has edits, and a version 1 manifest carrying `edits` is refused. For E3: `editBytes` cannot restore an earlier edit list, which the Hex editor's Undo needs; a `setByteEdits` is left to it.

- **E2** (2026-10-15, commit `ffdef834`): `lib/fileKinds.ts` recognises Files and `lib/fileViews.ts` holds `FileView` and each kind's views, apart so that the Project cleans `fileViews` without loading the ELF analysis. Recognition reads the first 4 KiB: an MP3 without a tag needs a Layer III frame header and another where that frame ends, as the MIME Sniffing standard matches one (one header alone took UTF-16 text for audio); an `ftyp` box is read before ICO, whose signature a 256-byte box size matches; M4A brands are audio, and HEIF brands without `avif` are bytes, since only Safari shows HEIC. A text File is text whatever its first bytes, but an ELF stored as text is still an Executable. Until the view switch (E6), an Executable opens on its Listing (`fileViewsOf('executable')` lists `listing` first, then `hex`), the only way to reach the Listing meanwhile; E6 puts `hex` first, and E8 adds `pseudocode`. A pane's `views` holds the view of each of its open tabs; a File without one there takes the Project's saved view, then its kind's default; choosing a view pins every other pane that has the File open to the view it shows, so that it does not switch with the saved one. `fileViews` is saved only where it is not the default, omitted when empty, and moved or dropped with a renamed or deleted File. Model keys and URIs carry a Listing's or Pseudocode's view (`#listing`, the URI's fragment), so a text model keeps its key; `retainedModelKeys` keeps a `#listing` key for every byte File. `editorFileKind(path, file)` calls a byte File `bytes`, and `controlsGroup` counts a pane showing a Listing as assembly. `showBuildFile` prefers a pane whose view `showsInstructions` (text or a Listing), `instructionLine` is -1 in any other view, `existsInBuild` takes a view, the mapping pair needs both panes on `text`, a tab moved to the other pane keeps its view and a closed tab forgets it, and going to a definition in a view shows that view without saving it. The Hex editor and the Preview are placeholders naming the File, its size and kind (`components/specific/workbench/hex/HexEditor.svelte`, `preview/FilePreview.svelte`).

- **E3** (2026-10-15, commit `da9d804d`): the Hex editor, in `components/specific/workbench/hex/` (`HexEditor.svelte`, with `hexGrid.ts`, `hexSearch.ts`, `dataInspector.ts`, `byteEditHistory.ts`, `HexStatus.svelte`, `HexFindBar.svelte`, `DataInspector.svelte`). The rows are absolutely placed in a window held at the top of the scroller by `position: sticky` (clipped with `overflow: clip`, so the offsets also stay put in a sideways scroll), over a sizer as tall as the rows or 8,000,000 px, past which the scrollbar's range maps linearly onto the rows' and the wheel moves the rows by its own distance; the scroll position is kept as a row, so a change of row height or width keeps the caret's row in sight. A row holds 16 bytes when a hidden 16-byte row, measured, fits the editor's width with 16 px for a scrollbar, and 8 otherwise: at the Workbench's 0.875rem monospace a 16-byte row is 644 px wide with four offset digits and 661 px with six, an 8-byte row about 375 px, which a 390 px phone holds. Offsets take at least four digits, the memory view's narrowest address column. The status line sits above the bytes, not below them, since the execution dock floats over a pane's bottom edge; it carries Find, Go to and the data inspector's toggle, which a phone has no keys for, and the bytes leave the dock's height free below the last row. The data inspector sits beside the bytes where a 16-byte row and its 17rem fit, below them otherwise (at most 40% of the editor's height); it is open by default and its toggle is kept per person in the Workbench layout (`hex:inspector`), and it reads little-endian until switched. The arrows move a byte (Left from a low digit goes to the high one first); Tab moves from the hex column to the text column and Shift+Tab back, and from the far column the key leaves the bytes, so the keyboard is never trapped in them. Typing is saved as one `editBytes` when it pauses for 600 ms, when the caret moves any other way, when the bytes lose the keyboard and when the editor closes (each editor shows one File for its life, keyed by path, and saves to the path it was opened on); a run is always the contiguous bytes typed, so the edit is built from what was typed alone. Undo and Redo use `ByteEditHistory`, one per Workbench session and shared by both panes, which keeps each File's edit lists before every change and its offset, starts again when the File's original changes (an upload, a program's write) and follows a rename; `FileSystem.setByteEdits(path, edits)` puts a whole list back, refused while a Debug session holds the Files and on a text File, and checked as a saved list is by `cleanFiles`. Copy gives lower-case hex separated by spaces (`7f 45 4c 46`) or the text column as shown, dots included; Find takes hex bytes, spaces optional, with `??`, or text as its UTF-8 bytes, case-sensitive, from the caret or after the selection, a selection of up to 64 bytes filling the query; Go to reads hex with or without `0x` and decimal after `#`. Key presses in the bytes stop at them, so the Workbench's Shift+letter shortcuts are digits there, as they are text in Monaco. ## Research (2026-10-15)

Gathered by a research agent; sizes marked as measured were measured on the downloaded files, which were not run.

- **Ghidra's decompiler in wasm exists.** [Pyre](https://github.com/ant4g0nist/pyre) (MIT over Apache-2.0 Ghidra sources with r2ghidra's patches; alpha; four commits, all 2026-05-04): x86-32/64 and AArch64, fully client side in a Worker, `pyre_decompiler.wasm` 2.0 MB (653 KB gzipped, measured), built `-Os -fexceptions`; the host adds memory regions, symbols, strings and read-only ranges, then decompiles at an address; about 100 libc prototypes hard-coded. [@mauricelam/ghidra-decompiler-wasm](https://www.npmjs.com/package/@mauricelam/ghidra-decompiler-wasm) 0.0.4 (Apache-2.0, 2026-04-06): 2.63 MB wasm, specs passed from memory, the architecture rebuilt on every call. Both return plain text only. [Kuna](https://github.com/Noelo-Lab/kuna) (Apache-2.0, very active) is a Rust port that has diverged from Ghidra: 11.4 MB wasm (4.1 MB gzipped, measured), parses the ELF itself, and its `inspect` JSON gives line mappings and a token address. rz-ghidra and r2ghidra (LGPL-3.0) are native only. No official Emscripten target.
- **Driving it without Java** means subclassing `SleighArchitecture` (as rz-ghidra's `RizinArchitecture` and Pyre's `WebArchitecture` do): the host supplies bytes, function entry points (the decompiler follows control flow from there), names, prototypes (bound by name, so libc's signatures come from the host), noreturn flags, read-only ranges and strings. x86-64 Linux needs `x86.ldefs`, `x86-64.pspec`, `x86-64-gcc.cspec` and the compiled `x86-64.sla`, 488 KB and already compressed since Ghidra 11.1 (measured; the other three about 30 KB together). Specs are read through `ifstream`, so a virtual filesystem or a patch.
- **Linking lines to addresses**: the decompiler's markup emitter puts an op reference on tokens (`EmitMarkup`, `opref`), which rz-ghidra turns into addresses. Pyre and the npm package print plain text, so either needs a patch (`setMarkup(true)`, or an `Emit` subclass overriding `tagOp`, `tagVariable` and `tagLine`). The map is sparse: not every token or line has an op.
- **Runtime needs**: no threads; C++ exceptions (wasm exception handling is in every current browser). No per-function timings were found for the wasm builds; Kuna takes about 0.45 s cold on a small binary. Ghidra's own guards: 30 s timeout, 50 MB payload, 100,000 instructions per function.
- **Licences**: Ghidra and its x86 SLEIGH files are Apache-2.0 (carry `NOTICE` and the licence, mark modified files); the decompiler's bundled zlib is under the zlib License.
- **Servers**: [dogbolt.org](https://dogbolt.org/faq) has intentionally no public API, sends no CORS headers, caps uploads at 2 MB and keeps uploaded binaries for the tools' authors. RetDec (MIT) is in limited maintenance since 2022 with no wasm build.
- **PDF previews**: desktop Chrome, Edge, Firefox and Safari show a PDF from a Blob URL in a frame (`navigator.pdfViewerEnabled`); iOS shows only the first page inline (not confirmed for iOS 26 and later); Android browsers show nothing inline (Chrome 135 and later open PDFs in a tab). The `sandbox` attribute stops Chrome's PDF viewer. A Blob URL has the page's origin, so an SVG opened in a frame or a tab runs its scripts as the site; in `<img>` it runs none.
- **Images and media**: `<img>` shows PNG, JPEG, GIF, WebP, AVIF, BMP, ICO and SVG everywhere, JPEG XL in Safari 17, Chrome 155 and Firefox 158, TIFF and HEIC in Safari only. `<audio>` and `<video>` play MP4/H.264, MP3, WAV, FLAC and WebM everywhere. No browser API reports a sniffed type, so the editor checks magic bytes itself ([MIME Sniffing](https://mimesniff.spec.whatwg.org/): PNG, JPEG, GIF, WebP, BMP, ICO, `%PDF-`, and audio and video signatures; none for AVIF, JPEG XL, TIFF, HEIC or SVG).

- The Pseudocode while the Listing is still being generated (a large static binary takes seconds), and while the decompiler package loads.

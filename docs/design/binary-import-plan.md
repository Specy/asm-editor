# Binary import: implementation plan

Written on 2026-10-12 after the design interview and the spike. The decisions are in [binary-import.md](./binary-import.md) (18 decisions, its **Spike results** and **Deferred** list), [ADR 0044](../adr/0044-an-executable-is-a-project-file-a-build-loads.md) (an Executable is a Project File a Build loads) and [ADR 0045](../adr/0045-invented-names-are-frozen-words-from-file-addresses.md) (invented names); the vocabulary is in [CONTEXT.md](../../CONTEXT.md) (**Executable**, **Listing**, **Command line**, **Arguments**). Read all three before starting. The plan covers one major release of the x86 Core (`@specy/x86`, the `packages/x86` submodule, repository `Specy/x86-js`) and the editor work in `packages/asm-editor` that uses it.

It is written for an agent implementing it without the interview's context. Where this plan and the design disagree, the design wins; where a step needs a choice neither settles, take the default in **Decisions taken while planning** and note it in the design's implementation notes.

## Ground rules

- **Repositories.** The editor is this monorepo (pnpm + Vite+, `mise install && pnpm install`; ADR 0043). The x86 Core is the git submodule `packages/x86`, consumed through `workspace:*`, so editor code sees Core source changes after `pnpm --filter @specy/x86 build`. Core work is committed in the submodule, editor work in the monorepo.
- **Never** add `Co-Authored-By` trailers to commits; the owner strips them. Do not push: the owner pushes and tags releases.
- **Rebuilding the wasm.** `source ~/emsdk/emsdk_env.sh` (emsdk 6.0.9), then `packages/x86/compile_blink.sh`, which rebuilds `libblink/o` from nothing and copies `blinkenlib.{wasm,js}` into `blink-js/src/wasm/`. CI never rebuilds the wasm; the committed files are what ships. Print and record the sha256 lines the script prints.
- **Core checks.** In `packages/x86/blink-js`: `npm run type-check`, `npm test` (vitest, Node), `npm run build`, `npm run test:dist` (`tests/dist-smoke.mjs`, which also pins the exact list of root exports: add every new export there).
- **Editor checks.** From the root: `vp check`/`vp test` as the repo's scripts define them, and the browser verification recipes in the owner's notes (headless Chrome 153; Monaco needs a real click before typing; use your own dev server with HMR off and its own cache dir if other sessions edit the tree; start it with `node_modules/.bin/vp dev`).
- **Reading code.** Line numbers below were taken on 2026-10-12 and will drift; search for the named function.

## Decisions taken while planning

Taken by default, for the owner to overturn. Record any change in the design.

1. **The x86 Core ships and resolves the five libraries.** They live in the Core package as assets (like the assembler ELFs in `blink-js/src/assets/assemblers`), with their licences, and the Core reads the Executable's `DT_NEEDED` entries, follows them through the bundled libraries and writes only what is needed after each reset. The design says "the editor bundles"; the Core owning it matches [ADR 0030](../adr/0030-cores-resolve-runtime-library-members.md) (Cores resolve what a program needs) and keeps the Core usable alone. Fetched by URL, only when needed, so the editor's first load does not grow.
2. **The libraries are Ubuntu 26.04 LTS's,** the exact builds the spike ran: `libc6 2.43-2ubuntu2.4` (dynamic linker, `libc.so.6`, `libm.so.6`), `libgcc-s1` and `libstdc++6` `16-20260322-1ubuntu1`, all baseline x86-64 (the spike shows glibc 2.43 starts on Blink, which advertises no SSE4; a v2 or v3 build would refuse, upstream issue #172).
3. **One disassembler module.** Zydis is built into its own small wasm, exposed as a new Core subpath `@specy/x86/disassembler` together with a pure-TypeScript ELF analyser; it needs no Blink module. The Core uses it for instruction text (History, Call stack, `getInstructionAt`), the editor's Listing worker uses it for Listings. Zydis is not linked into `blinkenlib.wasm`, so there is one copy.
4. **Listings are generated in a dedicated Web Worker** (`listing.worker.ts`, spawned like the language workers with `?worker`), since libc's Listing is about 390,000 instructions.
5. **The Listing's addresses are in the gutter.** The Workbench shows a Listing with Monaco's `lineNumbers` option set to a function printing each line's address, so the text itself stays assembly. Instruction bytes are in the hover, not the text.
6. **One Linux layout for every x86 program,** assembled or loaded: gdb's addresses with randomisation off, including the heap starting right after the program's highest segment (page-aligned) and `mmap` allocating downwards from `0x7ffff7fff000` as Linux does. The x86 Reference environment is one Linux process; two layouts would be two environments. This changes addresses that assembled programs see, so the release is a major version (`@specy/x86` 7.0.0).
7. **`IsShadow` goes from the wasm build** if, as expected, it only protects host memory in Blink's linear-memory mode, which the browser build never uses (`FLAG_nolinear`); otherwise it narrows to what it protects. Go binaries `mmap` at `0xc000000000`, inside today's range.
8. **A program's fixed environment** is `PATH=/usr/local/bin:/usr/bin:/bin`, `HOME=/project`, `PWD=/project`, `LANG=C.UTF-8`, `TERM=xterm-256color`, `SHELL=/bin/sh`, `USER=user`, `LOGNAME=user`.
9. **Arguments** are UTF-8 without NUL, at most 1,024 words and 128 KiB in all; Blink's 200-character printable-ASCII limit (`CopySafeAscii`) goes for program arguments.
10. **Invented names**: two lists, 256 adjectives and 256 animals, lower-case ASCII, 3 to 9 letters, giving `FUN_<adjective>_<animal>` and `DAT_<adjective>_<animal>`; derivation in M7. Versioned as `v1`.
11. **Library Listings** are at `@lib/<soname>` (`@lib/libc.so.6`); library code is anything under `@runtime/` or `@lib/`.
12. **Patching uses a prompt.** "Patch instruction…" (context menu and a key binding) on a Listing line during a Debug session opens an input prefilled with the instruction; the Listing model stays read-only.

## Milestones

M1 to M5 are Core work and end in a Core release the editor pins; M6 onwards are editor work against it. Each milestone ends with its checks green and a commit. The owner reviews between M5 and M6.

### M1. Core: run glibc programs correctly

Files: `libblink/blink/argv.c`, `memorymalloc.c`, `syscall.c`, `machine.c`, `blinkenlib.c`; tests in `blink-js/tests`.

1. **Test fixtures first.** Add `blink-js/tests/fixtures/elf/` with a `build.sh` (gcc and g++, documented flags, not run by CI) and its committed outputs, each listed with its sha256 in a `README.md`:
    - `crackme.c`: the 20-line password check from the spike (`strcmp` against `hunter2`, `fgets`, `puts`), built as dynamic PIE (`crackme`), stripped (`crackme-stripped`), static PIE and static non-PIE.
    - `hello-atexit.c`: `atexit`, `printf` of `argv[0]` and `argc`, exit code 3; static PIE, static non-PIE, dynamic.
    - `math.c`: `cos(atof(argv[1]))`, linked with `-lm` (dynamic).
    - `cpp.cpp`: `std::string`, `std::vector`, `std::cout`, a caught exception (dynamic).
    - `argv-env.c`: prints every `argv` and `envp` entry.
    - `ptrace.c`: `ptrace(PTRACE_TRACEME)` twice, printing each result and `errno`.
    - `self-write.c`: tries `open(argv[0], O_WRONLY)`, `unlink`, `rename` on itself and prints each `errno`.
    - `crackme-argv.c`: the same check on `argv[1]` instead of standard input (dynamic PIE).
    - `overflow.c`: passes an unterminated stack buffer filled past its end to `strlen`, so it crashes inside libc (dynamic PIE).
    - `avx.c`: one function using AVX2 intrinsics that `main` calls only when `argc > 5`, compiled with `-O2`, plus `-mavx2` on that function (`__attribute__((target("avx2")))`), for Listing tests.
    - A Go `hello` (static), if a Go toolchain is available; otherwise note its absence.
      Committing static glibc binaries distributes LGPL object code: the fixtures `README.md` names the glibc version and source.
2. **`rdx` at entry** (result 2, upstream issue #179): `argv.c` writes `rdx = 0` unless `m->system->iscosmo`. Test: every static fixture exits with its code and output, `hello-atexit` printing its `atexit` line.
3. **Private file mappings copy, not map** (result 3). In `ReserveVirtual`'s `PAGE_MUG` path under `__EMSCRIPTEN__`, a `MAP_PRIVATE` file mapping becomes ordinary Blink memory filled from the file (read with `pread`, zero past the end of the file), with no host `mmap` per page; `MAP_SHARED` file mappings keep today's path. Replacing or unmapping such pages frees them like anonymous ones. Check the interplay with `debughistory.c` (a mapping during a syscall marks the step irreversible today) and with lazy anonymous pages (`tests/lazy-pages.test.ts`). Tests: `math` prints `cos`, `cpp` prints its lines and catches its exception; memory: record the wasm heap growth for `cpp` before and after (the spike's per-page design cost ~170 MB), and assert it stays under a bound you measure (expected tens of MB).
4. **`set_robust_list` (273) and `rseq` (334)** as Linux does for one thread on one CPU: `set_robust_list(head, len)` checks `len == 24` (`EINVAL` otherwise), records the head per thread, returns 0 (`get_robust_list` likewise if cheap). `rseq(area, len, flags, sig)` registers once (a second registration `EBUSY`, unregister with `RSEQ_FLAG_UNREGISTER` returns 0), writes `cpu_id_start = 0` and `cpu_id = 0` (and `node_id`, `mm_cid` 0 when `len` covers them) and returns 0. No restartable-sequence aborts are needed: nothing preempts or migrates the single thread. Add both to the `DESCRIBE_SYSCALL` table so `getImplementedSyscalls` lists them. Test: a dynamic fixture runs with no `ENOSYS` from either (via M4's event, or by checking `rseq`'s result in a small fixture).
5. **`ptrace`** (decision 17): `PTRACE_TRACEME` returns 0 the first time and `EPERM` after; every other request returns `ESRCH` (no tracee exists). Test: `ptrace` fixture prints `0` then `-1 EPERM`.
6. **LZCNT and TZCNT** (upstream PR #216): `AluLzcnt` computes `bits - 1 - bsr(x)` for a non-zero source and the two helpers swap names to what they compute; flags unchanged (CF for a zero source, ZF for a zero result). Test: `lzcnt`/`tzcnt` on 16, 32 and 64-bit operands including zero, in the existing ALU test style.
7. **Unsupported instructions.** Confirm what Blink does on an instruction it does not implement (expected: `SIGILL`), with the `avx` fixture run as `avx 1 2 3 4 5`. The stop reason must carry the faulting address; the text comes from M4.

### M2. Core: gdb's layout

Files: `libblink/blink/tunables.h`, `map.c`, `loader.c`, `syscall.c` (mmap), `memorymalloc.c` (`FindVirtual`), `blinkenlib.c` (`IsShadow`), `blink-js/src/blink-runtime.ts` (`isShadowAddress`).

1. **Constants and scaling.** Under `__EMSCRIPTEN__`, `InitMap` stops scaling the layout into 32 bits (the guest has its own page tables: `FLAG_nolinear`). Stack top `0x7ffffffff000`; PIE base `0x555555554000`.
2. **Heap.** `brk` starts at the page-aligned end of the main program's highest `PT_LOAD` segment, PIE or not (Linux without randomisation); `FLAG_imagestart` stays only as the PIE base.
3. **Top-down `mmap`.** Allocate non-fixed, non-hinted mappings downwards from `mmap_base = 0x7ffff7fff000` (Linux's base for an 8 MB stack limit with randomisation off: the stack top less 128 MB) into the highest free range that fits, as Linux's top-down allocator does, wrapping to the bottom of the address space only when nothing above fits. The dynamic linker is mapped through the same allocator (so it lands just under `mmap_base`, as under gdb) instead of at `FLAG_dyninterpaddr` or 16 MB below a PIE (`loader.c:460`). A hinted mapping takes its hint when free, the allocator otherwise.
4. **`IsShadow`** per planning decision 7: establish whether it guards anything in the non-linear build (read `debughistory.c:341`'s comment and `SpyAddress`/`LookupAddress2`), then remove it there or narrow it; keep `isShadowAddress` in TypeScript consistent and update its export only through `dist-smoke.mjs`.
5. **Tests to update or add.** `tests/memory-regions.test.ts` (it sets `rsp = 0x4fffffff0000` and asserts the stack top and heap break), `tests/undo-capture.test.ts:535` ("Blink's own mmap() puts anonymous pages at 0x80000000": mmap'd stores become reversible, so the test inverts), `tests/write-values.test.ts:399` (`isShadowAddress`), `tests/lazy-pages.test.ts` (8 MiB stack; `0x10000000` unmapped). New: a dynamic fixture's PIE at `0x555555554000`, the dynamic linker under `0x7ffff7fff000`, libc below it, the stack top `0x7ffffffff000`, the heap right after the program; reading and undoing a store into a PIE's `.data` and into an `mmap`'d page.
6. **Editor-visible addresses.** Search the editor and the x86 Language course content for addresses of the old layout (`0x4fff`, `0x88000000`, `0x80000000`; the spike found only `memoryRegions.test.ts`'s synthetic values) and update any prose that quotes one.

### M3. Core: libraries, arguments, environment and the Executable's File

Files: `blink-js/src/blink-runtime.ts`, `x86-emulator.ts`, `file-system.ts`, `project-file-system.ts`, `types.ts`, `index.ts`, `resources.ts`; `libblink/blink/blinkenlib.c`, `blinkenlib_bindings.cpp`, `open.c`, `syscall.c`; new `blink-js/scripts/fetch-linux-runtime.sh`, `blink-js/src/assets/linux/`.

1. **Fetch script.** `fetch-linux-runtime.sh` downloads the three `.deb` packages of planning decision 2 from `archive.ubuntu.com`'s pool with pinned sha256 sums, extracts `ld-linux-x86-64.so.2`, `libc.so.6`, `libm.so.6`, `libstdc++.so.6` and `libgcc_s.so.1`, and writes them with a `manifest.json` (soname, install path, package, version, sha256, licence) and `NOTICE.md` plus the licence texts (LGPL-2.1, GPL-3.0 with the GCC Runtime Library Exception) into `src/assets/linux/`. The outputs are committed; `scripts/copy-assets.mjs` copies them into `dist`. The NOTICE names the Ubuntu source packages (`glibc`, `gcc-16`) and their versions as the source offer.
2. **Resolution.** Build M4.3's ELF analyser first; this step uses it. A new `loadExecutable(bytes, options?)` (async) parses the ELF, checks it is supported (see M6.1's rules, which live here so the Core refuses what it cannot run with the same reasons), reads `PT_INTERP` and `DT_NEEDED`, follows `DT_NEEDED` through the bundled libraries' own, fetches the needed ones once per module (cached), and calls `loadElf`. It resolves to an `X86ExecutableInfo` (`{ pie, interpreter, needed, missing: string[] }`). A needed library that is not bundled is reported in `missing` and does not stop the load: the dynamic linker then fails with its own message (`error while loading shared libraries: libcrypto.so.3`), which reaches the program's stderr. Keep `loadElf` for callers that need no libraries.
3. **Writing them after each reset.** A `systemFiles` map like `tools`, written in `startProgram` right after `resetFileSystem`, with `FS.mkdirTree`, at `/lib64/ld-linux-x86-64.so.2` and `/lib/x86_64-linux-gnu/<soname>`, mode `0755`. Not under `/project` (a `/project` descriptor cannot be `mmap`ped, `syscall.c:1311`).
4. **`loadElf` state.** `loadElf` also clears `layoutUnits` and `lastSourceCode`, so `getMemoryLayout()` and `getCompiledCode()` do not describe the previous Build.
5. **Arguments and environment.** Replace the space-split argv string with a native API that takes `argv` and `envp` as arrays (a NUL-separated buffer through the bindings is fine): `setProgramArguments(argv0: string, args: string[])` and the fixed environment of planning decision 8, applied at the next start. Limits per planning decision 9; reject beyond them with an error the editor can show. `argv[0]` is what the caller passes (the editor passes `./crackme` or `./main`); `AT_EXECFN` stays the real path. Wire `blinkenlib.c:setupProgram`'s `vars` (today `0`, marked TODO). Test: `argv-env` prints exactly what was set.
6. **Protecting the running Executable's File** (decision 16). `setProtectedPath(path | null)` names a `/project` path; while a program runs, opening it for writing or with `O_TRUNC` and `truncate` fail with `ETXTBSY` (Linux 26), `unlink` and `rename` of it (either side) with `EBUSY` (Linux 16; a documented deviation from Linux, which allows them). Implement in `project-file-system.ts`'s `fileStreamOps.open`, `fileOps.setattr`, `directoryOps.unlink`/`rename` (add Emscripten's `ETXTBSY` 74 and `EBUSY` 10 to its `ERRNO` table; `xlat.c` translates them). Reading stays allowed. Test: `self-write` prints the three errors; other Files stay writable.

### M4. Core: disassembler, breakpoints, objects and events

Files: new `blink-js/src/disassembler/` (TypeScript, Zydis wrapper C, its wasm), `blink-js/src/elf/` (analyser; move `elf-symbols.ts`'s parsing here), `x86-emulator.ts`, `native-history.ts`, `blink-runtime.ts`, `types.ts`, `index.ts`, `tsdown.config.ts`, `package.json` exports, `libblink/blink/syscall.c`, `blinkenlib.c`, `blinkenlib_bindings.cpp`, `wasm-types.ts`; new `compile_zydis.sh` at the package root.

1. **Zydis wasm.** Vendor Zydis 4.1.1 and Zycore at the commit Zydis pins (`0b2432ced0884fd152b471d97ecf0258ff4d859f`) under `packages/x86/third_party/zydis`, amalgamated with Zydis's `assets/amalgamate.py` (note: `git clone --recurse-submodules` fails under the host's mise `gettext.sh` shim; fetch Zycore by commit instead), MIT licence kept. `compile_zydis.sh` builds `zydis.wasm` with emsdk 6.0.9 (`-O2`, a C wrapper exporting batch decoding), copies it into `blink-js/src/disassembler/`, prints its sha256. The spike's build was 392 KB.
2. **Batch API.** `disassemble(bytes: Uint8Array, address: bigint, options?): DecodedInstruction[]` decodes a whole range in one wasm call. Each instruction: `address`, `length`, `mnemonic`, `text` (NASM-flavoured, below), `operands` as structured data the Listing needs (`branchTarget` for a relative jump or call; `memoryTarget` for a RIP-relative operand, the absolute address it reaches, and the operand's text span so the editor can replace it with a label), `isCall`, `isJump`, `isConditional`, `isReturn`, `isInvalid` (undecodable bytes become one-byte `db 0xNN` entries). Formatting: Zydis's Intel style with formatter hooks so the text reads as NASM: no `ptr` (`qword [rax]`), lower-case hex (`ZYDIS_FORMATTER_PROP_HEX_UPPERCASE` off), `[rel 0x…]` for RIP-relative with its absolute target, size keywords where NASM needs them, `endbr64` as itself. Throughput target: libc's `.text` in under 0.5 s in Node.
3. **ELF analyser** (pure TypeScript, exported from the same subpath): headers, program headers (`PT_LOAD`, `PT_INTERP`, `PT_DYNAMIC`), sections, `.symtab` and `.dynsym` with symbol versions stripped from names, `DT_NEEDED`, `DT_SONAME`, PLT stubs named from `.rela.plt` (`R_X86_64_JUMP_SLOT`, slot order) across `.plt` and `.plt.sec`, `.plt.got` stubs from `R_X86_64_GLOB_DAT`, the entry point, and `supported` with a reason (M6.1). Little-endian ELF64 only; anything else is unsupported, not a throw.
4. **Instruction text in the Core.** `getInstructionAt`, the History's rows and `getCompiledInstructions` take their `code` from Zydis on bytes read with the spy path (no HTML); Call stack names stay from `resolveSymbol`. Keep `blinkenlibGetDisassembly` untouched if anything still uses it, otherwise remove it in the major version. Test: an `endbr64` and an AVX instruction read back correctly through `getInstructionAt`.
5. **Address breakpoints.** `X86Breakpoint` gains `{ address: bigint }`; `resolveBreakpointAddresses` passes it through. Test: a breakpoint at the `crackme`'s `call strcmp@plt` stops with `rdi` pointing at the typed input and `rsi` at `"hunter2"`.
6. **Loaded objects.** `getLoadedObjects(): { path, soname?, base, end }[]` lists the main program, the dynamic linker and each library mapped from a file at offset 0 (Blink's file maps, the same ones `LoadFileMapSymbols` walks), with their load bias, so the editor can relocate link-time addresses and tell which object an address is in. Test: after `crackme` reaches `main`, the list has the PIE at `0x555555554000`, `ld-linux` and `libc.so.6` with their bases.
7. **Unimplemented-syscall event.** In `syscall.c`'s `DefaultCase` (and the `futex`/`prctl` defaults if they answer `ENOSYS`), an `EM_JS` hook calls an optional `Module.onUnimplementedSyscall(number)`; the runtime emits a new `unimplementedSyscall` event `{ number, name }` (non-fatal, no pause), with names from a static table of Linux x86-64 syscall numbers in the Core. Test: a fixture calling an unimplemented syscall emits it once per call.
8. **Single-instruction assembly** for patches: `assembleInstruction(text, address): Promise<{ bytes } | { error }>` runs the wasm NASM with `bits 64`, `org <address>` and `-fbin` (`wasm-assembler.ts:createNasmModule`, `callNasm`), returning its bytes or its first error line. Test: `je 0x555555555170` at a given address encodes the same relative jump as the original `jne`'s length allows.
9. **Exports and docs.** New subpath `@specy/x86/disassembler` in `package.json` and `tsdown.config.ts` (like `compiler-output`), inlining `zydis.wasm`; root exports added to `dist-smoke.mjs`; `blink-js/README.md` sections for loading executables, libraries, arguments, address breakpoints and the disassembler, in the owner's README style (library-only, no editor mentions, shaped like the existing README).

### M5. Core release

### M6. Editor: recognising and loading an Executable

Files: `lib/projectFiles.ts` (or a new `lib/executables.ts`), `lib/languages/X86/X86Emulator.svelte.ts`, `lib/languages/service/adapters/x86Adapter.ts`, `components/specific/workbench/EditorPane.svelte`, `routes/projects/+page.svelte`, `components/specific/project/Explorer.svelte`, `lib/Project.svelte.ts`.

1. **Recognition.** `executableKind(file): 'none' | 'supported' | { unsupported: reason }` from the File's first bytes, never its name, using the Core analyser's `supported`: `\x7fELF`, then class 64 (32-bit: "a 32-bit x86 program; only 64-bit x86-64 programs run"), machine x86-64 (others name the machine: "an ARM program"), type `ET_EXEC` or `ET_DYN` with an entry point (a relocatable object or a library: "an object file, not a program" / "a shared library, not a program"), OS ABI System V or GNU. A File is an **Executable** when it is `supported` and the Project is x86.
2. **Build.** In `compileSources`, before `linksX86StartUnit`: when the Entry file is an Executable, call `core.loadExecutable(bytes)` and return `{ ok: true, diagnostics: [] }`; `missing` libraries produce a warning Diagnostic-like Log line naming them as not bundled. When the Entry is an unsupported ELF, the Build fails with the reason. Set the Core's protected path to the Entry's `/project` path (M3.6) and its arguments (M10) before the start.
3. **Live checks.** `_checkCode` and `analyzeX86Project` skip NASM when the Entry is an Executable (no Diagnostics, Build enabled); an unsupported ELF Entry gives one error Diagnostic with the reason, which disables Build as any error does.
4. **Projects page import.** `importFromData` recognises an ELF by its bytes before the zip and text branches: a supported one becomes `makeProject({ language: 'X86', name: <file name>, files: { [fileName]: bytesFile(bytes) }, entry: fileName })` through `importProject`; an unsupported one is refused with its reason in the toast. `FileImporter`'s `accept` must let extension-less files through.
5. **Explorer upload.** After `uploadFiles` writes a supported ELF into an x86 Project whose Entry is not already an Executable, offer "Make <name> the Entry file?"; an unsupported ELF uploads as a plain File with a toast giving the reason it cannot run.
    - Superseded on 2026-10-21 by [programs.md](./programs.md): the question is "Create a program for <name>?", asked only when the Project already has a Program and the Executable is no Entry; with none, the upload makes the Program.
6. **Displayed Executable.** `EditorPane` shows the Executable's Listing (M8) instead of the "Binary file" notice; other binary Files keep the notice.
7. Tests: recognition table for every fixture plus a truncated file, an ARM ELF header and a 32-bit one; import and upload flows in component tests; Build of `crackme` reaches its entry point in an emulator test (stopping at `main` comes in M9).

### M7. Editor: the Listing generator

Files: new `lib/listing/` (generator, word lists, worker, protocol), tests beside it. Pure functions over the Core's `analyze` and `disassemble`, run in `listing.worker.ts`.

1. **Input and output.** Input: the ELF bytes, its load base (from `getLoadedObjects`, or the planned base before a run: `0x555555554000` for a PIE, 0 otherwise; libraries only ever get Listings during a run), and the word lists' version. Output: `{ text, lines: LineInfo[], labels: Label[], functions, version }`, where each line records its kind (`section`, `label`, `instruction`, `data`, `blank`), its link-time address range and, for instructions, the address, length and bytes. Same input, same output, byte for byte (tests compare generated text to committed snapshots).
2. **Code.** Every executable section in address order (`.init`, `.plt`, `.plt.got`, `.plt.sec`, `.text`, `.fini`), decoded linearly, each starting with a `section .text` line. Runs of padding between functions (`int3`, multi-byte `nop` after a `ret` or `jmp`) stay instructions.
3. **Functions** (decision 7). Function starts are, in order of precedence for naming: `.symtab` function symbols, `.dynsym` symbols, PLT stubs named `<name>@plt` from relocations, `main` from the pattern below, the entry point as `_start` if unnamed, and every direct `call` target inside an executable section, named `FUN_<adjective>_<animal>`. A function runs from its start to the next function start. **`main` pattern**: within the first 64 instructions from the entry point, the last `lea rdi, [rel X]` or `mov rdi, imm` before a `call` to `__libc_start_main` (through its PLT stub, its `.plt.got` stub or an indirect `call [rel GOT]` whose slot's relocation names it); `X` is `main`. Static non-PIE binaries load `rdi` with `mov edi, imm32`: accept it.
4. **Invented names** (ADR 0045). For a function at link-time address `a`: `h = FNV-1a 64` over `a`'s 8 little-endian bytes; adjective `= h mod 256`, animal `= (h >> 8) mod 256`. Names are assigned in ascending address order; on a clash with any name already used (a symbol's or an earlier invented one), set `h = FNV-1a 64(h's 8 bytes followed by a counter byte 1, 2, …)` and retry. Word lists in `lib/listing/words-v1.ts`, frozen: rules in ADR 0045 (adjective and animal, nothing reading as a finding or an instruction or register, nothing offensive in any pairing). A test pins a dozen known address → name pairs so any change to the lists or the derivation fails loudly.
5. **Blocks** (decision 8). Every direct jump target inside a function that is not a function start gets `.LAB_n`, numbered from 1 in address order within its function. A jump into another function's block prints `FUN_x.LAB_n`; a target outside any function or section prints its address.
6. **Operands.** A direct `call`/`jmp`/`jcc` target prints its label. A RIP-relative operand prints its target's label with any offset (`[rel DAT_calm_lynx+8]`), and a `; "text"` comment when the target is a string (escaped, truncated at 40 characters). Absolute immediates that equal a symbol's address in a non-PIE binary are left as numbers (decision: no guessing which numbers are addresses), but get the symbol name as a comment.
7. **Data** (decision 9). After the code, `.rodata`, `.data` and other allocated non-executable sections as `db`/`dq` lines (16 bytes per `db` line, `dq` for an 8-byte-aligned value that is the address of a function or data label in the same binary), `.bss` and other `NOBITS` sections as `resb`. Strings: runs of at least 4 printable bytes (plus `\t`, `\n`) ending in NUL, in read-only or writable data, printed as `db "…", 0` with escapes; named `s_<text>` from their first 24 characters folded to `[A-Za-z0-9_]` (repeated `_` collapsed), a clash taking `_2`, `_3`. Other referenced data addresses get `DAT_<adjective>_<animal>` (same derivation, own counter space). `.symtab` object symbols keep their names.
8. **Header.** A comment block at the top: file name, `ELF64 x86-64`, PIE or not, static or the interpreter, `DT_NEEDED`, stripped or not, the entry point, and one line saying the Listing is generated and read-only.
9. **Performance.** Target: `crackme` under 50 ms, a static glibc binary under 1 s, libc under 3 s in the worker; the worker posts progress for anything over 500 ms and the editor shows "Generating the Listing…". Cache per (bytes sha256, base, version) for the session.
10. Tests: snapshot tests for `crackme`, `crackme-stripped` (functions named, `main` found, `strcmp@plt`, `s_Enter_password`), static non-PIE `hello-atexit`, `avx` (AVX lines print, no desync), and a hand-built ELF with data in `.text`.

### M8. Editor: the Listing in the Workbench

Files: `lib/languages/GenericEmulator.svelte.ts`, `BaseEmulator.svelte.ts`, `commonLanguageFeatures.svelte.ts`, `X86/X86Emulator.svelte.ts`, `lib/workbench/WorkbenchSession.svelte.ts`, `EditorGroup.svelte.ts`, `editorModels.ts`, `editorFileRouting.ts`, `lib/languages/service/uri.ts`, `lib/monaco/assemblyLanguageRegistry.ts`, `components/specific/workbench/EditorPane.svelte`, `components/specific/project/Editor.svelte`, `LibraryMemberNotice.svelte` (or a sibling notice).

1. **Listing documents.** A second channel beside `_buildLibraryFiles`: `listingDocuments` keyed by path (the Executable's own path for its Listing, `@lib/<soname>` for a library), each holding the generator's output. The Executable's Listing exists outside a Debug session too (opening the File shows it; generated with the planned base), and is regenerated with the real base at Build if they differ. Listings are never Project Files: `projectTabs()` and `returnToLiveFiles()` treat `@lib/` tabs like `@runtime/` ones; the Executable's own tab stays (it is a Project File).
2. **Display.** `displayedFile`/`displayedCode` return the Listing text for those paths; the editor is read-only there with a notice ("Generated Listing of crackme: read-only"); Monaco's `lineNumbers` prints each line's address (planning decision 5; restore the normal option for other Files); the model's language is x86 assembly so highlighting and Documentation hovers work. Hover on an instruction adds its address and bytes.
3. **Current line.** The X86 adapter maps an address to `(file, line)` with the Listings' line tables: inside the Executable to its path and line, inside a library to `@lib/<soname>` (generating that Listing in the worker the first time, then revealing the line), elsewhere to no file. `existsInBuild` and `revealSourceLocation` accept Listing paths. Applies to `_getInstructionAt`, `_getNextInstruction`, the History rows and the Call stack.
4. **Breakpoints** (decision 5). `SourceBreakpoint` becomes `{ file, line } | { file, address }` (link-time address). Toggling on a Listing instruction line stores the address; the gutter maps it back through the line table; lines without an instruction take none; library Listings take none (decision 11). The breakpoint resolver relocates to the load base and passes `{ address }` to the Core.
5. **Navigation.** For Listing models: a definition provider (label under the cursor → its line, including `FUN_x.LAB_n` and `<name>@plt`) and a reference provider (every line naming the label), from the generator's `labels`; register them for the Listing URIs only, beside the x86 providers. Ctrl+click on a label in a library Listing works within that Listing.
6. Tests: component tests for display and read-only state, breakpoint round trip (toggle, Build, stop, gutter), go to definition and references on a snapshot Listing; a browser check (M13).

### M9. Editor: start and library stepping

Files: `lib/languages/GenericEmulator.svelte.ts`, `X86/X86Emulator.svelte.ts`, `lib/runtimeAbi.ts`, `stores/preferencesStore.svelte.ts`, components showing the Preference.

1. **Library code** is any instruction whose `file` starts with `@runtime/` or `@lib/` (`inRuntimeLibrary` generalised and renamed `inLibraryCode`); an Executable's own instructions carry its path, so they are program code.
2. **Run to `main`** (decision 11). After an Executable's Build, the adapter runs with Undo off (`_setUndoRecording(false)`, today's floor) to a temporary address breakpoint at `main` (from the Listing's analysis, available at Build from the cached Listing or a quick `main`-pattern pass), so the Build stops at `main`'s first instruction, Undo history starting there. With no `main` it stops at the entry point. If the program asks for input or ends before `main` (a constructor reading stdin), it stops there as any run does. Do not single-step: the dynamic linker's ~100,000 instructions would be slow through `runStartCode`'s loop; the existing loop stays for `@runtime/` start code.
3. **Step over library calls**: unchanged logic, now covering `@lib/`: a Step at `call puts@plt` runs until the next instruction in the Executable (the return, or a callback such as `qsort`'s comparison).
4. **Preference.** `stepIntoRuntimeLibrary` keeps its key (saved Preferences keep working) and is relabelled "Step into library code"; with it on, Steps enter library Listings.
5. Tests: emulator tests on `crackme` (Build stops at `main`; Step over `call printf@plt` lands on the next instruction; with the Preference on, a Step enters `@lib/libc.so.6`); `hello-atexit` static (no libraries: Step goes into libc's functions inside the Executable, as decision 11 accepts).

### M11. Editor: patching from the Listing

Files: `lib/languages/GenericEmulator.svelte.ts` (`pokeMemory`), `X86/X86Emulator.svelte.ts`, Listing display components, `lib/listing/`.

1. **Action** (decision 13, planning decision 12): "Patch instruction…" on an instruction line of the Executable's Listing, only during a Debug session and not while running. An input prefilled with the instruction's text; Enter assembles with `assembleInstruction(text, address)`.
2. **Fit.** If the new encoding is longer than the old instruction: refuse, saying how many bytes it needs and has ("needs 6 bytes, the instruction it replaces has 2; it would overwrite the next instruction"). If shorter: pad with single-byte `nop` (`0x90`) to the old length. Then a Poke of exactly those bytes through `pokeMemory` (one Undo step).
3. **Display.** The patched line shows the new instruction (decoded from memory with the disassembler) and a gutter marker; padding `nop`s are shown on the same line (`je .LAB_2 ; + 1 nop`), so line numbers and the line table do not change. Undo of the Poke restores the line. The next Build shows the original again.
4. Tests: flip `jne` to `je` in `crackme`, run, see `Correct!` for a wrong password; Undo restores `jne` and behaviour; a too-long patch is refused.

## Risks and open items

- **Memory.** Even with M1.3, a C++ program maps ~6.5 MB of libraries plus the Listing models; watch the wasm heap and the Monaco models for libc (~390,000 lines). If Monaco struggles, show library Listings windowed (a few thousand lines around the current instruction, regenerated as it moves) rather than whole.
- **Undo across the dynamic linker.** `MarkUnjournaledSyscallEffect` makes some steps irreversible (e.g. `arch_prctl`); they all happen before `main`, outside the history (M9.2). A program that `mmap`s or `dlopen`s later will have irreversible steps; that is acceptable and already how the Core reports them.
- **Binaries the bundle cannot run**: other libraries (`libseccomp`, common in pwn sandboxes; `libcrypto`), newer glibc symbol versions, `RUNPATH` to a challenge's own libc (deferred). They fail with the dynamic linker's message plus M12.4's note.
- **Threads, sockets, `fork`** are compiled out of the browser build (`config.h`); programs using them get `ENOSYS` (and M12.2's note) or fail. Go binaries start threads; M1.1's Go fixture shows how far they get, recorded, not fixed.
- **Word lists** are frozen once an editor release shows them; have the owner review them before then.

# Source compilation implementation plan

Implementation authorized by the owner on 2026-10-03 after the design interview. The accepted vocabulary lives in [CONTEXT.md](../../CONTEXT.md); the requirements and decisions are in [source-compilation.md](./source-compilation.md), [ADR 0027](../adr/0027-source-compilation-starts-with-self-contained-programs.md), and [ADR 0028](../adr/0028-persist-compilation-records-with-transient-source-maps.md).

## Behavior and remaining decisions

- Offer Compile in the Workbench for `.c`, `.cpp`, `.cc`, and `.cxx` Files on MIPS, RISC-V, and RISC-V-64. Existing Explorer creation/upload supplies source and local headers; include a usable source template when creating a C/C++ File. Other Targets show an explanation rather than calling an incompatible compiler. The Interactive editor and exams do not acquire compilation implicitly.
- Use the public Compiler Explorer HTTPS API directly from the browser. Compile is explicit, requires connectivity, and sends the selected source and project-local text headers to that service. Identify the service in the Compile tooltip. Bound requests, time out, and report compiler/network errors in the editor without replacing the previous result. No proxy or remote execution is added.
- Start with verified GCC 14.2 presets for C/C++ and each supported Target, constrained to its supported instructions, ABI, and endianness. Default to `-O0`; offer named optimization levels without arbitrary flags. Disable PIE, stack protection, C++ exceptions, and RTTI; omit library/runtime linking. Persist the preset and optimization with the Compilation record. Keep provider, language, and Target-specific output preparation separate for future compilers and runtimes.
- Require a parameterless `int main(void)`/`int main()` program entry. Rename the compiler's `main` symbol through a compiler definition and prepend a Target-specific assembly `main` wrapper that calls it and exits through the simulator's service. Preserve data/labels/directives needed to assemble the program. Wrapper lines have no higher-level Source map. Unsupported external symbols or runtime requirements produce ordinary build diagnostics; do not simulate missing libraries.
- Derive `<full-source-path>.<target-extension>`. Reuse the recorded output path on recompilation. Confirm before replacing manually edited or unowned output, after compilation succeeds and before committing it. Recheck inputs/output after asynchronous work and confirmation; discard a superseded result. Compilation during a Debug session is disabled until Stop, following existing FileSystem locks.
- Commit output, saved provenance, transient mapping, and Entry path only after successful preparation. Open the generated output automatically. Do not automatically execute it; the existing Build, Run, Step, and Undo controls remain the execution interface.
- Keep maps in memory on the Project, outside its serialized data and guest Files. Persist bounded, validated Compilation records with source/output paths, input/output content fingerprints, Target, compiler preset, and optimization. Preserve them through browser saves, archive export/import, and sharing. Missing records remain compatible with older Projects. Saving a map never becomes a `.map` File.
- Invalidate mapping immediately on any compiler-input or generated-output edit/deletion, including changes through FileSystem APIs. Input changes mark output stale; output changes identify manual edits. Mapping does not return on Undo; explicit recompilation restores it. A reload with unchanged fingerprints says mapping is unavailable until recompilation, rather than incorrectly calling the assembly stale. Rename/move keeps provenance paths aligned where possible but invalidates mapping; generated output is not silently renamed with its source. An absent original input remains identifiable as stale.
- Show source and assembly side by side while a valid map exists; stack panes on narrow screens. Source remains editable before Build and is read-only during debugging. Clicking a line in either pane highlights its corresponding lines in the other, including one-to-many relationships and local-header locations. Execution and Undo highlight the corresponding higher-level line from the current assembly instruction. Lines without a mapping clear the source execution highlight. Source-level stepping and breakpoints are deferred.
- Keep runtime Build snapshots distinct from the transient compilation map: guest writes invalidate the live map; do not attach a map to assembly with different bytes. Selecting ordinary assembly continues to use the existing editor. Dispose pending requests and Monaco listeners on unmount.

## Control placement refinement

The owner requested that Compile and optimization move into the bottom execution dock, sharing Build's control styles. Source Files show Compile in Build's place; generated assembly keeps Build with Recompile beside it. The Compile button shows a spinner while a request is pending and offers Cancel. Unsupported Targets show a short explanation beside the disabled Compile button and omit optimization. Remove the compiler/service/signature labels above the editor and the success message after compilation; keep errors and stale/manual-edit notices. Entry behavior and its UI remain unchanged while alternatives are discussed.

Compiler diagnostics request plain output and defensively strip terminal controls from API responses. Prefer structured diagnostic text and locations, with a plain-text location parser as fallback. Function/include context and caret excerpts do not become separate errors; notes become related locations. Problems show clickable File/line/column positions, and C/C++ Files and headers do not acquire diagnostics from the assembly language service.

Verification after this refinement: 63 affected source-compilation, Workbench, and Monaco tests pass; Svelte checking reports zero errors with the same 32 existing warnings; targeted ESLint passes. Isolated Chromium checks pass for the desktop compile spinner, optimization control, compilation without a success message, Build/Step/Undo, edit invalidation, replacement confirmation, and reload. Mobile checks verify the bottom placement and stacked mapped panes; an unsupported M68K Project shows the inline warning and no optimization selector.

## Mapped section colors

The owner requested matching colored code sections, while explicitly deferring the Entry decision. Generate a color for each original source File/line using a hashed File-path offset and golden-angle hue spacing; colors are independent of compilation order and optimization, with no fixed palette to exhaust. Every contiguous assembly block mapped to that source line receives the same color, including disjoint blocks and local-header locations. Show subtle full-line backgrounds and matching gutter stripes in both panes. Startup and unmapped lines stay neutral. Selection, execution, and error highlights take precedence over the section backgrounds.

Colors are derived from the transient Source map and disappear with it on invalidation. Monaco groups contiguous ranges, and each editor owns and disposes its generated color styles so changing Files or closing the split view does not accumulate styles.

Scope colors to Monaco's persistent container: Build and Stop replace the inner view when switching between live and snapshot models. Ignore programmatic cursor moves when selecting source correspondence, and retain the user's selection through the unmapped startup wrapper until execution reaches mapped code.

Verified with 10,000 generated colors, compilation-order stability, contiguous ranges, unmapped gaps, and header locations. The 63 affected tests pass, Svelte checking reports zero errors with 32 existing warnings, and targeted ESLint/Prettier checks pass. Isolated Chromium checks confirm matching colors across both panes and header switches, light and dark themes, execution/Undo highlight precedence, cleanup after edit invalidation, and the stacked mobile view. Entry behavior remains unchanged.

## Implementation sequence

1. Add compilation types, record validation, fingerprints, language detection, presets, Compiler Explorer transport, diagnostics, and Target-specific assembly preparation. Verify against actual API responses.
2. Add saved records and transient maps to Project ownership/serialization, with FileSystem-based invalidation and rename handling.
3. Integrate the asynchronous Compile action and overwrite protection into the Workbench, expose a small Compile toolbar, and implement the mapped split view using existing Monaco editors.
4. Verify persistence and invalidation, mocked request failure/races/cancellation, mappings, and execution of actual compiler output through the real MIPS/RISC-V Cores. Run the affected tests, type checking, formatting/lint checks, and a production build if its prerequisites are available.

## Completion evidence

Implemented on 2026-10-03. All four implementation steps are complete. The remaining decisions above are the implemented defaults.

- `src/lib/sourceCompilation` separates saved provenance and mapping types, Compiler Explorer request/output handling, and transactional publication. `Project` owns transient maps and serialized records. The Workbench supplies Compile/Recompile and optimization in the execution dock, cancellation, overwrite confirmation, stale notices, and the editable source/assembly split view. Creating C/C++ Files supplies a `main` template.
- Compiler output preserves executable code and data, normalizes GNU data sections for the existing Cores, drops debug sections/directives/labels, disables GCC section anchors, and adapts GNU MIPS immediate `slt` forms. The startup wrapper exits with the program's return value. Source-map lines are recomposed after these transformations; startup and unmapped lines carry no source highlight.
- Captured actual Compiler Explorer responses for C and C++ at `-O0` and `-O2` on all three Targets. Twelve offline integration cases assemble those responses with the real MIPS/RISC-V Cores, execute a program using a local header, global data, a loop and functions, verify the return value, and exercise Step/Undo. Additional tests cover diagnostics, malformed/oversized responses, persistence, invalidation, renames, cancellation, overwrite protection, and asynchronous races.
- Automated checks: 60 source-compilation/Project/archive tests, 190 Workbench/storage/Emulator/language-session regression tests, and 13 Monaco tests passed (263 total). Svelte checking reports zero errors with 32 existing warnings; targeted ESLint and Prettier checks pass. The production build completes successfully.
- Browser verification used an isolated Chromium session and a live Compiler Explorer request, verifying that direct browser access works. Further checks with captured responses passed for Entry selection, source-to-assembly highlighting, execution/Undo source highlighting, manual-edit invalidation, declining and accepting the overwrite popup, source-edit stale warnings, and save/reload with preserved provenance and no serialized map. The production build's mobile view was verified at 390 × 844 pixels: both panes remain visible and stack vertically. No uncaught page errors occurred.
- Verified boundaries: Compile needs internet access and sends source/local headers to Compiler Explorer. Programs require parameterless `int main()` and remain self-contained; library calls, unsupported instructions, and runtime initialization are outside this release. Rust, multi-translation-unit linking, additional Targets, standard runtimes, source breakpoints, and source-level stepping remain future work. The design records the GNU assembler path as a candidate for future x86 support instead of assuming Intel syntax supplies NASM-compatible output.

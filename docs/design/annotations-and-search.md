# Renames, comments and project-wide search

Status: researched and planned 2026-10-22. The owner's four decisions (renames, what drops them, comments, the Search panel) are fixed; the decisions marked _proposed_ and the [Open questions](#open-questions) were settled the same day by the organiser, on the owner's instruction to implement, and the owner may revisit any of them. Implemented on 2026-10-22 and 23, documentation included ([Implementation](#implementation)); the closing review of the whole change remains. Terms are in [CONTEXT.md](../../CONTEXT.md), the new ones among them ([Glossary terms](#glossary-terms)).

[The reverse-engineering UX design](./reverse-engineering-ux.md) deferred "Rename and comments, saved in the Project, fed into both the Listing and the decompiler" and "Search across every function's Pseudocode". This record takes up both:

- **Annotations** on an imported **Executable**: **Renames** of its global names (functions, data, strings, jump targets) and of the **Pseudocode**'s local variables, and **Comments** on its lines and functions, shown in the **Listing** and the Pseudocode, saved with the **Project**.
- A **Search panel** that finds text in the Project's **Files**, in each Executable's Listing and in the Pseudocode of all its functions.

`E/` is `packages/asm-editor/src/`, `D/` is `packages/decompiler/`, `G/` is `packages/decompiler/ghidra/decompile/cpp/`, and `J/` is Ghidra 12.1.4's Java sources, which are not vendored and were downloaded for the research (`Ghidra/Features/Decompiler/src/main/java/` and `Ghidra/Framework/SoftwareModeling/src/main/java/`). Line numbers are from `feat/pseudocode` at `f6bb2f2b` and the decompiler at `dbedf86`, and will drift.

## Decisions

### Annotations

1. **What they are** (owner, 1 and 3). An **Annotation** is a Rename or a Comment a person makes on an Executable that is a File of the Project. Four kinds:
    - a **global rename**: a function, a data label, a string label (`s_…`) or a jump target (`.LAB_n`) of the Executable's own Listing, keyed by its address in the file;
    - a **local rename**: a variable or parameter of one function's Pseudocode, keyed by the function and the decompiler's identity for the variable (decision 15);
    - a **line comment**: text at the address of a Listing line that has one, an instruction or data;
    - a **function comment**: text for a function, Ghidra's plate comment.

    Not annotatable: a **Bundled library**'s Listing (`@lib/…`), the **Build output** (never saved, [ADR 0050](../adr/0050-the-built-program-is-a-build-output-never-saved.md)), and any Library code. A read-only Workbench takes none.

2. **Saved on the Executable's File record** (_proposed_, the organiser's, kept). `ProjectFile` (`E/lib/projectFiles.ts` :19) gains `annotations?`, beside its `edits`, as [ADR 0047](../adr/0047-byte-edits-are-kept-apart-from-the-original-bytes.md) put the Byte edits beside the original bytes:

    ```ts
    /** `0x` and lower-case hex digits: a link-time address, the file address ADR 0045 names by. */
    type FileAddress = string
    type Annotations = Readonly<{
        names?: Readonly<Record<FileAddress, string>>
        comments?: Readonly<Record<FileAddress, string>>
        /** By the function's address. */
        functionComments?: Readonly<Record<FileAddress, string>>
        /** By the function's address, then the variable id (decision 15). */
        locals?: Readonly<Record<FileAddress, Readonly<Record<string, string>>>>
    }>
    ```

    Addresses are link-time ones, as [ADR 0045](../adr/0045-invented-names-are-frozen-words-from-file-addresses.md) derives Invented names from, so an annotation does not depend on where a PIE is loaded. On the record, annotations move with a rename of the File, go with its deletion, and travel with every save, autosave, share link and the **Project archive**. Proposed as ADR 0055 ("Annotations are kept on the Executable's File and go with its content"), since the saved format is hard to reverse. Rejected: a Project-level map by path, which every rename, deletion, upload and program write of a File would have to keep in step by hand.

3. **Dropped with the content** (owner, 2). Whatever makes a File's whole content new drops its annotations: an upload over it (`FileSystem.writeBytes`, the Explorer's upload), Keep as File over it, and a program's write during a **Debug session** (the session rebuilds the record from the new bytes). What keeps them: a **Byte edit** and the Hex editor's Undo and Redo of one (overwrites only: addresses do not move), typing into the Hex view of an Executable stored as text (`overwriteText`, also an overwrite), and renaming the File. Instruction Undo of a program's write brings back the record it replaced, annotations included, as it brings back Byte edits today.

4. **Stale annotations stay** (_proposed_). Nothing is pruned when it no longer applies after a Byte edit: a rename whose address no longer starts a label, a comment at an address no line starts at, a local whose id the decompiler no longer reports. Each shows again when the bytes bring its address back, Undo included. A comment at an address inside a line shows on that line; a function comment whose function is gone shows above the line holding its address.

5. **Limits** (_proposed_). A name has at most 128 characters; a comment at most 4,000 characters and 40 lines; a Project's annotations at most 256 KiB of text together, checked by `cleanFiles` as the 16 MiB of Files are, so that an archive's 1 MiB manifest (`E/lib/projectArchive.ts` :41) holds them beside the Byte edits.

### Renames

6. **What can be renamed** (owner, 1; _proposed_ in detail). Global: a function, data, string or jump-target label of the Executable's own Listing, by its link-time address. The rename replaces the name operands use there (`primary` in `E/lib/listing/generateListing.ts` :369); other names at that address (aliases) stay. Not renamable: PLT stubs (`name@plt`, `name@plt_resolver`) and GOT slots (`name@got`), whose names are the library symbols the dynamic linker binds, and which the Pseudocode prints as the library function. Local: a variable or parameter the decompiler reports with an id, except a parameter whose name a C declaration fixes (`puts(char *s)`), which the package marks `locked`.

7. **What a name may be** (_proposed_, the organiser's rule narrowed). A C identifier, `[A-Za-z_][A-Za-z0-9_]*`, of at most 128 characters: narrower than the Listing's name characters (`NAME_CHARACTER`, `E/lib/listing/listingNavigation.ts` :24, which also takes `$ # @ ~ . ?`), because the Pseudocode prints a name as given (`undefined8 my main(void)` for a name with a space, research [Global names](#global-names-in-the-decompiler)) and `@` and `.` already mean something in the Listing (`@plt`, `.LAB_3`). Not a C or C++ keyword, a word of Ghidra's (`undefined`, `undefined1`…`undefined8`, `code`, `bool`), an x86 register's name or a NASM operand word (`byte` to `zword`, `ptr`, `rel`, `abs`, `short`, `near`, `far`, `strict`, `wrt`, `seg`), which would read as the instruction's own text in the Listing and the Patch prompt. Uniqueness:
    - a global name differs from every other label name of the Listing, raw, invented or renamed (the organiser's rule, until [demangling's phase 2](./cpp-demangling.md#phase-2-demangled-names-in-the-listings-text) gives the Listing name spans);
    - a jump target's differs from its function's other jump targets; it is written `.name` inside its function and `FUN_x.name` from elsewhere, as `.LAB_n` is;
    - a local differs from its function's other variables and from every global name (Ghidra would print `::printf` for a clash), and does not look like one of Ghidra's own names (`iVar1`, `local_10`, `param_2`, `uStack_48`, `in_…`, `unaff_…`, `extraout_…`), which would read as the decompiler's.

    A refused name says why in the prompt.

8. **Where a global rename shows** (owner, 1; _proposed_ in detail). Everywhere the name does ([table](#where-a-global-name-shows-and-what-a-rename-regenerates)): the Listing's label line and every operand, `dq` pointer and comment naming it, Go to Symbol, the **Symbols panel**, the Pseudocode, its header and hovers, the Call stack, the memory view's label for it, the memory address box and the Patch prompt. The hover says what it was: "Renamed from `FUN_brave_otter`", then that name's origin as today ("An invented name: …"). Invented names of other addresses never change, since renames apply only once every name is claimed (ADR 0045).

9. **A rename overrides a Demangled name** (_proposed_, the organiser's). The label line and operands write the person's name with no demangled comment; lists show it; the hover keeps every demangled form under "Renamed from `std::string::operator+=`"; the Symbols panel's filter also matches the raw, short and signature forms; the Pseudocode prints the name in the global scope, without the namespaces, its `symbol` still the mangled name so `glibc.h`'s C++ declarations bind (decision 17).

10. **Reset name** (_proposed_, the organiser's) removes a rename, global or local. A global rename whose name another label took meanwhile (a Byte edit gave the program a new symbol) is not applied, and the label's hover says so, until one of the two changes.

### Comments

11. **Line comments in the Listing's text** (owner, 3). A comment is written into the Listing:
    - one line of at most 60 characters goes at the end of its line, after the comments the Listing writes itself, with a second semicolon between them: `    lea rdi, [rel s_hunter2]        ; "hunter2" ; the password`;
    - anything longer, or of several lines, goes above the line, after any labels of that address, as `    ; …` lines wrapped at word boundaries to 100 columns, its own line breaks kept, as Ghidra's PRE comments sit;
    - the words are text: like a Demangled name's comment (`ListingIndex.inDemangledComment`, `E/lib/listing/listingNavigation.ts` :137) they are never a name to hover, follow or double-click, nor a Reference, since a comment saying "calls main twice" names nothing.

12. **Function comments** (owner, 3). In the Listing, `; …` lines between the blank line before the function and its label, wrapped likewise; in the Pseudocode, Ghidra's header comment above the declaration, before Ghidra's own header warnings.

13. **Comments in the Pseudocode through Ghidra's comment database** (owner, 3). Line comments go in as Ghidra's PRE comments (`user2`, which Ghidra's Java side sends for PRE and its printer shows by default) at their addresses, and Ghidra puts each before the statement whose code holds the address; the function comment as its `header` comment. A comment Ghidra cannot place (on an instruction with no p-code, such as the entry's `endbr64`, or in code it found dead) is listed under Ghidra's own heading "Comments that could not be placed in the function body:" at the top, so no comment a person wrote is hidden (_proposed_). A comment's `*/` is written `* /`, so the C reading does not end early.

14. **A comment set on a Pseudocode line** (owner, 3) is stored at that line's first mapped instruction: the first instruction of the first block mapped to it, the address a Breakpoint set there would take first (`pseudocodeBreakpointAddresses`, `E/lib/pseudocode/pseudocodeMap.ts` :104). On the function's declaration line, Comment… edits the function comment. It is offered on no other line (braces, declarations). Research measured the alternative of the line's largest address ([Where a Pseudocode line's comment lands](#where-a-pseudocode-lines-comment-lands)); open question 2.

### The decompiler's side

15. **Variable ids** (owner, 1; _proposed_ in detail). The package reports, on each variable token and in a list per function, an id built from Ghidra's storage for the variable:
    - `stack:-0x98`: a variable tied to the stack, by its offset alone, so it survives a change of size;
    - `register:0x0:4@+0x8e`: storage space, offset and size, and its first use as an offset from the function's entry (as Ghidra's Java side keeps a first-use offset), so the id does not depend on where the image is placed; a parameter's first use is `@-0x1`, the entry minus one, as Ghidra writes it;
    - `join(register:0x10:4+register:0x0:8):12@+0x2a`: a value split across registers, by its pieces, since Ghidra numbers join addresses in the order it meets them;
    - `hash:0x3f276f9932@+0x6c`: a temporary, by Ghidra's dynamic hash and its use, and any storage id that Ghidra's own lookup finds ambiguous.

    The editor stores ids as opaque strings. Stack ids survive almost every Byte edit, register ids survive while the instruction that sets them stays, hash ids are the most fragile ([Robustness](#robustness-of-the-ids)).

16. **Names applied after the analysis** (_proposed_; open question 1, which blocks P0). The decompiler analyses a function as it would without names, then, before printing, renames each variable whose id was given a name, made unique in its scope. The code and every other variable's name stay as Ghidra printed them. This is the owner's "locked local names" at the last moment rather than Ghidra's own route, in which the Java side sends a renamed local as a name recommendation that `ActionNameVars` applies mid-analysis: research found that route renumbers other default names (`pcVar2` becomes `pcVar1`), misses parameters the code never reads and temporaries whose hash changes after naming, and needs this same final step for those anyway ([Locked names](#how-ghidra-keeps-a-renamed-local)).

17. **The package API** (_proposed_). Per decompile call, beside `maxInstructions` and `timeLimitMs`: `locals` (ids and names), `comments` (addresses and texts), `functionComment` and `unplacedComments`; tokens gain `variable` (the id) and `comment` (`'user'` or `'warning'`); a decompiled function gains `variables` (each id, kind, name, Ghidra's description of its storage, and `locked` for a declared parameter). The program image stays version 3, so a comment or a local rename never reopens a program; global renames need no package change, the editor reopening the program with the person's name as the function's or datum's `name` and its raw name kept as `symbol`. Backward compatible: a call without the new options decompiles as today, byte for byte. Details in the [plan](#p0-the-decompiler-package-decisions-13-15-16-17).

### Editing, Undo and saving

18. **How a person makes one** (_proposed_; the organiser's keys kept, F2 added).
    - **Context menu**, in a group after the debugging one: Rename… on a label line or an operand naming a label in the Listing, and on a function, global or variable in the Pseudocode; Comment… on a Listing line with an address (on a function's label line, the function comment), and on a Pseudocode line with instructions or its declaration; Reset name and Delete comment where there is one to take away; Undo and Redo of the last annotation (decision 19).
    - **Keys**, while a Listing's or Pseudocode's text has the keyboard (Monaco's `editorTextFocus`, as Space for Patch and F9 have it): `n` and F2 for Rename…, `;` for Comment…, as IDA, Binary Ninja and Cutter have `n` and `;`, and VS Code F2. Both views are read-only, so the keys type nothing there, and Monaco's own F2 needs a writable model.
    - **Prompts** over the line, as the Patch prompt opens (`E/components/specific/workbench/PatchPrompt.svelte`): a one-line field for a name, with the reason a name is refused under it; a multi-line field for a comment, where Enter saves, Shift+Enter starts a new line, Escape cancels and saving it empty deletes the comment.
    - **The Symbols panel**: Rename… and Reset name in a function row's menu and on F2 while a row has the keyboard; on a touch screen, a row button.

19. **One undoable step each, in the Workbench's annotation history** (_proposed_, the organiser's). An annotation history per File for the Workbench session, shared by both panes, like the Hex editor's `ByteEditHistory` (`E/components/specific/workbench/hex/byteEditHistory.ts`): each rename, reset, comment or deletion is one step, Ctrl+Z undoes and Ctrl+Shift+Z or Ctrl+Y redoes it while that Executable's Listing or Pseudocode has the keyboard, and the context menu has both. It starts again when the File's content is replaced and follows a rename of the File. It is neither instruction Undo (Shift+↑) nor Monaco's text Undo.

20. **Saving** (_proposed_). Annotations change through the **FileSystem** (`FileSystem.annotate`), whose File change notice already schedules the save (`WorkbenchSession` :968-975), so autosave saves them, Save waits for them, and the unsaved-changes comparison sees them (`contentKey`, `E/lib/Project.svelte.ts` :329, serializes `files`). During a Debug session the change also goes into the FileSystem session's record of the File, so its next publish keeps it. A Build's staleness and a Compilation record's fingerprints ignore annotations (`sameFileContent`, `fileFingerprint`), so a rename never makes the Build output stale.

21. **The archive** (_proposed_). A manifest's File entry gains `annotations`, in a version 4 written only when some File has annotations, following the archive's rule of the oldest version that holds a Project (`E/lib/projectArchive.ts` :29-38); older editors refuse version 4 as an unknown version, since they refuse unknown keys in a File entry anyway (:279-296). A Project with annotations never downloads as the single source file (`isSingleSourceProject`).

22. **What regenerates, and when** (_proposed_).
    - A global rename: the Listing is generated again with the annotations, in its worker; the Pseudocode's program is opened again with the new names; the function each Pseudocode pane shows is decompiled again.
    - A comment: the Listing is generated again; the function holding it, or the function a function comment is for, is decompiled again.
    - A local rename: only its function is decompiled again.
    - A pane keeps showing the old text until the new is ready, as a Pseudocode pane does today, and then keeps its cursor and first visible line on the same address.
    - During a Debug session the running program's Listing and Pseudocode take annotations at once: the x86 adapter reopens its Listing with them, as it already reopens one at another load base.

### The Search panel

23. **A panel of its own** (owner, 4). The **Search panel** is a side panel with its own rail entry ("Search", after Symbols, before Testcases) in every Target, and Ctrl+Shift+F (⌘⇧F on a Mac) opens it from anywhere in the Workbench with the query focused and filled with the editor's selection when that is on one line. The key is a new shortcut, "Search the Project", rebindable in Settings like the others. A host can switch it off (`BuiltinPanelId` gains `search`); an Exam does, since it hides the Explorer.

24. **The query** (owner, 4). One box, with Match case, Match whole word and Use regular expression toggles (JavaScript's syntax), and optional "Files to include" and "Files to exclude" boxes taking comma-separated patterns (`*.c`, `src/**`, `?`), a pattern without `/` matching a name in any folder. Listing and Pseudocode results are filtered by their Executable's path.

25. **Where it looks** (owner, 4; _proposed_ in detail). Three ticks, labelled "Look in":
    - **Files**: every text File of the Project (assembly, C and C++, Markdown, text, JSON, …), the Generated assembly among them, being Files; not the Runtime library's members, the Build output or an Executable stored as text;
    - **Listings**: each Executable File's Listing, with its annotations, generated in the Listing worker where no pane has made it; not a Bundled library's or the Build output's;
    - **Pseudocode**: every function of each Executable but its PLT stubs (named `@plt`, `@plt_resolver`, or starting inside `.plt`, `.plt.sec` or `.plt.got`, where the first stub has an Invented name); a static program's glibc is the program's and is included.

    Listings and Pseudocode are offered only in a Project with an Executable. Files and Listings start ticked and Pseudocode unticked, and the person's choice is kept with the Workbench layout (open question 4).

26. **Results** (owner, 4). Grouped by File, the Pseudocode's by Executable then function (by the name lists use), each row the line's number and its text with the matches highlighted. At most 2,000 rows are shown with the count of the rest and Show more; the panel says how many matches in how many Files. Clicking a row or pressing Enter opens it: a text File with the match selected; a Listing at the line, found again by its address; a function in the Decompile view, its Listing beside it, at the match. The jump goes into the pane's **Navigation history** when the pane left a Listing or Pseudocode place, as Go to Symbol does.

27. **Searched as you type** (owner, 4). Files and Listings are searched 150 ms after typing stops, in a search worker that keeps a copy of each text, sent again only when it changes. A query of any kind that runs past 2 s ends the worker, which is started again, and the panel says "The search took too long", for a regular expression that backtracks; plain and whole-word queries take milliseconds ([Search cost](#search-cost)).

28. **The Pseudocode in the background** (owner, 4; _proposed_ in detail).
    - While the panel is shown with Pseudocode ticked, each Executable's functions are decompiled in the Pseudocode worker at background priority: one at a time, only when no Pseudocode a pane shows is waiting, with a 5-second limit each.
    - Functions reachable from `main` by direct calls come first, breadth first, then the rest by address, so a static program's own code is searched before its glibc.
    - The panel streams results and says "Decompiling 120 of 290 functions of factcheck", with Cancel; closing the panel or unticking Pseudocode stops it, keeping what was done.
    - A function past the limit is listed as not searched, with Try again, and its failure is not kept, since a less busy machine may beat it.
    - The cache keeps each function's text and where its function and data names are, keyed by the File's content, Byte edits and load base, and each function's entry also by its locals and comments. A global rename rewrites the cached texts from those names' targets without decompiling again; a local rename or a comment decompiles its function again. It lives as long as the Workbench session and is never saved.

29. **Not now**: Replace across text Files (owner, 4), searching a Bundled library's Listing, and the Documentation, which keeps its own search (Ctrl+K).

## Research

The experiments ran in Node 24 against the editor's own modules (the Listing generator, `programImage`, the demangler) and the decompiler package, natively and in wasm, in a scratch copy of the package with a prototype host (about 780 lines added), and on these programs: `crackme` and `crackme-stripped` (C, `D/js/tests/fixtures/elf/`), the FactCheck-like C++ program `factcheck` (356 functions), the x86 Core's `cpp` fixture (`packages/x86/blink-js/tests/fixtures/elf/cpp`), the static `hello-atexit-static` (1,111 functions) and the Bundled `libc.so.6` and `libstdc++.so.6`. The machine was shared and at times heavily loaded (a load average from 3 to 40), so times are medians of repeated runs, and a busy run can be twice a quiet one. The scripts and outputs stayed in the session's scratchpad.

### How Byte edits are saved, which annotations follow

- **The record.** A `ProjectFile` is `{ encoding, content, edits? }` (`E/lib/projectFiles.ts` :19-23). `cleanFiles` (:401-445) copies only those three fields (:428-432), so any other field is dropped on every load, import and share link: annotations need adding there. `withByteEdits` (:264-276), which every Byte edit and the Hex editor's Undo go through (`FileSystem.commitByteEdits`, `E/lib/languages/peripherals/FileSystem.ts` :387), also builds a new record of those three, and would drop them too.
- **Replacing content.** `FileSystem.writeBytes` (:271-278) makes a new record from the bytes (`bytesFile`), which is how decision 3's drop falls out: the Explorer's upload (`E/components/specific/project/Explorer.svelte` :587) and Keep as File (:762) use it. `overwriteText` (:328-350) builds a plain record without Byte edits and would need to keep annotations; `rename` (:364-376) moves the record as it is.
- **During a Debug session.** The FileSystem session keeps each File's record beside its bytes (`Node.file`, :38-44, set from the Project at :465-466), drops it when the program changes the bytes (`replaceBytes` :992-1017, `appendBytes` :961-990, which keeps a plain record only when the appended bytes are text) and puts it back when instruction Undo restores the bytes, so `flush` (:619-626) republishes the original record rather than one rebuilt from the bytes. So an Undo brings back the record, Byte edits and annotations included, as [the file views plan](./file-views-plan.md)'s decision 4 made it; the flattening its research table describes is gone. The session publishes its records over the Project's, so an annotation made during the session that is not also in the session's record would be lost at the next publish.
- **Saving.** A File change notice runs `debouncedFileSave` (`E/lib/workbench/WorkbenchSession.svelte.ts` :523, :968-975), then `changed()` (:1226), which autosaves when autosave is on. The page's unsaved flag compares `contentKey` (`E/lib/Project.svelte.ts` :329-343), which serializes the whole `files` map.
- **The archive.** Version 2 added `edits` to a manifest File entry and version 3 the Programs; an archive is written in the oldest version that holds it (`E/lib/projectArchive.ts` :29-38, :66-83), and a reader refuses a File entry with any key it does not know (:279-296). The manifest is at most 1 MiB (:41).
- **Hex Undo.** `ByteEditHistory` keeps a stack per path for the Workbench session (`WorkbenchSession` :259), shared by both panes; a stack belongs to the original its edits were made over and starts again when the content differs (`byteEditHistory.ts` :37-43), and it follows the Explorer's rename and deletion (`fileRenamed` :2076, `fileDeleted` :2100). `changeFileBytes` (:2196) refuses edits while the Workbench is read-only, the Files are locked, or a Run or Build is under way. Annotations need the same history, minus the lock.

**Generating again or patching the text.** A rename changes a Listing's text, labels, functions and holders, and a comment adds lines; generating again with the annotations as input is exact and keeps one code path. ### How Ghidra keeps a renamed local

- **What the Java side sends.** A local renamed without a new type is committed with an undefined type (`J/…/HighFunctionDBUtil.java` :629-636), and `LocalSymbolMap.grabFromFunction` (`J/…/LocalSymbolMap.java` :156-204) sends it in the function's `<localdb>` with its name locked and its type not: stack or memory storage without a use point, register storage with the function's entry plus the first-use offset, and a temporary or an untied stack location as a dynamic hash (`J/…/HighVariable.java` :178-186). Parameters of a default signature travel the same way (`LocalSymbolMap.java` :206-246).
- **What the decompiler does with it.** `Funcdata::decode` reads `<localdb>` (`G/funcdata.cc` :804-809) through `ScopeLocal::decode` (`G/varmap.cc` :472) into `collectNameRecs` (:357), which turns every symbol whose name is locked and type is not into a name recommendation by storage and use point (or hash) and removes the symbol (:1600). `ActionNameVars` applies the recommendations before any default naming (`G/coreaction.cc` :3026, `G/varmap.cc` :1507): with no use point, a tied variable at the same start; at the entry minus one, an input; otherwise one written at the use point; a hash through `DynamicHash::findVarnode`.
- **Locked symbols kept through the analysis are not the way.** `ScopeInternal::clearUnlocked` keeps only type-locked symbols (`G/database.cc` :2042), at `Funcdata::clear` (`G/funcdata.cc` :95) and again in `restructureVarnode` (`G/varmap.cc` :1259), so a symbol only name-locked (the console's `name varnode`) is silently discarded; locking the type too, as the console's `rename` does (`G/ifacedecomp.cc` :1332-1357), changed the code: `char password[136]` became `undefined1`, `'\0'` became `0`, a new `lVar1` appeared. For a parameter the console also locks the whole prototype (`setInputLock`, `G/fspec.cc` :3921-3935), which freezes the parameters' count and types.
- **The host can report an id per variable.** Today `RecordingEmit::tagVariable` records each variable token's varnode (`D/host/src/markup.cc` :70), but a stack variable read through a stack reference has none (`G/printc.cc` :1076-1111), and `_uStack_60` is the printer's spelling of a size mismatch (:2133). The prototype records the symbol behind each variable token by overriding the printer's `pushSymbol`, `pushMismatchSymbol` and `beginVarDecl`, and builds the id from its storage (decision 15). Two of its first ids were wrong and are fixed in it: join addresses are numbered in the order Ghidra meets them (`G/translate.cc` :696-700), so ids name the pieces; and in `_IO_str_count` the storage `RAX:8` at one instruction matched two variables, so every storage id is checked against Ghidra's own lookup and replaced by the hash when it does not find exactly that variable.
- **Two ways of naming, both prototyped.** Ghidra's route (each name added as an undefined-typed, name-locked symbol, then an empty `<symbollist>` decoded so `collectNameRecs` runs) needs a final step for what it misses: parameters the code never reads, which have no input varnode (the Java side names those by committing the whole prototype), and temporaries whose hash changes after `ActionNameVars`, since `ActionSetCasts` runs later (`G/coreaction.cc` :5790-5791). Naming after the analysis alone (rename each symbol whose id has a name, `makeNameUnique`, before printing) uses the same id code to report and to apply, so every reported id applies.

**What it prints.** In `crackme`'s `main`, `stack:-0x98` named `password` and `register:0x0:4@…` (the result of `strcmp`) named `result`:

```c
  result = strcmp(password,"hunter2");
  if (result == 0) {
```

for `iVar1 = strcmp(acStack_98,"hunter2"); if (iVar1 == 0) {`. ### Comments in Ghidra

- **The database.** A SLEIGH architecture keeps comments in a `CommentDatabaseInternal` (`G/sleigh_arch.cc` :244, `G/comment.hh`), keyed by function entry and address. `Funcdata::warning` and `warningHeader` add `warning` and `warningheader` comments (`G/funcdata.cc` :119-145), and `Architecture::clearAnalysis` clears only those two types (`G/architecture.cc` :335-341), so a person's comments stay across decompilations until replaced. Ghidra's own process fetches a function's comments for each decompilation (`G/comment_ghidra.cc` :30-49) and flushes them on a change (`G/ghidra_process.cc` :262-273); per-call comments do the same here.
- **Types.** The printer shows `user2|warning` in the body and `header|warningheader` above the function by default (`G/printlanguage.cc` :579-587). The Java side maps EOL to `user1`, PRE to `user2`, POST to `user3` and PLATE to `header` (`J/…/DecompileCallback.java` :577-594), and its defaults include PRE comments, warnings and the header's warnings and leave EOL, POST and PLATE comments out (`J/…/DecompileOptions.java` :320-358), so Ghidra's own window shows no plate comment until asked to. So a person's line comment is `user2`, which shows by default, and the function comment `header`, shown because the owner's decision 3 puts it above the function in both views.
- **Placement.** `CommentSorter::findPosition` (`G/comment.cc` :270-330) takes the first operation, by creation, at or after the comment's address: if its block holds the address, the comment goes before that operation's statement; otherwise before the end of the previous operation's block, or at an operation at exactly the address. A block runs from its first operation's address to its last's (`G/flow.cc` :967-1000), so an instruction with no p-code at the start of a block (the entry's `endbr64`) is in none. What finds no place is dropped unless "unplaced" display is on, which only `PrintC::setDisplayUnplaced` sets (`G/printc.cc` :1652, :3419-3434).
- **Prototyped**, on `crackme`'s `main`: comments at `call strcmp`, at the terminator's store (two lines) and before the call of `__stack_chk_fail` went where expected, a person's above Ghidra's `/* WARNING: … */` at the same address; comments at `push rbp` and `sub rsp` went before the first statement; one at `endbr64`, one in code made dead by a Byte edit and one outside the function were dropped, or listed under "Comments that could not be placed in the function body:" with unplaced display on; a 140-character comment wrapped at 100 columns; `*/` inside one was printed as it is, ending the C comment early; the function comment printed above the declaration, before Ghidra's header warning. Each word of a comment is a token carrying the comment's address (the header's carries the entry); an override of `emitLineComment` tells a person's from a warning.
- **Per call or in the image.** Per decompile call, with the function's locals: it matches Ghidra's fetch per function, a change invalidates one function's cached Pseudocode and reopens nothing, and a background decompilation for search passes each function its own. The editor passes the comments in the function's address range; extra ones are harmless.

### Interactions

- **C++ names.** The Listing's comments give the demangled signature beside each mangled token, so a search finds a C++ function by its C++ name at its definition and its calls; the Pseudocode prints short names in namespaces. A renamed one is found by the person's name, its old names only in the hover (decision 9).
- **Invented names** are derived from the address in the file and never from another name (ADR 0045), so applying renames after every name is claimed changes none of them; a person's name can never be an Invented name another address has (decision 7).
- **The Navigation history** records Listing places by line, which comment lines shift; the plan keys them by address, which also fixes the older case of a Byte edit that changes how code decodes.
- **Exams and other hosts**: Executables are not in Exams, whose Workbench hides the Explorer; the Search panel goes off with it. A read-only Workbench (`host.readonly`) refuses annotations, as it refuses Byte edits.
- **Phones.** The Search panel opens in the drawer like any panel. Monaco opens its context menu on a long press on Android but iOS's Safari sends no `contextmenu` for a touch, so on an iPhone Rename… and Comment… in a Listing or Pseudocode have no way in but the keys of an attached keyboard; the Symbols panel's row button covers function renames (open question 5).
- **Accessibility.** The prompts are labelled fields with the refusal as their description; the panel's toggles are pressed buttons with names ("Match case", "Match whole word", "Use regular expression"); the results are a tree that the arrows, Home, End and Enter move through, as the Symbols panel's rows are; the Pseudocode's progress is announced politely.

## Risks

- **The static program's Listing takes about half a second to make again** for each rename or comment, during which the pane shows the old text. CTF programs take under 100 ms. The name spans of demangling's phase 2 would let a rename patch the text instead.
- **Comments land a statement off** about 10% of the time in the Pseudocode, where statements share an instruction, and comments on instructions without p-code are only in the unplaced list.
- **Hash ids are fragile**: a Byte edit near a temporary can change its hash, and its name is then silently not applied, though kept.
- **Searching the Pseudocode of a static program takes minutes** of one core, and a pane's request can wait up to the background limit of 5 s behind a call under way.
- **The cache's rewritten lines may break differently** from a fresh decompilation; a click finds the match again rather than trusting the line number.
- **Keys**: `;` sits where the US key is on other layouts; Ctrl+Shift+F may be taken by an input method on Windows or by a Mac's Chrome; Monaco's own Undo or F2 could win in a read-only editor if an action's key weight is lower than assumed (the browser check covers these).
- **Annotations made during a Debug session** are lost with the record if the program then rewrites its own Executable, and instruction Undo of that write brings back the record from before them.
- **The archive's version 4** cannot be opened by an editor older than this change; only Projects with annotations are written in it.
- **The package** grows by about 35 KB of wasm (14 KB gzipped) with the prototype's code; the final code should be smaller without its debugging hooks.

The memory view gives a Core symbol whose name and address a renamed label has the person's name as `displayName`: data only, and only symbols the Core lists, so a stripped program's renamed `DAT_` has no label there (open question 8). The Patch prompt and patched lines read the generated labels, and a patched line keeps its end-of-line comment (`describeLine`).

The editor passes only the comments within the function's own range (`functionAnnotations`, from `forFunction`), since `unplacedComments` would list every other one, and sets `unplacedComments` whenever it passes any. Changed: a line holding only comments, a person's or Ghidra's `WARNING` lines alike, maps to no Listing line, so the program counter, Breakpoints, the pairing and the colouring land on the statement; before, a `WARNING` line took its address's.

### Follow-ups

- **Phones without a keyboard** (open question 5). Rename… and Comment… in a Listing or Pseudocode come through keys or Monaco's context menu, which Safari on an iPhone does not open on a long press, so there only the Symbols panel's ⋯ button, for functions, reaches them. A Rename/Comment button in the notices or a long press of the Workbench's own is not built.
- **Renamed `goto` targets** (open question 6). A jump target's rename shows in the Listing only; the Pseudocode's `goto`s would need code labels in the program image, a version 4.
- **A Workbench-wide Search Chapter** (open question 7). The Search panel is documented in the x86 Executables Chapter alone, though every Target offers it for its Files.
- **Memory-view labels for renamed data in stripped programs** (open question 8). The memory view labels only the Core's symbols, so a stripped program's renamed `DAT_` has no label there; the address box takes it.
- **A renamed local's default name is known only in memory**: `PseudocodeDocument.defaultNames`, 256 functions a session, never saved. After a reload, the hover and the prompt cannot say what a local was renamed from, and typing the decompiler's name does not reset it, until a decompilation has printed that name again (Reset name, Undo).
- **Intermediate Pseudocode text during a comment.** A pane may first show its function decompiled with the new comment against the old Listing, then against the new one: two decompilations for one comment, the text never blank.
- **Ctrl+Shift+F in Firefox and Safari** was not checked, nor Windows input methods that take it (Microsoft Pinyin); Chromium lets the page have it, and Settings can rebind it.
- **Replace** across text Files (decision 29), and searching a Bundled library's Listing.
- **Undo and Redo do not show the place** they change (decision 19).
- **Not browser-checked**: a renamed C++ function of `factcheck`, a stripped program's rename, a reload and an archive round trip, and the static program's Pseudocode search with Cancel, which the DOM tests cover on `factcheck` (progress, Cancel, Resume, unticking).

## Glossary terms

Proposed for [CONTEXT.md](../../CONTEXT.md) and added there on 2026-10-23, adapted to what was built: **Annotation** names its keys and [ADR 0055](../adr/0055-annotations-are-kept-on-the-file-apart-from-its-bytes.md), **Rename** the names that cannot change, and the **Search panel** is offered in every Target, searching only Files where there is no Executable. Kept here as proposed:

### Annotation

A **Rename** or a **Comment** a person adds to an **Executable** of the **Project**, saved with that **File** apart from its bytes, as its **Byte edits** are, and shown in its **Listing** and **Pseudocode**. Replacing the File's whole content (an upload over it, a program's write) drops them; a Byte edit keeps them. A **Bundled library**'s Listing and the **Build output** take none. One Rename or Comment is one step of Undo, apart from instruction Undo.
_Avoid_: note, markup, bookmark, label (a name of the Listing)

### Rename

A name a person gives in place of the one the **Listing** or the decompiler gave: a function's, a datum's, a string's or a jump target's of an **Executable**, by its address in the file, shown wherever that name is; or a variable's of one function of its **Pseudocode**, by the decompiler's identity for it. It overrides an **Invented name** and a **Demangled name**, which the hover still gives, and Reset name takes it away. A PLT stub and a GOT slot keep the library's names.
_Avoid_: alias, symbol, display name (the code's field), relabel

### Comment

Text a person attaches to an address of an **Executable** (a line comment, at an instruction or data line) or to one of its functions (a function comment). The **Listing** writes it at the end of its line, or above it when long, and above the function's label; the **Pseudocode** has Ghidra place it before the statement whose code holds the address, and a function's above its declaration. A comment set on a Pseudocode line is kept at that line's first mapped instruction. Its words are text, never a name to follow. Distinct from the comments the Listing and the decompiler write themselves: a string's text, a **Demangled name**, Ghidra's warnings.
_Avoid_: note, remark, annotation (for a Comment alone), EOL/PRE/plate comment (Ghidra's kinds)

### Search panel

The **Workbench** side panel that finds text across the **Project**, in what the person ticks under "Look in": its text **Files**, each **Executable**'s **Listing**, and the **Pseudocode** of every function of each Executable, which it decompiles in the background while it is open. A result opens the File, Listing or function at its line, and the jump goes into the pane's **Navigation history**. Distinct from Ctrl+F (one editor), the **Symbols panel** (one Executable's names) and the Documentation's search, whose **Search scope** the place it is made from sets.
_Avoid_: find in files, global search, grep, search scope (for its ticks)

Entries amended there: **Listing** (a person's Renames in its text and Comments as its lines), **Pseudocode** (a person's names and Comments), **Executable** (its Annotations), **Byte edit** (keeps Annotations), **Symbols panel** (a renamed function by its new name, the filter matching the old), **Navigation history** (a Listing place by its address) and **Search scope** (not the Search panel's ticks).

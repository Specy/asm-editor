## Decisions taken while planning

Taken by default, for the owner to overturn.

1. **Pixels is a flag on the BMP Preview kind.** `fileKind` parses a BMP's header from the head it already reads and, when the layout is one design decision 3 edits and the pixels fit inside the File, returns `{ preview: 'image', mime: 'image/bmp', pixels: true }`; `fileViewsOf` gives such a kind `['preview', 'pixels', 'hex']`. A Byte edit that breaks the header takes Pixels away, and the pane falls back to the Preview as any view a kind stops offering does.
2. **Pixels is offered up to 4,194,304 pixels** (2048 × 2048). A 16 MiB 1-bit BMP holds 128 million pixels, half a gigabyte as RGBA, so the cap is on pixels rather than bytes; a larger picture keeps Preview and Hex, with no note. New pictures and Canvas size stay within 1 to 1024 (design decisions 5 and 9).
3. **A BMP is stored as bytes even when it decodes as UTF-8.** `bytesFile` stores bytes that `isBmp` recognises as base64, so an upload or a program's write of a dark, small picture opens as a picture. `projectFileFromBytes` keeps honouring an archive's `plain`, so an old archive holding such a picture as text still opens (as text); New picture and Canvas size write with `encoding: 'base64'` explicitly. A picture already saved as text stays text until it is uploaded again.
4. **A stroke is committed once, at pointer-up.** The editor draws a stroke into its own copy of the pixels and, when the pointer comes up, hands the session every byte run it changed in one call: one `FileSystem` commit, one autosave, one Undo step. A stroke cancelled by a second finger or Escape commits nothing. `FileSystem.editBytes` takes a list of runs for this, a single run being the Hex editor's case.
5. **Overwrites up to 32 bytes apart are joined.** `mergeOverwrites` takes the File and fills a gap of 32 bytes or fewer between two runs with the original's bytes, decoded from that slice of the base64 only, so the File is never decoded whole on an edit (the review fix that brought `editBytes` to 0.1 ms stays). A vertical stroke in a 32-bit picture still makes one run a row; a dither or a 24-bit stroke's neighbours become one. Each run costs about 45 bytes of record, so a gap of 32 bytes, about 43 of base64, is where joining stops paying. _Superseded 2026-10-25 by design decision 12 ([ADR 0063](../adr/0063-a-file-holds-its-current-bytes-and-undo-is-a-journal-beside-it.md)): a File holds its current bytes, so no edits are merged or joined._
6. **In a 32-bit picture without an alpha mask, a drawn pixel's fourth byte is left as it is.** Chrome reads that byte as alpha when the picture's fourth bytes are not all zero, so writing 0 into a picture whose pixels carry 0xFF would make the drawn ones transparent in the Preview. New pictures are all zeros there. The joined runs of decision 5 make the skipped byte cost nothing.
7. **A colour is quantised to the File's layout when drawn.** In a 16-bit or masked picture the chosen colour becomes the nearest value its masks hold, and the colour row shows colours as the File stores them, so what is drawn is what a program reads.
8. **Zoom: Fit is the largest whole multiple that fits, or the largest 1/n for a picture larger than the pane.** Steps are 1/8, 1/4, 1/2, then 1 to 64; Ctrl or Cmd with the wheel, and a pinch, zoom at the pointer; the wheel and two fingers pan. The status line says the zoom as a percentage, as the Preview does. _Revised 2026-10-25 at the owner's request:_ the zoom is smooth, any scale from 1/8 to 64; the wheel and a pinch change it continuously and settle nowhere, Zoom in, Zoom out, + and − multiply it by √2 and Fit and 1 slide there over 160 ms (at once where motion is reduced), and Fit fills the pane exactly. At a scale between whole numbers pixels are a device pixel wider or narrower, and what is drawn over them keeps to their edges.
9. **Keyboard:** B Pencil, L Line, U Rectangle, G Fill, I Eyedropper, E Erase, each without Shift, which leaves the key to the Workbench's shortcuts (Shift+B builds); holding Alt picks colours with any tool; Shift fills a rectangle (or unfills it when the Rectangle's Fill setting is Filled) and snaps a line to 0°, 45° or 90°; Ctrl or Cmd with Z undoes, with Shift and Z or with Y redoes; `+` and `-` zoom, `0` fits, `1` is 100%. Keys act only while the Pixel editor has the focus.
10. **The cell grid is saved as `cellGrids`** beside `fileViews` in `ProjectData`: `{ width, height }` per path, each 1 to 1024, cleaned by `cleanEditorTabs`, moved by `fileRenamed`, dropped by `fileDeleted`. It is off until turned on; turned on, it starts at 16 × 16. The pixel grid needs no saving: it shows at 8× and above.
11. **Canvas size is an Undo step of its own kind.** `ByteEditHistory` steps become `{ kind: 'edits', edits, offset }` or `{ kind: 'replace', file }`, the second holding the whole previous File record; a replace moves the stack onto the new `content` instead of starting a fresh one, and Undo puts the record back through a new `FileSystem.restoreFile(path, file)`, Redo the resized one. Both editors share the history, so the Hex editor's Undo walks back through a resize too. _Superseded 2026-10-25 by design decision 12: Canvas size is an Edit step of the journal that keeps the whole content it replaced; `ByteEditHistory` is gone._
12. **Archive version 5.** Written whenever a File has overwrite Byte edits; versions 1 to 4 keep their meaning and are still read. For such a File: `files/<path>` holds the edited bytes, `original-files/<path>` the original, and the manifest's `edits` items are `{ offset, remove }` without `insert`. A File whose edits insert or delete keeps today's form. The reader requires `original-files/<path>` for exactly the Files whose items lack `insert`, of the same length as `files/<path>`, equal to it outside the ranges, and rebuilds `insert` from `files/<path>`; anything else is "Archived File and its original do not match". The expanded total may reach twice 16 MiB and `ARCHIVE_BYTE_LIMIT` doubles, since an edited File is there twice; `cleanFiles` then applies the Project's own 16 MiB rule (original plus edited bytes). _Superseded 2026-10-25 by design decision 12: archives hold each File as it is, in versions 1, 3 and 4; version 5 was never released._
13. **The New picture form is its own dialog**, `NewPictureDialog.svelte`, styled as `PromptProvider`'s, since the Prompt store asks only text, confirm and alert. Name `sprite.bmp`, else `sprite1.bmp`, `sprite2.bmp`… when taken; size 16 × 16; layout per design decision 5. It writes the File, calls `onFilesAdded`, selects it and opens it in Pixels through a new Explorer prop, `onPictureCreated`, which the Workbench answers with `group.setView(path, 'pixels')`, saving the view.
14. **The colour row** of a picture without a palette shows the current colour, then up to 32 colours the picture uses most, counted when it opens and after each stroke. A palette picture shows its palette instead; double-clicking an entry, or a long press on touch, opens the browser's colour picker to recolour it (design decision 6).
15. **One canvas the size of the pane draws the visible part** of an offscreen canvas holding the picture at 1:1, without smoothing, then the pixel grid, the cell grid, the pointer's pixel and a Line or Rectangle being drawn. A canvas the size of a 1024-pixel picture at 64× would be 65,536 pixels wide.
16. **Documentation:** a "Pictures in Files" section in `mars/screen.md` for MIPS and RISC-V, a paragraph beside the M68K's graphics tasks in `traps.md`, one in the Z80's `screen` port group documentation, and a line in the Pac-Man example's README. x86 gets none, having no Screen.

## Milestones

P1 gates the rest. P2 and P3 are independent of each other; P4 needs P1 and P2; P5 needs P4; P6 and P7 come last.

### P1: The BMP codec, kinds and views

- `lib/pixels/bmp.ts`, pure: `readBmpLayout(head, length)` → `{ width, height, topDown, bitsPerPixel, masks?, alphaMask?, palette?: { offset, entrySize: 3 | 4, count }, pixelOffset, rowStride }` or the reason it is not editable (compressed, 2 bits a pixel, too large, pixels past the end); `decodePixels(bytes, layout)` → RGBA, partial alpha kept (design decision 7); `pixelRuns(layout, changes)` → byte runs to overwrite for a set of pixel values (index or colour); `paletteRun(layout, index, colour)`; `encodeColour(layout, rgba)` with quantisation (decision 7); `makeBmp({ width, height, layout, palette })`; `resizeBmp(bytes, layout, width, height)` anchored top-left, filled black or transparent (design decision 9).
- `lib/pixels/palettes.ts`: 3-3-2 stretched as `Z80Device.ts:629` stretches it, the 16 Windows and VGA colours, black and white (design decision 6); `newPictureLayout(language)` (design decision 5).
- `lib/fileKinds.ts`: the `pixels` flag (decision 1, 2); `lib/fileViews.ts`: `'pixels'` in `FileView`, `FILE_VIEWS` and `fileViewsOf`.
- `lib/projectFiles.ts`: the `bytesFile` BMP rule (decision 3).
- Tests: `bmp.test.ts` against fixtures written by a committed `scripts/pixel-fixtures/make.py` (Pillow: 1, 4, 8, 24, 32-bit bottom-up, odd widths for row padding) checked in under `lib/pixels/fixtures/`, and hand-built ones for top-down, 16-bit 5-5-5 and 5-6-5, `BITMAPCOREHEADER`, `BI_BITFIELDS` and `BITMAPV4HEADER` with alpha; round trips (decode, change, runs, decode); `makeBmp` for each layout reads back with `readBmpLayout` and, for 24 and 32-bit, with the Pac-Man example's rules; resize keeps the pixels inside the overlap; `fileKinds.test.ts` for the flag, the cap and an RLE8 File without it; `bytesFile` stores an ASCII-only BMP as base64 and `projectFileFromBytes(…, 'plain')` still reads one.

### P2: Edits, Undo and saved state

- `FileSystem.editBytes(path, runs)` takes a list of runs (decision 4), still refusing insert/delete Files; `mergeOverwrites(edits, file)` joins gaps of 32 bytes or fewer with original bytes from a base64 slice (decision 5); `FileSystem.restoreFile(path, file)` (decision 11), refused while locked like every host write.
- `ByteEditHistory`: the step union and the replace step (decision 11); `recordReplace(path, before, after)`. The Hex editor's `undoEdits` gains the replace case through a new `onRestoreFile` prop, so its Undo walks back through a resize as the Pixel editor's does.
- `WorkbenchSession`: `editFileByteRuns(path, runs)` and `resizePicture(path, width, height)` through `changeFileBytes`, the second recording the replace step; Undo and Redo of a replace through `restoreFile`; `cellGrids` moved and dropped with `fileViews` in `fileRenamed` and `fileDeleted`.
- `Project.svelte.ts`: `cellGrids` in `ProjectData`, `StoredProject`, `cleanEditorTabs`, a `setCellGrid(path, grid)` (decision 10).
- Tests: multi-run edits commit once and merge; gap joining with and without a gap past 32; an edit never decodes the whole original (spy on the slice decoder, a 16 MiB File timed as the review measured it); history across a replace in both directions, the Hex editor's Undo walking back through a resize; `cellGrids` cleaning, rename and delete.

### P3: Archive version 5

- `projectArchive.ts`: the writer and reader of decision 12, the version rule, the doubled limits, the consistency check; the module's version comment.
- Tests: a version 5 round trip with an edited picture, its `files/` entry equal to the edited bytes and its `original-files/` to the original; a Project without edits still writes 1, 3 or 4 as before; version 2 and 4 archives with base64 inserts still read; a 16 MiB File with one byte edited round trips; a mismatch outside the ranges, a missing or extra `original-files/` entry and a length difference are refused; an `original-files/` entry in a version 4 archive is still "Unsupported archive entry".

### P4: The Pixel editor

- `lib/pixels/tools.ts`, pure: Pencil (a stroke's pixels with the gaps between pointer events filled by Bresenham), Line (with the 45° snap), Rectangle (outline and filled), Fill (four neighbours, design decision 8), Eyedropper, Erase (alpha pictures only); `lib/pixels/zoom.ts`: Fit and the steps (decision 8).
- `lib/pixels/PixelDocument.svelte.ts`: the decoded picture, the stroke in progress, the runs it changed, the colour row (decision 14); testable without a canvas.
- `components/specific/workbench/pixels/PixelEditor.svelte` (+ `PixelToolbar.svelte`): the viewport canvas (decision 15), pointer events with one finger drawing and two panning and pinching (design decision 10), the toolbar wrapping at phone width with the Filled toggle, the colour row and palette with recolouring, the cell grid control, a status line in the Preview's manner (name, width × height, layout, zoom, the pixel under the pointer with its colour or index, "edited"), the read-only notice from `bytesReadOnly`, keys (decision 9).
- `EditorPane.svelte`: a `pixels` branch keyed by path, as the Hex editor's; `EditorGroup.pixelViews` for zoom and scroll while the tab is open; `ExecutionControls.svelte`: `pixels: { label: 'Pixels', title: "Show the File's pixels in the Pixel editor" }` with a brush icon.
- Tests: unit tests for each tool (Fill not leaking through a diagonal gap, Line's ends, Rectangle's fill), zoom steps and Fit, `PixelDocument` runs for every layout; dom tests with a canvas stub: the switch offers Preview · Pixels · Hex for an editable BMP and Preview · Hex for an RLE8 one, the read-only notice during a Debug session, a stroke reaching `editFileByteRuns` once, the tool keys.

### P5: New picture and Canvas size

- `components/specific/project/NewPictureDialog.svelte` (decision 13); the Explorer's header button ("New picture") and `folderItems` entry ("New picture in this folder"), disabled when `locked`; `onPictureCreated` wired in `SidePanel.svelte`.

- Tests: dom tests that New picture writes a base64 BMP of the Target's layout (32-bit top-down in MIPS, RISC-V, M68K and x86; 8-bit 3-3-2 in the Z80), with `sprite1.bmp` when `sprite.bmp` is taken, and opens it in Pixels with the view saved; Canvas size grows and crops, and Undo restores the File record exactly.

### P6: Documentation

- The sections of decision 16; the design record's "Open for planning" pointed at this plan; CONTEXT.md if implementation sharpens a term.

### P7: Verification and review

In headless Chrome, with the scenarios added to [manual-verification.md](../manual-verification.md):

1. The Pac-Man Project: open `assets/sprites.bmp`, switch to Pixels, recolour a ghost with Pencil and Fill, switch to Preview (the browser's own decoder shows the same pixels), Build and Run (the game draws the recoloured ghost).
2. Every fixture layout: draw one pixel, then compare the editor's decode with the browser's `<img>` decode of the edited File, pixel for pixel.
3. A 32-bit picture whose fourth bytes are 0xFF: a drawn pixel stays opaque in the Preview (decision 6).
4. New picture in each Target's Project; Canvas size and its Undo; Undo across Pixels and Hex in two panes.
5. Export the Project, unzip it with `unzip` and check `files/` holds the drawn picture and `original-files/` the original; import it again.
6. Phone width (390 px, touch emulated over CDP): one-finger stroke, pinch with no stray mark, the toolbar wrapping, no sideways page scroll.
7. A Debug session: the editor read-only with the Hex editor's words; a program writing the picture shows it.

Then a code review of the branch at high effort, its findings fixed before handing back.

## Implementation record

Implemented on 2026-10-25 on branch `feat/pixel-editor`, from `origin/main` at `775f2760`, uncommitted. Paths under `packages/asm-editor/`.

- **P1.** `src/lib/pixels/bmp.ts` reads and writes every layout of decision 3 and owns `isBmp`, which `fileKinds.ts` and `projectFiles.ts` now import; `palettes.ts` holds the starting palettes and `newPictureFormat`. `scripts/pixel-fixtures/make.py` writes the fixtures and Pillow's decoding of them into `src/lib/pixels/fixtures/`; Pillow and the editor widen 5- and 6-bit channels differently by at most 1, which the test allows for 16-bit pictures only. OS/2's 64-byte header is taken uncompressed only, since its compression 3 is not bit fields. A `BITMAPCOREHEADER` palette has as many entries as fit before the pixels, as Windows reads one.
- **P2.** `FileSystem.editByteRuns` and `restoreFile`; `mergeOverwrites(edits, original)` joins runs at most `JOIN_GAP` (32) bytes apart from a slice of the base64. `ByteEditStep` is `{ edits, offset }` or `{ replaced, offset }`, so the existing tests' steps are unchanged. The session's `resizePicture(path, bytes)` takes the resized bytes, which the editor makes with `resizeBmp`, rather than a width and a height.
- **P3.** As decision 12; `Unsupported archive entry` for `original-files/` before version 5, `Malformed manifest File entry` for ranges before it, `Archived File and its original do not match` for the rest.
- **P4.** `components/specific/workbench/pixels/PixelEditor.svelte` with `src/lib/pixels/tools.ts`, `zoom.ts` and `pixelDocument.ts`. Beyond the plan: Undo and Redo buttons in the toolbar, since a phone has no keys; a 2-pixel outline on the pixel under the pointer; the region takes the keys wherever the focus is inside it, and it takes the focus on a click, as the Hex editor's grid does, not when the view is switched to. Fill and a filled rectangle hand their pixels to a callback rather than build arrays, since a 2048 × 2048 one is four million of them. The picture's colours for lines and the checkerboard are read from hidden elements styled with the theme's variables.
- **P5.** `components/specific/project/NewPictureDialog.svelte`; every layout is written top-down, and a picture with transparency starts transparent rather than black. The session's `openInPixelEditor` opens it and saves the view.
- **P6.** `mars/screen.md` and `m68k/traps.md` gained a "Pictures in Files" section (the M68K's beside its graphics tasks), and the Pac-Man README a section on its pictures, after which `pacman.asmproj` was packed again (still version 3). The Z80's section, at first left out on the mistaken belief that it could read no File, was added on 2026-10-25 beside its colours in `z80/io.md`: the Z80 assembler's `#insert "file"` (z80-asm, which also serves the TRS-80 IDE) copies a File's bytes into the program at Build, Byte edits applied (`assemblyFiles`), so a Z80 program reads an 8-bit 3-3-2 picture's pixels 1078 bytes after its label. `Z80Emulator.test.ts` checks it.
- **P7.** The rows P1 to P7 of [manual-verification.md](../manual-verification.md), "Pixel editor (2026-10-25)".
- **Review** (high effort, 2026-10-25): 10 findings, 9 fixed. A long press on a palette entry now opens the picker as the finger lifts, which a browser counts as the person's act; Ctrl or Cmd with the wheel turns a step only every 60 pixels of turning, so a trackpad pinch zooms gently; the wheel reads `deltaMode`; the document skips re-reading a File by comparing it with the one its own save made rather than with a flag; an Undo or Redo the File refuses is put back (`ByteEditHistory.putBack`, the Hex editor's too); a stroke snapshots only the rows it touches and saves only the bytes it changed, so one in a pixel's own colour saves nothing; the theme's colours are read at most twice a second; panning keeps the pane's middle on the picture. Skipped: the New picture dialog repeats the prompt tray's styles rather than sharing them.
- **Independent review** (an agent, 2026-10-25, at the owner's request): 13 findings, all fixed.
    - **Memory and speed of large edits.** `mergeOverwrites` now merges in one pass per `EDIT_CHUNK` (64 KiB) piece. No run crosses a multiple of it, so two runs may touch there, and an edit alone in its piece comes back as the same object, so a stroke re-encodes only the pieces it touches and the Undo history shares the rest. A fill of a 1024 × 1024 32-bit picture saves in linear time. `withByteEdits` reads the length of edits the File already had rather than decoding them, and `fileHead` decodes only the part of an edit that lies in the head.
    - **The Undo history** is also capped at 64 MiB of base64 a File (`KEPT_CHARACTERS`), an edit shared with the step before counting once.
    - **Archives.** `editsFromRanges` refuses unsorted or overlapping ranges before encoding any, so a few bytes of manifest cannot ask for gigabytes; a null edit item is a `ProjectFormatError` in every version.
    - **The editor.** A touch Fill runs as the finger lifts and a colour picked by touch is put back when a pinch follows. A change to another File no longer makes the picture be read again, since its bytes are compared rather than its record, which `cleanFiles` rebuilds. Canvas size takes a larger picture up to its own size and says why it will not resize. The cell grid shows in a read-only Project. A dragged rectangle plots only what lies inside the picture.
    - **The codec.** Pixels is offered only up to 16,384 pixels a side (`SIDE_LIMIT`). Growing a picture copies the bits no channel uses from its top-left pixel. A V5 header's linked profile moves like an embedded one, and one that cannot be kept is no longer named.
    - **The docs.** The pixels-start-at-54 wording now names the default 32-bit layout, and design decision 9 names palette entry 0.
- **Edit steps and the Edit history** (2026-10-25, design decision 11, at the owner's request after asking how drawing programs keep their history and how large it would grow). `src/lib/editSteps.ts` adds, undoes, redoes, goes to and folds steps as pure functions over a File: a step's edits stay unmerged at the end of `edits`, and `ProjectFile.history` holds `steps` (`{ label, time, count }`) and `undone` (with their edits). Readers needed no change. `FileSystem.editByteRuns` and `editBytes` take a label (`Typing` from the Hex editor); `replaceContent` is Canvas size's step; `undoEdit` and `goToEdit` move through them. A commit that would take the Project past 16 MiB folds steps, the newest too, before refusing. `overwritesOnly` and `fileHead` accept a whole-content replacement. The session-only Undo of byte Files is gone: `ByteEditHistory` keeps only text Files' typing, and `restoreFile`, the replace step, `putBack` and the 64 MiB session budget went with it. Archives keep the steps in a binary `edits/` entry and the manifest; share links drop them (`withoutSteps`). The panel is `EditHistoryPanel.svelte`, a rail entry offered in a Project that has a File stored as bytes. Measured before deciding: a Pencil stroke costs tens to a few hundred bytes, a Fill the area it covers.
- **The Edit journal** (2026-10-25, design decision 12, [ADR 0063](../adr/0063-a-file-holds-its-current-bytes-and-undo-is-a-journal-beside-it.md), after an independent design review and a code review of the Edit steps above, following [the journal plan](./pixel-editor-journal-plan.md)). A File is its current bytes: `ProjectFile` lost `edits` and `history`, and `editSteps.ts`, `ByteEditHistory`, `mergeOverwrites`, `withByteEdits`, `byteEditsKey` and archive version 5 are gone. `cleanFiles` applies the Byte edits a Project saved before (versions 2 to 4 of an archive, IndexedDB, share links) once, within 16 MiB put in and a bound on the copying insertions and deletions cost (`EDIT_COPY_LIMIT`). `overwriteBytes` writes runs over a File, decoding and encoding only the base64 groups they touch, and returns the runs that put it back; `FileSystem.changeBytes` makes a list of runs or whole contents in one save and returns each one's inverse. `src/lib/editJournal.ts` keeps each File's steps as those inverses (one side only), 1 MiB a File, 4 MiB a Project and 1,000 steps a File, and forgets a File's steps when its content is no longer the one they left (compared by string in the session, by `fileFingerprint` after a reload). The session owns the journal, flushes Hex typing before Undo, Redo and the panel's jumps, carries the annotation history over overwrites (`AnnotationHistory.overwritten`), and tells the host's `editJournals` store which journals changed; the project page reads them as `ProjectStore.save` takes the Project's snapshot and writes them in the same IndexedDB transaction (Dexie version 3, table `editJournals`, deleted with the Project), so a journal is never stored ahead of the File it fits nor behind it. A Project from a link keeps its journal in memory only. The Hex editor's text Files use the journal too. A picture an older editor stored as text was to be stored as bytes from its first stroke, but such a File is never offered Pixels (planning decision 3), so the branch was removed after the final review. From the code review, also: Canvas size refuses the picture's own size, and a kept Erase tool falls back to the Pencil on a picture without alpha. The "edited" badges of the Hex editor, the Preview and the Pixel editor went with the edits they named. Tests: `fileOverwrites.test.ts` (in place of `byteEdits.test.ts`), `editJournal.test.ts`, `EditHistoryPanel.svelte.dom.test.ts`, and the session's reload through a store in `fileViews.dom.test.ts`.
- **Review of the journal** (an agent, 2026-10-25): 8 findings; a fuzz of 3,000 overwrites and 300 journal histories found every inverse exact. Fixed: Undo, Redo and the panel's jumps no longer trim the journal (counting the step a large Undo moved to Redo had taken the steps before it), only a new step does; the journal was saved on its own debounce and on `pagehide`, ahead of or behind the Project's save, so a tab closed between them lost the whole journal, and it is now written in the Project save's transaction, as above; the bounds on legacy edits count over the Project rather than a File, which a link spreading thousands of deletions over many Files slipped past; `changeBytes`'s comment named the wrong order for its inverses; an Undo that changed nothing kept a preview tab open; the content-keyed caches kept up to 128 whole Files (the Listing's and the Pseudocode's content numbers now keep 8, the Hex editor's decoded bytes 2), since every overwrite makes a new content string; and file-views.md and annotations-and-search.md now point to ADR 0063 where they describe Byte edits.

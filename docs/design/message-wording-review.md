# Message wording review

Status: inventory for the owner to reword, 2026-10-23. Not a decision record.

Every error, warning, refusal and status message a person can see that was added or changed by three bodies of work on `feat/pseudocode` after `24ff537a`: the [reverse-engineering UX batch](reverse-engineering-ux.md), [C++ demangling phase 1](cpp-demangling.md), and [renames, comments and the Search panel](annotations-and-search.md). AVX support, the MIPS/RISC-V speedups and the editor file drop are left out.

## How to use this file

- Write your wording in the **New wording** column. Leave it empty to keep the current text.
- **Suggested** is a first try at plainer wording. Take it, change it or ignore it.
- `{name}` and the like are placeholders. Keep them, or move them to wherever they read best.
- **Where** says how the person sees the message: toast, prompt error (the red line under the Rename or Comment field), prompt note (the line under the prompt's title), Log note, run status (the line that says how the run ended), dock label (the Build button's text), panel state (a note in the Symbols or Search panel), hover, tooltip, Problems (a warning in the Problems panel and the editor), dialog, or console only.
- A row tagged **(unchanged)** keeps text from before this work. It is listed because the work changed when or where it shows.
- Rows tagged **★** are the ones you complained about.
- Paths are repo-relative. `E/` is `packages/asm-editor/src/`, `X/` is `packages/x86/blink-js/src/` (the x86 Core submodule), and `D/` is `packages/decompiler/` (the decompiler submodule).
- Before you change wording, note that the x86 manual (`E/lib/documentation/x86/executables.md`) quotes many of these messages, at lines 33, 192, 196, 200, 201, 204, 267, 277, 289, 298, 304, 320 and 417–418. The tests also assert the exact text: `E/lib/annotations/names.test.ts`, `E/lib/workbench/annotations.dom.test.ts`, `E/lib/workbench/pseudocode.dom.test.ts`, `SymbolsPanel.svelte.dom.test.ts`, `SearchPanel.svelte.dom.test.ts`, `E/lib/projectSearch/*.test.ts`, `buildProgress.dom.test.ts`, `X86Notes.test.ts`, `termination.test.ts`, `x86Adapter.test.ts`, `GenericEmulator.test.ts` and `workbenchLog.test.ts`. Change the wording and its quotes together.
- The Patch prompt has no message that this work added or changed. It only began to share the register and NASM word lists with the name checks.

### ★ R20, the library-name refusal

Today it reads "strcmp is named by the library it comes from". It sounds as though the library chose a name for the person, and it does not say that the rename was refused. Some alternatives:

1. **strcmp comes from a shared library, so it can't be renamed.** It is short, says what happened and why, and needs no PLT or GOT.
2. **strcmp is a library function. Its name comes from the library and can't be changed.** It is a little longer, and it teaches the idea of a library function.
3. **Library functions such as strcmp keep their names. Rename your own functions instead.** It points the person at what they can rename.

R21 has the same problem ("is named by the C declaration of puts, so it keeps that name"), so reword both in the same pattern. For example, after option 1: "s belongs to the library function puts, so it can't be renamed."

## Patterns

What does not match across the messages above:

- **Ending punctuation.** Prompt errors and toasts have no period (R1–R21, C1–C3, U1–U6). Prompt notes, panel notes and hovers have one (R23–R25, L1, L4, S4, S13). The Search summary mixes both: `No results found.` has a period, but `12 matches in 3 Files` has none. So do the two Log notes: A1 ends with a period and A3 does not. B7 joins the browser's message and `. Check the connection`, and Firefox's message (`NetworkError when attempting to fetch resource.`) already ends with a period, so Firefox users get `resource.. Check the connection`.
- **Voice.** There are three:
    - Rules stated in the third person: `A name holds letters, digits and underscores only, not …`, `A comment has at most 40 lines…`.
    - Commands: `Write a name`, `Tick a place under Look in…`, `Check the connection and Build again`.
    - Notes about the person: `which you renamed`, `once you search`, `Your name … is not applied`.

    Many messages say what is true but not what to do (R5–R11, R13, R16, R19, U6).

- **Words that describe the machinery.** `named by the library it comes from`, `named by the C declaration of`, `a type the decompiler writes`, `reads as a name the decompiler gives`, `a word NASM reads in operands`, `The Pseudocode writes it`, `whose Pseudocode would then write this label as ::name`, `its worker sent an unreadable message`, `link-time address`, `annotation limit`. Each explains why the code refused, not what the person should do.
- **"named" and "called".** These all say "has the name" in different ways: `is the name of another label`, `another label has it`, `another label has that name`, `is named by`, `keeps its own`, `keeps that name`.
- **Names are not set apart.** The person's name sits bare in the sentence (`and is a keyword of C++`, `size is a type…`), which is confusing when the name is a common word. Nothing is quoted in prompt errors and toasts. Hovers and Log notes put names in code font, and the Symbols panel uses curly quotes (`Nothing matches “x”.`).
- **Terms.** One thing gets several names:
    - The Executable is called `program` (`The program is running`, `Load the program…`, `The program ran…`), `Executable` (L1) and `File` (`{path} is not a File of the Project`).
    - `File` and `Files` are capitalised in running text (`3 Files`, `the Project's text Files`), but `Entry file` is not.
    - `Pause` is capitalised in the middle of a sentence after a colon (U4).
- **Addresses.** Refusals show full run-time addresses (`at 0x5555555551e9`) even when a name would identify the label, and a beginner cannot act on them.
- **Units and numbers.** The units differ: `no data for 20 s`, `for 30 seconds`, a 2-second search limit the panel never states. The number style differs too: `4,000` has a separator, `128` and `40` are plain.
- **Same idea, different words.** `Reset name gives back the name the decompiler gave it.`, `Reset name gives that name back.` and `Renamed from main; that name resets it.` all say one thing.
- **Older messages beside these.** `Error compiling code. {message}` (WorkbenchSession.svelte.ts:3931) still shows for any non-download Build failure, in an older voice than B7.

### Proposed house style

1. **Say what happened, then what to do,** in one or two short sentences: "Another label is already called “main”. Choose another name."
2. **Speak to the person.** Use "you" and plain commands ("Pause the program", "Reload the page"). Don't explain the internals: no "worker", "link-time", "annotation", "reads as", or "NASM reads". Mention the decompiler only when the person can act on it.
3. **Use full sentences with a period** in toasts, prompt errors, notes, Log notes and hovers. Labels and progress text (dock, panel progress, headings) have no period and end with "…" while something is under way.
4. **Put the person's names and code in quotes or code font,** the same way every time: curly quotes in plain text (“main”), code font in hovers and the Log.
5. **Keep the product's terms and capitals:** Project, File, Executable, Listing, Pseudocode, Build, Debug session, Testcases, Entry file. "Program" means only what runs. Say "called" for names, not "named by" or "has the name".
6. **Show an address only when it helps find the thing,** after the name: "(at 0x1149)".
7. **Write numbers and units for people:** "20 seconds", "4,000 characters", "128 characters". Say the limit when you refuse: "Search stopped after 2 seconds."
8. **Pick one form for negatives** and use it everywhere. The suggestions above use "can't" and "couldn't", which read friendlier. Older messages use "cannot" and "Could not".

### Answers to the owner's questions

- **Why 256 KiB (U6).** Renames and comments are saved inside the Project archive's manifest, next to the Byte edits, and the manifest is capped at 1 MiB (`E/lib/projectArchive.ts:41`). 256 KiB keeps them well inside it. That is about 4,000 typical comments or over 10,000 renames. It can be lifted later by storing annotations as an archive entry of their own.
- **S13.** It shows when all three Look in boxes are unticked, so there is nothing to search; the new wording says so.
- **C5.** The comment prompt gets a Delete button when the comment already exists, and the hint no longer explains deleting. Saving an empty comment still deletes it.

# Pixel editor: journal refactor plan

Written on 2026-10-25 when the owner chose "current bytes plus an Edit journal" over the Edit steps kept in the File, after two reviews (a design review from the code alone and a code review). The decision is [the Pixel editor design](./pixel-editor.md), decision 12, and [ADR 0063](../adr/0063-a-file-holds-its-current-bytes-and-undo-is-a-journal-beside-it.md), which supersedes ADR 0047. This plan is for picking the work up after a context compaction.

## Where things stand

- **Done** (2026-10-25, after the compaction): steps 1 to 14, recorded in [the plan's implementation record](./pixel-editor-plan.md#implementation-record), "The Edit journal". Typecheck, lint and format are clean; the full suite passes but for the tests that fail only under its load and pass alone; the browser rows P1 to P6 and P8 of [manual-verification.md](../manual-verification.md) were run again. Step 15, the review, followed, its findings fixed. Committed as `6083b15a` and pushed to `feat/pixel-editor` on 2026-10-25, without a Co-Authored-By trailer.
- Departures from the steps below: the journal compares a reloaded File by `fileFingerprint` (the Compilation fingerprint, a string) rather than a hash of its own; `FileSystem.changeBytes` takes a list of changes and returns each one's inverse, in place of `overwriteBytes`, `overwriteText` and `replaceContent`; the journal is loaded when the session is created rather than mounted; and the annotation history is carried over overwrites (`AnnotationHistory.overwritten`), since it was keyed by a content that now changes with every overwrite.

## Target design

- `ProjectFile` is `{ encoding, content, annotations? }`: no `edits`, no `history`. A File is its current bytes.
- Saved data and archives of version 2 to 4 may still carry `edits`: `cleanFiles` validates them (keep `cleanByteEdits` and `applyByteEdits` as private helpers) and **flattens** them into `content` (base64 of the applied bytes). Nothing writes edits any more.
- **Edit journal**, per File, beside the Project:
    - Entry: `{ label, time, runs: { offset, bytes: Uint8Array }[] }` holding the bytes a change overwrote, or `{ label, time, content: Uint8Array, encoding }` for Canvas size (the whole previous content).
    - Undo pops an entry, writes its bytes back, and pushes onto redo an entry holding the bytes it just overwrote (read at that moment); Redo is the mirror. Each entry stores one side only.
    - Budget: 1 MiB of entry bytes per File (undo plus redo); drop the oldest undo entries past it; the newest stays even if larger. Consider also a 4 MiB cap per Project (drop the oldest entry by time across Files).
    - Staleness: in the session, the journal remembers the `content` string its last change produced; before using it, compare with `project.files[path].content` (string equality, cheap when it is the same string; `cleanFiles` rebuilds records but keeps the strings). A mismatch drops the File's journal (a program's write, an upload). On load from IndexedDB, compare a stored fingerprint (a fast hash of the content string, computed when saving) and drop on mismatch.
    - Rename moves the journal; delete drops it; deleting a Project drops its journals.
- **Persistence**: a Dexie table, e.g. `editJournals` keyed by `${projectId}\0${path}`, holding `{ fingerprint, undo, redo }` with `Uint8Array` bytes (structured clone, no base64). New Dexie version (currently 2) in `src/lib/storage/db.ts`. Saves debounced per File. Loaded for the whole Project when the session mounts (async; until loaded, Undo of a File with an unloaded journal does nothing).
    - Injected through the host: add an optional `editJournals?: EditJournalStore` to `WorkbenchSessionHost` (`src/lib/workbench/WorkbenchSession.svelte.ts` ~line 273), a `Workbench.svelte` prop passed through `WorkbenchShell.svelte` (session created ~line 70). The project page `src/routes/projects/[project]/+page.svelte` (~line 296) passes an IndexedDB store unless `project.id === SHARE_ID`; the exam (`ExamAssemblySection.svelte`) passes none, so its journal is in memory only.
- **Archives** go back to versions 1, 3 and 4 only (writer as on `main`: originals under `files/` were the File itself). Remove version 5 entirely, with `original-files/`, `edits/`, `packEdits`, `unpackEdits`, `editedParts`, `EXPANDED_BYTE_LIMIT` 3× (restore the limits on `main`). The reader still accepts versions 2 to 4 with manifest `edits`; `cleanFiles` flattens them.
- **Share links**: no `withoutSteps`; Files are already flat.

## Review findings and how this refactor treats them

From the design review: history wiped by a rename (gone: the journal is outside the record); the original and undone bytes in links and archives (gone); 2× storage (gone); freezes from insert or delete edits in crafted input (legacy edits are applied once on load; consider refusing more than, say, 10,000 edits a File, or applying them in one pass, so a crafted share link cannot freeze the tab); four undo systems (now Monaco's for text views and the journal for the Hex and Pixel editors, plus the Debug session's); `goToStep` stepping one at a time (fine for the journal; keep it O(steps) in one pass if possible); the budget tight for big pictures (unchanged trade-off).

From the code review: manifest overflow from step labels (gone); `withAnnotations` dropping history (gone); quadratic replay after Canvas size (gone); same-size Canvas size wiping Undo (refuse an unchanged size in `PixelEditor.svelte`'s `canvasProblem`: still to do); cost per step with 24,000 steps (bound the journal's entry count too, say 1,000 a File, and virtualise or cap the panel's rows); more than 2,048 edited Files failing import (gone with version 5); pending Hex typing discarding redo steps (the panel and its Undo/Redo should call the session's typing flush first: `flushTyping` is private in `WorkbenchSession`, add a public path); a remembered Erase tool drawing black when the picture lost its alpha (check `offersErase` when restoring the view state's tool); stale docs (P6, ADR 0047 text: superseded now).

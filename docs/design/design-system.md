# Design system

Status: decided on 2026-11-07 by grilling the [design system audit](../research/design-system-audit.md); decision 1 is [ADR 0078](../adr/0078-every-page-wears-the-workbench-s-look-but-the-home-page.md). The implementation plan is [design-system-plan.md](./design-system-plan.md). What is implemented is recorded in the plan: stages 1-4 done, on `feat/design-system` (stage 3 and stage 4 on 2026-11-08). Terms are in [CONTEXT.md](../../CONTEXT.md) (**Card**, **Tray**, **Popover**). `CardOutline` was renamed `PopoverOutline` in stage 3.

## What it is

One set of tokens and shared components that every page draws with, so that screens stop rewriting the same values by hand and drifting apart. The audit counts what drifted (43 radii, 39 shadows, 66 font sizes, ~30 hover tints, ~18 icon-button recipes) and proposes the tokens and the merges; this record keeps what the owner decided about them.

## Decisions

1. **One look, the Workbench's.** Every page draws with the Workbench's tokens and shared components: Rubik, cards on the `.wb-cards` tokens, hairline lines, tray surfaces. That covers the public pages (`/projects`, `/projects/create`, the documentation index and pages, the course indexes, the blog, `/donate`, `/changelog`, `/examples`), the tool pages and the Workbench itself. The home page is the one exception: it keeps its own motifs (the frame and its guides, the rules with dots, the hex-byte bands, the ruled tile grids, the serif section heads), but builds them from the shared tokens and components. The navbar and the hex footer are site chrome, shared by every page, not home's own. A page outside the editor is always in the Cards surface style; the Lines Preference only applies inside the Workbench. Rejected: carrying the home page's look onto every public page, which suits one long page but not pages dense with content such as the documentation index or the changelog; and letting each area keep its own look over shared tokens, which keeps the drift the audit found.
2. **Three font roles.** `--font-ui` (Rubik) is for all interface and reference text: the app, the index pages, documentation pages and entries, sidebars, search, page titles. `--font-read` (Noto Serif) is for long prose read from top to bottom: lecture bodies, blog post bodies, and rendered Markdown by default, which keeps the Workbench's Markdown Preview and the exam statement in the serif. `--font-mono` (Fira Code) is for code and machine values only (registers, memory, hex, addresses, the Terminal), never for labels or prose. The sidebar's chapter headings move from Fira Code to Rubik, and the 24 bare `monospace` declarations become `--font-mono`. The home page keeps its Fira Code body and serif headings (1). This writes down the rule `EntryBody.svelte` already follows: an entry is reference and uses the app's font, a Lecture uses the serif.
3. **Two floating styles, one rule: anchored or free.** What points at something and is about it is a **Popover**, drawn as `CardOutline` draws the menus today: the menus, the `Select` list, a popover opened from a button (the Pixel editor's tools, `ScreenDisplayConfiguration`), and, drawn the same way though they hold no controls, the Tooltip and the hover cards over data (the Hex editor's, `ValueDiffer`'s, Monaco's hover). It is raised `--tertiary`, with an arrow when it is about one item. What floats free or docks to an edge is a **Tray** (`tray.surface`): the prompts, the toasts, the execution dock, the search palette, dialogs, the floating Debug tools and `FloatingContainer`, the find bars (the Hex editor's, Monaco's) and the notices. Both share one radius, 0.6rem, and the elevation scale (Trays one step, Popovers the next). Their edges stay different on purpose, since a `--tertiary` line disappears on a `--tertiary` fill. The Tooltip's 0.4rem radius ([tooltips.md](./tooltips.md), decision 11) becomes 0.6rem. Rejected: trays for everything, which would undo the Tooltip's solid `--tertiary` fill, chosen so that its text reads over a busy canvas, and the menus' raised look over the item they are about. _Added on 2026-11-07, by the owner, after the first screenshots:_ the Popovers that open over canvases (the `Select` list, the Pixel editor's tool popover, the display configuration) stay translucent like the menus, the blur of what is beneath included. The tool popovers and the hover cards about one item get the arrow, drawn with the card as one outline by `PopoverOutline` (the Tooltips design, decision 13): the Pixel editor's tool popover and `ScreenDisplayConfiguration` point at the button that opened them, and the Hex editor's byte card, the register value card and `ValueDiffer`'s card at the byte, value or cell they are about, never at the pointer. The floating Debug tools keep the Tray's hairline, though it reads fainter over code than their old `--accent2` frame.
4. **Two row states, two tokens.** `--hover-bg` is the surface's own text colour at about 10%. It marks the row under the pointer and the row the arrow keys have reached in a list (the search palette, a menu, the `Select` list), which are one state, and it shows on a Card, a Tray and a Popover alike, a light theme's included. `--selected-bg` is an accent tint of about 20% with a 2px accent edge on the leading side. It marks only the current item, the one the person has: the Explorer's open File, the `Select`'s chosen value (in place of bold), the sidebar's current page, the opened row of the Search and Symbols panels. The accent then always means "this is the one you have". It replaces some 30 hover and selection tints, among them the menus' and `Select`'s accent 25%, which they used because a `--tertiary` tint disappears on a Popover's `--tertiary` fill. The search palette's highlighted row loses its accent edge, since the palette has no current item.
5. **Button roles now, the look later.** `Button` and `ButtonLink` take a role: `primary`, the one action that moves things on (Save, Create, Build), filled with the accent; `secondary`, any other action beside it (Cancel, Open, Download), filled with a tint of the surface's text colour, so it shows on any surface without a fill picked for it; and `ghost`, a label that only takes `--hover-bg` when hovered, for toolbars and Trays, which `tray.tool`, the `FileStatusLine` and `ProjectTopBar` actions and the other bespoke compact buttons become. Two sizes, `sm` and `md`, replace the 33 inline size overrides. `IconButton` is the icon-only `ghost`, in sizes of its own. The `cssVar` prop goes; the few buttons in another colour (`accent2` ×3, `green` ×1) each become one of the roles or stay a deliberate exception, decided as each moves. The look of each role (radius, padding, weight, the hover) stays open, as it was left after the landing redesign, behind one switch as `buttonVariant.ts` already allows.
6. **Uppercase for the panel title only.** The side panel's title, its name at its top (EXPLORER, SETTINGS, SEARCH), stays uppercase and letter-spaced, as VS Code's are: it is the one heading whose job is to differ from everything under it, and in sentence case Settings would stack "Settings" over "Project" with nothing to tell them apart. Every heading inside a panel is in sentence case in one small-heading style: the Settings part titles (DISPLAY), the Explorer's section, library and hints titles, the `CyclesLine` label and the `DocumentationBrowser` label stop being uppercase.
7. **Lines are `--tertiary` at 60%, and a surface can redefine them.** `--line` is the Workbench's hairline as it is today, so no line in the Workbench changes. A surface on which that line would not show redefines `--line` for everything inside it, as `tray.scss` already does with `--tray-line`: a Popover sets it to its text colour at 15%, since a `--tertiary` line disappears on its `--tertiary` fill, and a menu's separators then simply use `--line`. The home page drops its local `--line` and `--line-strong` (the text colour at 11% and 20%) for the shared ones, so its lines take on the theme's colour: bluish on Default and dimmer than before on the RISC-V theme. Rejected: the text colour at 11% everywhere, one recipe for every surface with no overrides, which would change every hairline in the Workbench and lose the theme's colour in them.
8. **One page title, one page column.** `Header.svelte` draws every page title in the style `contentPages.css` gives the content pages today (Rubik 700, 2.75rem, tracking −0.03em, balanced wrapping), as `--fs-h1`: `/projects`, `/projects/create`, `/changelog`, the exam pages and blog posts too, which go from 3.2rem to 2.75rem. Only the home page differs (1). Every index and tool page is one 70rem column with its title at the left edge, so the titles line up from page to page; what is narrower inside it, such as the create form, sits at the left under the title rather than centred on its own. A reading page keeps its sidebar and its prose column at `--md-text-width`. _Added on 2026-11-08, by the owner:_ the create page is centred. Its title, the line under it, the Card holding its form and the drop zone share one 40rem column centred in the 70rem one, the title and that line centred over it; the title stays at the height of the other index pages' titles.
9. **Three status colours, named by meaning.** The theme's shared read-only colours `red` and `green` are renamed `danger` and `success`, with the same values (`#ed4f4f`, `#356a59`), as the `TODO` in `themeStore.svelte.ts` asked, and a third, `warning`, is added at `#d49a30`, the fallback `Editor.svelte` and `LogView` already draw with, so the editor's warning marks and the Log's notes do not change. Each gets its `-text` as every theme colour does. The five hand-written yellows, the Explorer's `#c74444` and `#fff` and `--tc-fail` move onto them. A stored custom theme's `red` and `green` entries are renamed when it loads; they are read-only, so no one has a value of their own in them. _Added on 2026-11-08, in the owner's absence, while implementing stage 3:_ two of the audit's five warning yellows turned out to be data colours, a folder's yellow in the Explorer and a text value's in a Testcase's memory table, and keep their own colour, as the file type colours of `SourceFileIcon` do; the others are warnings and use `warning`.
10. **No automatic check.** Nothing in `pnpm lint` or `pnpm test` rejects a raw radius, shadow, font or colour; review is what keeps new code on the tokens. Rejected: Stylelint with a strict-value plugin, which would be a fourth lint tool just after the Vite+ move cut their number down, and a ratchet script counting raw values per file against a committed baseline. The cost is that drift can come back unnoticed, as the audit shows it did, so a later audit may be worth repeating.
11. **One type scale, a step larger on reading pages.** The interface end is the audit's: `--fs-micro` 0.65rem, `--fs-caption` 0.75rem, `--fs-small` 0.85rem, `--fs-body` 1rem. The page end is the scale `contentPages.css` already has: `--fs-prose` 1.1rem, `--fs-lead` 1.2rem, `--fs-h3` 1.4rem, `--fs-h2` 1.8rem, `--fs-h1` 2.75rem, stepped down for phones in one media query on the tokens (2.1rem, 1.6rem, 1.3rem and 1.05rem for the title, headings and prose). A reading page (a lecture's body, a blog post's body) redefines `--fs-prose`, `--fs-h3` and `--fs-h2` one step up (1.15rem, 1.55rem, 2rem), as `.learn-pages` does today; the title stays at `--fs-h1` (8). The bump moves from the whole `/learn` section to the reading pages, so the course indexes are drawn at the docs' size and blog posts gain it. The ~450 `font-size` declarations round to the nearest step. The audit's `clamp(2.2rem, 4vw, 3.2rem)` title and 1.6rem `h2` are not used. _Added on 2026-11-08, in the owner's absence:_ blog posts were not at the docs' size but larger, so one reading scale shrinks them a little (prose 1.2rem to 1.15rem, `h2` 2.2rem to 2rem, `h3` 1.8rem to 1.55rem; the title per D8); kept, so lectures and posts share one scale. A reading page's lead (a blog post's stand-first) is a step up too, `--fs-lead` 1.3rem (1.2rem on phones), so it reads larger than the 1.15rem prose under it.
12. **Radii: a scale for what stands alone, a derived radius for what is chained.** The scale is `--r-chip` 0.25rem, `--r-control` 0.4rem (a Card's too, as `--wb-radius` is), `--r-overlay` 0.6rem (Trays, Popovers, a lecture's code blocks, the file drop zone) and `--r-pill` 999px, and it is only for an outermost surface or a control that stands on its own. An element close inside a rounded parent takes the parent's radius less the parent's border and its inset from the padding edge, never below 0, written with one helper that names the parent's token (`nested-radius(var(--r-overlay), $border: 1px, $inset: 0.25rem)`), so that changing the parent's token moves every child with it and a grandchild chains the same way: the dock's tools, a menu's highlighted row, the palette's rows, `SegmentedControl`'s highlight (today 0.4rem − 0.1rem border − 0.1rem inset = 0.2rem, by hand), Monaco inside the editor Card. A child inset by at least its parent's radius is far from the curve and takes its own step of the scale. The owner wants concentric corners and has tuned some by eye: the migration rewrites only a radius it can explain, as a step of the scale for something standing alone or as a derived radius for something chained, leaves any other one as it is and lists those for the owner to look at, rather than rounding it to a step. The audit's `--r-sheet` (1rem) is cut: its users become Cards (the blog cards), Trays (`FloatingContainer`, the floating Debug tools) or `--r-pill` (`RgbLine`, the theme editor's swatches, the editor's badges).
13. **Three shadows, two durations.** `--shadow-1` for sticky headers and raised rows, `--shadow-2` for Trays and `--shadow-3` for Popovers; the audit's `--shadow-4` is cut, since the palette and the floating windows are Trays (3), and `FloatingContainer`'s and the agent panel's shadows fold in. `--dur-fast` 120ms for hover and press, `--dur-base` 160ms for a Tray or Popover opening and closing, `--ease-out` as Svelte's `cubicOut`, and one `prefers-reduced-motion` rule. The toasts' 400ms becomes `--dur-base`, and the 18 `transition: all` name their properties.
14. **Choices, tabs and tools are three components.** `SegmentedControl` picks one value or view out of a few short options shown at once (the dock's view switch, Little · Big, Hex · Text, the Symbols panel's filter, `SizeSelector`, the choices in Settings); it loses its `tabs` mode and moves from `specific/project/cpu/` to `shared/input/`. A new `TabStrip` switches what a panel shows, as a strip on the panel's top edge, with closable tabs as an option: `FileTabs`, `BottomPanel`, the Playground's file tabs, the Register files' CPU · FPU · CSR (out of `SegmentedControl`'s `tabs` mode, keeping their look) and the embed page's CPU · System. The modes of a tool, where a button can do more than select, are a toolbar of `IconButton`s with a `pressed` state: the Pixel editor's tools, whose current tool opens its settings when pressed again, which a `SegmentedControl` cannot carry. The home page's browser tabs over its demo are tabs and one of its motifs (1), and stay as they are. This keeps the rule that options shown at once are a `SegmentedControl`, never a row of pressed-key buttons, and that tabs keep their look.
15. **Fira Code from its variable font, at 500 by default.** `global.css` loads `FiraCode-VF.woff2` (weights 300 to 700, 113 KB) declared `font-weight: 300 700`, in place of the static `FiraCode-Medium.woff2` (102 KB) declared with no weight, which every Fira Code text is drawn in today whatever weight it asks for, bold synthesised by the browser. `--font-mono` text defaults to weight 500, and Monaco gets `fontWeight: '500'`, which it does not set today, so code, registers and memory keep their weight (the variable font at 500 lays about 2% more ink than the static Medium file, checked in Chrome, a change too small to see side by side); bold Fira Code becomes the real 700. A request below 500 also draws at 500, which gives up Fira Code Light. The five static Fira Code files and `Orienta-Regular.ttf` in `static/fonts/` are referenced by nothing and go. Rejected: keeping the Medium file and giving up bold Fira Code, 11 KB lighter but a rule to remember. Rubik needs nothing: its file from Google Fonts is variable too, and Chrome draws its weights from the font's axis with no range declared (checked on 2026-11-07: 400, 500, 600 and 700 measure 639, 669, 675 and 691 px on the same text, ranged or not).
16. **One branch in four stages, the second checked by pixel diff.** The work goes on one branch, `feat/design-system`, as one series of commits per stage, and the owner reviews at the end of each stage. 1, fixes that need no decision: the undefined variables, the global focus ring, `font: inherit` on form controls, `monospace` to `--font-mono`, Fira Code's variable font (15), the exam page's offset, themed scrollbars, the dead files. 2, tokens: the tokens are added, the old names become aliases of them (`--wb-line: var(--line)`), and raw values that already equal a token are replaced; nothing on screen may change, which is checked by screenshotting every route and the Workbench's states before and after on the same machine (the audit's list, `.cache/design-system-audit/`) and requiring them to be identical. 3, components: `IconButton`, the Button roles (5), `TextField`, `TabStrip` (14), `PopoverOutline` (3), `Kbd`, `Badge`, `Spinner` and `EmptyState`, each with its call sites in the same change. 4, pages: the page title and column (8), the one Card, the home page on the shared tokens (7), the embed and exam pages brought up to the Workbench. Stages 3 and 4 come with before and after screenshots of what changed and the list of radii the migration could not explain (12). The Buttons' look stays as it is until the owner takes up its own decision (5).
17. **Muted text is one thing, and the prose colour is renamed.** `--text-muted` is the surface's own text colour at about 65%, taken from `currentColor` as `--hover-bg` is (4), so it reads on a Card, a Tray and a Popover alike. It replaces the 154 opacities on text, the ~27 `color-mix` text tints and the home page's `--muted` (68%). The theme's `--*-text-muted` colours, which are not muted labels but the text dimmed a hair for long prose (`#d4d4d4` against `#dbdbdb`, used 39 times, nearly all in documentation prose), are renamed `--*-text-prose`, so that "muted" means one thing; the audit had proposed them for the labels, which would have brought a label at 60% opacity back to nearly full brightness. `--hint` (`#939393`) stays for placeholders and the faintest text. Rejected: dropping the prose colour into the text colour, since it was added on purpose.

## The owner's changes after reviewing the result (2026-11-08)

Asked for by the owner after looking at the finished work; each overrides what the decision named says, in the places named.

- **Tooltips and hover cards take a control's corner** (0.4rem, `tooltipRadius()` in `styles/elevation.ts`), not the menus' 0.6rem (D3, D12). Menus keep theirs.
- **The floating windows** (the Debug tools, the Screen window) have their `--accent2` frame back and a control's corner (D3's addition: the hairline was not visible enough).
- **The CYCLES label is uppercase**, the one label inside a panel that keeps its capitals (D6).
- **Register and memory values** stay in Fira Code (D2) but at its regular weight and scaled to the old system monospace's size (D15's 500 default does not apply to them).
- **The memory panel's region picker, address box, list and filter** keep their old look, written in `MemoryControls.svelte`, not the shared field look.
- **Every field** (TextField, Textarea, the Select trigger, SearchField, the inline editors) takes the old Testcase fields' colours.
- **The navbars' buttons**, the site's and the Workbench top bar's (its logo cell, Back, Donate, Share), are square, the bar's full height and edge to edge again, with their old padding (D5's roles, not its shapes, apply there).

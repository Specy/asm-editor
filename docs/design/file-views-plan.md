# File views: implementation plan

Written on 2026-10-15, after the design interview. The decisions are in [file-views.md](./file-views.md) (18 decisions, its **Research**, **Deferred** and **Open for planning**), [ADR 0047](../adr/0047-byte-edits-are-kept-apart-from-the-original-bytes.md) (Byte edits), [ADR 0048](../adr/0048-decompiled-code-is-a-view-not-a-file.md) (decompiled code is a view), [ADR 0049](../adr/0049-pseudocode-comes-from-our-own-ghidra-decompiler-package.md) (our own Ghidra decompiler package) and [ADR 0050](../adr/0050-the-built-program-is-a-build-output-never-saved.md) (the Build output); the vocabulary is in [CONTEXT.md](../../CONTEXT.md) (**Hex editor**, **Byte edit**, **Preview**, **Pseudocode**, **Build output**, and the **Executable**, **Listing** and **Patch** of [the binary import design](./binary-import.md)). Read them before starting. The plan covers a new repository and package, `@specy/decompiler`, and the editor work in `packages/asm-editor`; the x86 Core needs no change.

It is written for an agent implementing it without the interview's context. Where this plan and the design disagree, the design wins; where a step needs a choice neither settles, take the default in **Decisions taken while planning** and note it in the design's implementation notes.

## Ground rules

- **Repositories.** The editor is this monorepo (pnpm + Vite+, `mise install && pnpm install`; [ADR 0043](../adr/0043-the-repository-is-a-workspace-of-its-packages.md)). The decompiler is a new repository, `Specy/decompiler-js`, which the owner creates on GitHub; until then, initialise it locally and add it as the submodule `packages/decompiler` once the remote exists (ask the owner). Decompiler work is committed in the submodule, editor work in the monorepo. The x86 Core (`packages/x86`) is read, not changed.
- **Never** add `Co-Authored-By` trailers to commits; the owner strips them. Do not push: the owner pushes, creates the repository and tags releases.
- **Building wasm.** `source ~/emsdk/emsdk_env.sh` (emsdk 6.0.9, as the x86 Core uses). The monorepo's toolchain (`mise.toml`) has no emsdk and must not gain it: as in the x86 Core, the built wasm and compiled processor descriptions are committed, CI never rebuilds them, and the build script prints sha256 lines to record in the commit message.
- **Editor checks.** From the root: `vp check` and `vp test` as the repository's scripts define them (`--maxWorkers=2` if the machine is shared), and the browser verification recipes in the owner's notes: headless Chrome 153, which reports `hover: none` (patch `matchMedia`); Monaco needs a real click before typing; run your own dev server with HMR off, its own cache directory and port, started with `node_modules/.bin/vp dev`, if other sessions edit the tree.
- **Reading code.** Line numbers below were taken on 2026-10-15 and will drift; search for the named function. Paths without a prefix are under `packages/asm-editor/src/`.

## Decisions taken while planning

Taken by default, for the owner to overturn. Record any change in the design.

1. **Names and layout.** Repository `Specy/decompiler-js`, npm `@specy/decompiler`, submodule `packages/decompiler`. Inside: `ghidra/` (the vendored upstream subset), `patches/` (our changes to it, applied by the build script), `host/` (our C++ host layer), `specs/<architecture>/` (compiled processor descriptions), `js/` (the npm package: TypeScript wrapper, wasm, tests), and `scripts/` (`vendor-ghidra.sh`, `compile_specs.sh`, `compile_decompiler.sh`, and the native build and reference scripts). The monorepo's workspace lists `packages/decompiler/js`.
2. **Ghidra 12.1.4**, vendored as `Ghidra/Features/Decompiler/src/decompile/cpp` and, per architecture, the `.slaspec`, `.pspec`, `.cspec` and `.ldefs` files it needs, with Ghidra's `LICENSE` and `NOTICE`. Moving to a newer release is a deliberate change with its own commit.
3. **The build.** emsdk 6.0.9, `-O2`, native wasm exception handling (`-fwasm-exceptions`, in every current browser) rather than JavaScript-emulated exceptions, no threads, an ES module factory. Processor descriptions are written into Emscripten's in-memory filesystem from bytes before the architecture is built, so nothing reads files synchronously over the network. The wasm is a separate asset loaded by URL (about 2 MB, too large to inline as the disassembler does).
4. **Processor descriptions are compiled ahead of time** with Ghidra's own SLEIGH compiler, built natively from the same vendored sources, and committed. Version 1.0 carries `x86-64` only; another architecture is a later minor release.
5. **Prototypes ship with the package** as `prototypes/glibc.h`: C declarations for the glibc functions programs commonly call (stdio, string, stdlib, unistd, fcntl, ctype, time, signal, setjmp, the `_chk` and `__isoc99_` variants, `__libc_start_main`, `__stack_chk_fail`, `__cxa_*`), each parsed by the decompiler's own C parser, with the noreturn ones marked (`exit`, `_exit`, `abort`, `__stack_chk_fail`, `__assert_fail`, `longjmp`, `err`, `errx`, `pthread_exit`, `__cxa_throw`). The caller passes them; nothing is hard-coded in the host layer (ADR 0049, amended).
6. **The package's API** (TypeScript, addresses as `number`: every x86-64 user address is below 2^53):
    - `loadDecompiler({ architecture: 'x86-64', wasmUrl? }): Promise<Decompiler>`
    - `decompiler.openProgram(image: ProgramImage): DecompiledProgram`, where `ProgramImage = { regions: {address, bytes, readOnly, executable}[], functions: {address, name}[], data: {address, name, size?}[], strings: {address, length}[], prototypes: string }`
    - `program.decompile(address, { maxInstructions? }): DecompiledFunction`, `= { address, name, text, lines: DecompiledLine[] } | { address, error }`, `DecompiledLine = { text, tokens: {start, end, kind, address?, target?}[], addresses: number[] }`, where `kind` is Ghidra's token class (keyword, variable, function, type, constant, comment, syntax), `address` the instruction a token came from, `target` the address a function or data name refers to, and `addresses` the sorted set of a line's instruction addresses
    - `program.dispose()`, `decompiler.dispose()`
7. **The Pseudocode uses the Listing's names** for every function and data it refers to, invented ones included (ADR 0045): the editor passes every label the Listing has, `DAT_` names and `name@got` slots included, and the package invents no names of its own, so an address the Listing does not name prints the decompiler's own (`cRam0000000000004018`). Local variables and parameters keep the decompiler's (`iVar1`, `acStack_98`, `param_1`); the Ghidra application's `local_98` comes from stack analysis on its Java side, which is not replicated. Strings print inline as Ghidra prints them (`puts("Correct!")`).
8. **The editor runs the decompiler in its own worker** (`lib/pseudocode/pseudocode.worker.ts`), one per Workbench session, like the Listing worker: requests answered in order, a request silent for 45 seconds, above the decompiler's own 30-second limit (D3.2), ends the worker (restarted at the next request), results cached by File content, base, function address and decompiler version, 32 kept.
9. **The saved form of a Byte edit.** `ProjectFile` gains `edits?: readonly ByteEdit[]`, only on `base64` Files, omitted when empty; `ByteEdit = { offset: number; remove: number; insert: string }` (`insert` in base64), applied in order to the original bytes (`content`). The editor writes only `remove` equal to the inserted length, and while every edit is an overwrite it may merge them into sorted, non-overlapping runs, since the result is identical. A Project with edits opened by an older editor loses them silently through `cleanFiles`, which is acceptable for a site that always serves its newest build.
10. **Archives.** A File's manifest entry becomes `{encoding, edits?}` and `files/` keeps the original bytes; `ARCHIVE_VERSION` becomes 2 only when some File has edits, so an archive without any stays readable by older editors.
11. **Reading a File.** `fileBytes(file)` returns the edited bytes everywhere; a new `originalBytes(file)` returns the original. Fingerprints, content equality and caches keyed on content include the edits. A byte File's encoding never changes through Byte edits.
12. **Views.** `FileView = 'text' | 'hex' | 'listing' | 'pseudocode' | 'preview'`. Each `EditorGroup` holds a map from path to view; the Project saves `fileViews` (path to the last view chosen, only where it differs from the File's default) beside `openTabs`, cleaned the same way. Model keys include the view (`sessionId:path#listing`, `#pseudocode`), so a Listing pane and a Pseudocode pane of one File have models of their own, and code that picks a group by path picks by path and view.
13. **The switch** is a `views` prop of `ExecutionDock`, drawn in the left toolbar outside the debugging branch with the dock's own tool buttons (`aria-pressed`), not `SegmentedControl`'s pill. A pane showing a byte File always gets a dock carrying at least the switch, on every device class (on a tablet, a pane dock like a source File's compile dock).
14. **The Pseudocode pairing** is function-scoped: a `PseudocodeMap` holding the Listing line range of the function and, both ways, Listing lines to Pseudocode lines, built from the decompiler's line addresses through `lineOfAddress`. The pairing's consumers take an optional line range so they walk only the function's lines rather than the whole Listing.
15. **The Build output** comes from `core.getExecutable()` right after `compileProject` succeeds (no Core change). Its path is `commandLineProgram(entry)` without `./`. The editor's FileSystem capability presents it to the program as a read-only file at `/project/<path>`, protected with `setProtectedPath`, and so do the Testcases' FileSystems. It stays listed until the next Build starts or the Project closes, dimmed with "From an earlier Build" once a source File has changed since. Its Listing and Pseudocode take no Breakpoints and show no program counter: the debugger follows the assembly source. "Keep as File" asks for a name, prefilled with its path, and refuses an existing one.
16. **Recognition by signature** (`lib/fileKinds.ts`): PNG `89 50 4E 47 0D 0A 1A 0A`; JPEG `FF D8 FF`; GIF `GIF87a`/`GIF89a`; WebP `RIFF????WEBP`; BMP `BM`; ICO `00 00 01 00`, CUR `00 00 02 00`; AVIF an ISO box `ftyp` with brand `avif` or `avis`; JPEG XL `FF 0A` or the container `00 00 00 0C 4A 58 4C 20 0D 0A 87 0A`; PDF `%PDF-` at offset 0, as the MIME Sniffing standard has it; audio `ID3`, an MPEG frame sync, `OggS\0`, `RIFF????WAVE`, `fLaC`; video an `ftyp` box of any other brand (MP4, MOV) and EBML `1A 45 DF A3` (WebM, Matroska). An ELF stays `executableKind`'s.

- **Batch 2, branch `feat/pseudocode`, from `feat/file-views`** (rebased onto `main` once Batch 1 is merged): D1.6 (the submodule, once the owner has pushed `Specy/decompiler-js`), E8, E9, the rest of E10 (the Pseudocode's Documentation and verification), and D4, the package's 1.0.0 release, once E8 has used its API. ### D1. Decompiler: repository and build

Files: the new repository (decision 1).

1. **Vendor Ghidra 12.1.4** (decision 2) with a `ghidra/README.md` naming the tag, the commit and the files taken, and the licences. Keep a script that re-vendors from a tag, so an upgrade is reproducible.
2. **Build natively first.** Build the decompiler's console (`decomp_dbg`/`consolemain`) and the SLEIGH compiler with the host's compiler, compile `x86-64.slaspec`, and decompile `main` of the binary import fixture `crackme` (copied into `js/tests/fixtures/` from `packages/x86/blink-js/tests/fixtures/elf/` with its README's sha256 and source) through the console, as the known-good reference for the wasm build.
3. **`compile_specs.sh`** builds the SLEIGH compiler and writes `specs/x86-64/` (`x86-64.sla`, `x86-64.pspec`, `x86-64-gcc.cspec`, `x86.ldefs`), printing sha256 lines.
4. **`compile_decompiler.sh`** builds the library with the host layer (empty for now beyond a smoke entry point) to `js/src/wasm/decompiler.{wasm,mjs}` with decision 3's flags, applying `patches/` first; record the size, raw and gzipped. Patch what Emscripten needs (file access through `ifstream` and directory scans of the spec directory) in `patches/`, each patch with a comment saying why.
5. **The npm package skeleton** in `js/`: `package.json` (`@specy/decompiler`, `0.0.0` until D4, `type: module`, exports `.` and `./prototypes/glibc.h`), `tsdown` build, a `copy-assets.mjs` placing the wasm, the specs and `LICENSE`, `NOTICE` and the zlib licence in `dist`, vitest in Node, `npm run type-check`, `test`, `build`, `test:dist`.
6. **Monorepo wiring** (once the owner has created the remote and the submodule is added): `pnpm-workspace.yaml`, `.gitmodules`, a `build:decompiler` task beside `build:x86` in the root `vite.config.ts` and in `build:cores`, the `CORES` ignore lists, and CI's `cores` job's uploaded paths. Tests: `pnpm cores:build` builds it; the editor resolves `@specy/decompiler` through `workspace:*`.

### D2. Decompiler: host layer and markup

Files: `host/` (C++), `js/src/`.

1. **The architecture.** A `SleighArchitecture` subclass (as Pyre's `WebArchitecture` and rz-ghidra's `RizinArchitecture` do; borrow from Pyre's, which is MIT, crediting it) whose load image answers from `ProgramImage.regions`, whose symbol database holds `functions` and `data` names, whose read-only ranges come from `readOnly` regions, and whose strings are `strings`. The language is chosen from `x86.ldefs` by `architecture`; the compiler spec is `gcc`.
2. **Prototypes.** Parse `ProgramImage.prototypes` with the decompiler's C parser into its type and prototype store, binding by name; mark the noreturn ones. A declaration that does not parse is reported once in `openProgram`'s result, not thrown.
3. **Markup.** Decompile with Ghidra's markup emitter (or an `Emit` subclass overriding `tagOp`, `tagVariable`, `tagFuncName` and `tagLine`) and turn each token's op reference into its instruction address and each function or data name into its target, producing decision 6's `DecompiledLine`s. Not every token or line has an op; a line's `addresses` is the set of its tokens' addresses.
4. **The TypeScript wrapper** (decision 6): loading the wasm and the specs by URL, `openProgram`, `decompile`, `dispose`, with the C++ exceptions surfaced as `{ address, error }`.
5. Tests, in Node against the wasm: crackme's `main` (from its symbols) decompiles to text containing `strcmp`, `"hunter2"` and `puts`; with `crackme-stripped` and the Listing's invented names passed as `functions`, the text uses those names; every token with an `address` names an address inside the function; the result for crackme's `main` matches the native console's (D1.2) modulo names; `dispose` frees memory (decompile the same function 500 times without the heap growing past a bound you measure).

### D3. Decompiler: prototypes, guards and measurements

1. **`prototypes/glibc.h`** (decision 5): write it from the bundled glibc's exported functions most programs call, and test that every declaration parses and every noreturn mark lands.
2. **Guards**: `maxInstructions` (default Ghidra's 100,000) and a per-call time limit of 30 seconds, Ghidra's default, inside the wasm; a function that exceeds either returns `{ address, error }`, with tests of both.
3. **Measurements**, recorded in the package README and the design's implementation notes: load time and the time to decompile each function of `crackme`, `crackme-stripped` and the static non-PIE `hello-atexit` (thousands of glibc functions; take its 20 largest), first call and warm. Targets: a small function under 100 ms warm. The slowest functions are recorded, not failed: `printf_positional` in `hello-atexit-static` took 14 s in D2, within the 30-second limit.
4. _(Moved to E8.1 on 2026-10-15: it needs the monorepo, so it is written with the `ProgramImage` builder.)_

### D4. Decompiler: release

After E8 has used the API in the editor (moved on 2026-10-15), so that 1.0.0 is the API the editor needs; the editor uses the workspace build until then.

1. `README.md` shaped like the x86 Core's (library only; no mention of the editor), `CHANGELOG.md`, the licences and `NOTICE` in the package, a CD workflow copied from the x86 Core's `cd.yml` (tag on the default branch, version match, checks, `npm publish` with trusted publishing).
2. Version `1.0.0`. Stop for the owner to review, push, tag and publish. The editor keeps using the workspace build meanwhile.

### E1. Byte edits in the Project

Files: `lib/projectFiles.ts`, `lib/projectArchive.ts`, `lib/Project.svelte.ts`, `lib/languages/peripherals/FileSystem.ts`, `lib/sourceCompilation/fingerprints.ts`, `lib/executables.ts`, `lib/listing/listingDocuments.svelte.ts`, the readers in **Starting point**.

1. **The record** (decision 9): `ByteEdit`, `ProjectFile.edits`, `applyByteEdits(original, edits)`, `mergeOverwrites(edits)`; `cleanFiles` validates and keeps `edits` (offsets inside the File, `remove` equal to the insert's length while only overwrites exist, total size within the 16 MiB limit counted as original plus edits).
2. **Readers** (decision 11): `fileBytes` applies the edits, `originalBytes` does not; `fileText` refuses a File with edits (only base64 Files have them); every direct reader in **Starting point** goes through `fileBytes` or includes the edits in its key (`fileFingerprint` hashes `encoding\0content\0` plus the edits; `projectContentEquals` and `contentKey` compare them; `startsWithElfMagic` and `executableAnalysis` read the edited bytes, so a Byte edit to the magic number is seen).
3. **Writes.** `FileSystem.editBytes(path, offset, bytes)` appends an overwrite to a base64 File's edits and commits, refused while locked and on a text File. `writeBytes`, uploads and a program's write replace the record and drop its edits (ADR 0047, decision 15).
4. **Undo in a Debug session** keeps records: a history node remembers the record it replaced, and an Undo that returns a File to those bytes restores that record (original and edits) instead of rebuilding one with `bytesFile`.
5. **Archive and share link** (decision 10): manifest `edits`, version 2 when needed, round trip; a share link carries `edits` through `toObject()`.
6. Tests: unit tests of apply, merge and validation; a File keeps `base64` when its edits make it valid UTF-8; Build sources, fingerprints and Listing documents change when an edit does; an upload and a program's write drop edits; Debug session Undo restores original and edits; archive round trip with and without edits (version 1 when none); IndexedDB save and load.

### E3. The Hex editor

Files: new `components/specific/workbench/hex/` (`HexEditor.svelte`, `hexGrid.ts`, `hexSearch.ts`, `dataInspector.ts`, `HexStatus.svelte`), tests beside them.

1. **Grid** (decision 7): offset column (hex, as wide as the File's largest offset), 16 bytes a row, hex and text columns (printable ASCII, `.` otherwise), drawn for the visible rows plus a margin only. Row height fixed; when the rows' total height passes a browser's element limit (keep it under 8 million pixels), the scrollbar is scaled: a fixed-height scroller maps its position to a row. The memory view's font, cell padding, colours and hover style.
2. **Caret and typing**: one caret, in the hex column on a nibble or in the text column on a byte; arrow keys, Home and End (row), Page Up and Down, Ctrl+Home and End; Tab switches column. Typing a hex digit overwrites the nibble and advances; typing in the text column overwrites the byte with the character's code when it is printable ASCII. Each change is a Byte edit through `FileSystem.editBytes` (debounced into one edit per run of typing).
3. **Undo and Redo** (Ctrl+Z, Ctrl+Shift+Z or Ctrl+Y): a per-File stack of the edit lists before each change, for the editor's lifetime, as Monaco's is.
4. **Selection and copy**: Shift with arrows or a drag; copy as hex (`7f 45 4c 46`) or text from a context menu, Ctrl+C copying in the caret's column's form.
5. **Go to offset** (Ctrl+G; hex with or without `0x`, or decimal with a `#` prefix) and **Find** (Ctrl+F; hex bytes with `??` wildcards, or text; next and previous, wrapping), in a small bar like Monaco's.
6. **Status line**: caret offset, selection length, File size, "edited" when the File has Byte edits.
7. **Data inspector**: the value at the caret as signed and unsigned 8, 16, 32 and 64-bit integers and single and double precision, in both byte orders (a toggle), from `byteSliceToNum`, `unsignedBigIntToSigned`, `decodeSingle`/`decodeDouble` and `formatFloat32`/`formatFloat64`. A side panel on a wide pane, collapsible; below the grid on a narrow one.
8. **Read-only** during a Debug session or for a read-only Project, under decision 8's notice for an Executable ("The File's bytes. Patches and the program's writes are in memory: see the memory view."); a Build output is always read-only.
9. **Phone** (open item): 8 bytes a row below a width you measure; the inspector below the grid.
10. Tests (jsdom): typing nibbles and characters makes the expected Byte edits; Undo and Redo; selection and copy text; go to; find with wildcards; only visible rows are in the DOM for a 16 MiB File; the scaled scrollbar reaches the last row; read-only refuses typing.

## Risks and open items

- **The decompiler build** may need more patches than expected for Emscripten (file access, exceptions, memory); Pyre and the npm package show it can be done, and D1.2's native reference catches a wasm build that decompiles differently.
- **Decompile times** in wasm are unmeasured (no figures were found); D3.3 measures them. If a large function is slow, the guards return an error rather than hang, and the worker restarts.
- **Memory.** One `DecompiledProgram` per open Executable holds a copy of its bytes in the wasm heap; dispose it when the File's content changes or its last pane closes.
- **Names Ghidra prints itself**: a function the Listing does not start (a target only reached through a jump table) gets Ghidra's `FUN_<address>`; record how often in D3, and if it matters, pass such targets back to the Listing's naming rather than letting the two disagree.
- **Byte edits in an older editor** are dropped silently (decision 9).
- **The Hex editor on a phone** is new ground (E3.9).

# One instruction layout for every language

Status: being decided on 2026-10-18 in a grill session. Terms are in [CONTEXT.md](../../CONTEXT.md) (**Documentation entry**, **Instruction form**, **Instruction tag**, **Instruction category**). It builds on [instruction-categories.md](./instruction-categories.md). The implementation plan, with the planning decisions 13-22 I made after the session, is [instruction-layout-plan.md](./instruction-layout-plan.md).

## What it is

Each language draws an instruction's **Documentation entry** its own way today: MIPS and RISC-V list every form as a sentence, x86 joins every form with `|` above the description and again in a table, the Z80 has one table row per form (192 for `ld`), and M68K has a flags grid and an addressing-mode table nobody else has. The Workbench's Documentation panel and the documentation pages have drifted apart as well. This design gives all five languages one layout, taking the best part of each.

## Decisions

1. **One view, two places.** One shared instruction view draws every language's instruction entry, on the documentation page and in the Workbench's Documentation panel, at two densities: the full page and the compact panel. Each language feeds it through the same data shape instead of drawing its own page.
2. **A row is a Form pattern, not a form.** The list of forms shows one row per **Form pattern**: the **Instruction forms** that differ only in an operand's width or in which register of one class they name are one row, written with a symbol the page explains (`r`, `rr`, `r/m`, `imm`), with chips for the widths it comes in. Forms with different **Instruction tags** never share a row, so MIPS `lw $t1,-100($t2)` (a real instruction) and `lw $t1,100000($t2)` (a pseudo-instruction) stay apart. Expanding a row lists the forms it stands for, with each one's own facts. Measured on today's data: x86 `mov` goes from 65 rows to 15, `add` from 38 to 4, `cmovle` from 6 to 1; Z80 `ld` from 192 to 31, `add` from 42 to 13; M68K is already written this way; MIPS `lw` goes from 12 to about 8. The Z80's per-form sentences ("Loads B into A") become one per row ("Loads `r'` into `r`"), the concrete ones staying in the expanded row. Each language needs a small step that knows its operand classes.
3. **Sections by tag, then rows by note.** The list starts with the untagged Form patterns under "Forms", then one section per set of **Instruction tags** ("Pseudo-instructions", "Undocumented", "Privileged", "RV64 only", or a heading naming both tags for a pattern that has two, such as Z80 `add ixh`). The section heading says the tag once, with a line on what it means, instead of a badge on every row. A row carries a note only when it adds something to the instruction's description; inside a section, rows with the same note sit under it once. MIPS `lw` reads as one real form, then its pseudo-instructions under three notes; x86 `add` as four rows with no notes; Z80 `ld` as rows each with its own note.
4. **Facts on the row's own line.** A Form pattern's facts (Z80 bytes and cycles, x86 processor level and NASM notes, M68K sizes) are a short line at the right end of its row, which drops under the syntax on a phone, instead of table columns. A fact with the same value on every row is said once in the page's header instead (x86 `cmovle` is "Pentium Pro and later" for every form). A fact that differs inside one Form pattern sits on its width chip and in its expanded row. On today's Z80 data, 281 of 284 Form patterns have one byte count and one cycle count; the other three are register splits that make their own rows (`ld (nnnn),hl` is shorter than `ld (nnnn),bc`).
5. **One flags strip.** Every language with status flags shows one strip under the header, in the order of that language's register panel (x86 `CF PF AF ZF SF … OF`, Z80 `S Z H P/V N C`, M68K `X N Z V C`), each flag with one mark from a shared set (changed by the result, set to 0, set to 1, undefined, unchanged) and the legend once. When the Form patterns of a mnemonic affect the flags differently (Z80 `add a, r` against `add hl, rr`), the flags go on each row's fact line instead. MIPS and RISC-V have no strip. x86 gets flags from a new source, Intel's XED tables (Apache-2.0, flags per form, to be confirmed), and shows no strip until it has them.
6. **The header, and a long name and summary for every mnemonic.** The header reads: the mnemonic with its long name ("Load word") and mnemonic-level tags beside it, muted, its **Instruction category** left to the sidebar and the Chapter's headings (plan, decisions 29 and 30), a one-sentence summary of the whole mnemonic, then the facts that are the same on every row ("Pentium Pro and later", "Sizes .b .w .l, .w by default"); the flags strip follows. The long name and the summary are two fields of each mnemonic, no longer the first form's description (which gives Z80 `add` the summary "The value of BC is added to HL."). They are derived where the source has them (the MARS and RARS "Title :" prefix, the x86 Opcodes summary, M68K's first sentence) and written in a small table per language in the editor where it has not or is wrong (all 68 Z80 mnemonics, the 113 x86 ones without a summary), with a test that every mnemonic has both. The same summary is the page's, the hover's, the search row's and the meta description. A longer description follows the header only where the language has more to say than the summary.
7. **Each language's own notation, explained on the page.** Rows are written in symbols in the notation of that language's manual and **Language course** (NASM's `r/m32` and `imm8`, the Z80's `r` and `nn`, M68K's `Dn` and `<ea>`, MIPS `$rt` and `imm16`), not in example values: MIPS reads `lw $rt, imm16($rs)` rather than MARS's `lw $t1,-100($t2)`, whose `-100` silently meant "signed 16-bit". MARS's spellings stay as the concrete forms in the expanded row. An "Operands" legend under the list explains only the symbols that page uses, one line each with its meaning and range ("`imm16` signed 16-bit, −32768 to 32767", "`r` any of A B C D E H L"); hovering or tapping a symbol in a row shows its line, which links to the symbol's own **Documentation entry** where there is one (Z80 operands, M68K addressing modes). One notation shared by all five languages was rejected: the pages would look more alike but stop matching the manuals and courses students read next to them.
8. **One order of sections.** Every instruction reads: header, flags strip (where the language has flags), Forms, Operands legend, description (where there is more than the summary), example. The header and the Forms answer "what does it do and how do I write it" without scrolling, now that the Form patterns keep the list short; the description is for reading and the example for trying. MDN's order, the example straight after the header, was rejected because it puts an embedded editor several hundred pixels tall ahead of the forms on every page.
9. **The panel keeps every section; long sections are cut by count.** The compact panel shows the page's sections in the page's order, with the fact lines always under the syntax and the example as static highlighted code instead of the runnable editor. A section of more than about six rows shows six and a "Show all" that expands in place, so it works in an **Exam** where links are disabled. Rows are ordered so that the cut keeps the common ones, in the order the language's manual uses, never the source table's order (x86 `mov` showed "4 of 65 forms", all four `moffs`). On the page every section is open except the Undocumented ones, which start collapsed with their count. There is no filter: with Form patterns the longest list is about 31 rows (Z80 `ld`).
10. **The forms list shows what the language's emulator runs.** x86 forms that need an extension the Core does not run (APX, BMI2 and the rest; 19 of `add`'s 38 forms, 461 of the 1443 on today's pages) and `nolong` forms, which do not assemble in 64-bit code, are left out of the list. One line at its end says what was left out ("19 more forms need APX, which this emulator does not run") and opens to list them; it was to link to the x86 "Complete documentation" page, which turned out not to list an integer instruction's extension forms (plan, decision 28). RISC-V's RV64 only forms stay as a tagged section, because RV32 and RV64 Projects read the same page. The x86 notes that remain are written in words on the fact line ("takes LOCK", "64-bit mode only"), and the raw NASM flags and the "recent" processor level go.
11. **Pseudo-instructions show their expansion.** On MIPS and RISC-V each pseudo form in an expanded row shows the real instructions the assembler turns it into, with the Core's placeholders rewritten into the page's symbols (`lui $at, hi(imm) ; lw $rt, lo(imm)($at)` for `lw $t1,100000`). The templates are in the Cores already (MARS `PseudoOps.java`, RARS `PseudoOps.java`) but are not exported: MARS and RARS each gain a per-form export, released and bumped as `isPseudo` was. A Z80 pseudo row says which form it stands for ("same as `add a, c`"), from the data the Core already has.
12. **The editor builds the shape from the Cores' facts ([ADR 0052](../adr/0052-instruction-documents-are-built-in-the-editor-from-core-facts.md)).** One adapter per language under `src/lib/documentation/<language>/` turns that language's raw data into the shared shape, and the view reads nothing else. The teaching choices are the editor's, in tables per language beside the category tables, each with a test that covers every mnemonic: operand classes and symbols, legend lines, long names, summaries, row order. The facts about forms come from the Cores: tags, pseudo expansions, the Z80's bytes, cycles and flags. x86's flags from XED go through the existing generator script into `generated/` like the rest of its data.

# Audio: implementation plan

Written on 2026-10-23 after the design interview. The decisions are in [audio.md](./audio.md), the synthesizer and bank in [ADR 0058](../adr/0058-notes-play-on-the-bank-mars-plays-on-jdk-21.md), Undo in [ADR 0059](../adr/0059-undo-takes-back-the-sounds-an-instruction-made.md), the Z80 ports in the 2026-10-23 update of [ADR 0011](../adr/0011-z80-peripherals-through-the-port-map.md), the vocabulary in [CONTEXT.md](../../CONTEXT.md) (**Audio**, **Note**, **Sound**). The plan covers a release of `@specy/mips`, `@specy/risc-v` and `@specy/s68k`, the Audio Peripheral and its browser output, the four adapters, the dock button and Preferences, and the documentation, Lectures and Examples. Nothing is implemented.

## Decisions taken while planning

Taken by default, for the owner to overturn.

1. **One new handler, `midiOut`, required like every other service.** Service 31 calls `midiOut`; service 33 calls `midiOut` and then the existing `sleep` handler for the duration, so the Core itself states the design record's rule that 33 is 31 followed by a 32 of the same length, and the editor's sleep path (the Screen flush, `pauseAtSleep()`, the Testcase's virtual clock) serves 33 without code of its own. `midiOut` may return a Promise, which the Core awaits as it does any handler's, and that is how the first Note holds the program while the bank loads. A host without audio registers a `midiOut` that does nothing. Changed on 2026-10-23 at the owner's word that breaking changes are welcome: the first draft made two optional handlers, `midiOut` and `midiOutSync`, with a fallback in the Core, only to spare other hosts a type change and the Cores a major release; `randomSeed` stays the only optional handler, because only it has a fallback the reference itself defines.
2. **"Loading sounds…" is shown on the dock's speaker button, not in the Screen panel**, amending the design record (confirmed by the owner on 2026-10-23). The button appears at that first sound anyway (decision of the design record), a MARS Note can come from a program with no Screen, the panel can be hidden until Build, and the panel has no status line today. The button shows a spinner and says "Loading sounds…" while the program is held.
3. **A WAV is decoded, a MIDI File is played live.** A WAV becomes an `AudioBuffer` through `decodeAudioData` (3 to 12 ms for half a second in the spike) and plays as an `AudioBufferSourceNode`. A MIDI File plays through a `Sequencer` on a `WorkletSynthesizer` of its own, taken from a pool that grows on demand and keeps its synthesizers for reuse; each holds its own copy of the bank, about 110 ms to set up the first time. At most 4 MIDI Files play at once, inside the cap of 64, one more cutting the oldest one-shot first as the cap does; like the cap it changes only what is heard, since the DirectX tasks answer 1 whether or not an older Sound is cut. Task 74 parses and keeps the File's bytes; 73 and 75 start at once. Changed by the spike on 2026-10-23: the first draft rendered every MIDI File to audio in a Worker, but the spike rendered a three-minute File in 11 to 12 s (15 to 16 times real time) into 64 MB of samples, which would hold a program for seconds; live playback starts within a render quantum. Sharing the Notes' synthesizer between several MIDI Files was ruled out: `Sequencer` has no channel offset, and routing its messages through the main thread would lose its timing.
4. **Each sounding Note has a synthesizer channel of its own**, from a pool of 64 allocated once when the engine loads, each forced melodic with `setDrums(false)` (channels added by `addNewChannel()` start as drum channels), with a program change before its note-on, so Notes stay independent as MARS's sequencer-per-Note makes them. The pool is indexed by Audio itself and never sized from `channelCount`, which double-reports: 48 calls took it from 16 to 112 in the spike. The note-off is scheduled with the note-on through the `time` option, not by a host timer; the spike heard a scheduled release begin on time.
5. **The bank is generated by a committed script and checked in.** `packages/asm-editor/scripts/audio-bank/generate.mjs` runs a small Java program on the JDK 21 that `mise` provides, calling `EmergencySoundbank.createSoundbank()` and saving the SF2; `--check` regenerates and compares bytes. The file and its notice live with the Audio code and are imported with `?url`, so the build content-hashes them into `_app/immutable/` and the service worker caches them like the search model. Committing the 1.9 MB file keeps a JDK out of the editor's build.
6. **Audio sends its changes at the moments the Screen flushes**: before a wait, a sleep or an input read, at the end of a slice, at the program's end. Between two flushes it collects starts and stops and prunes what the cap would cut, which is how a runaway loop costs one message per surviving sound. A Note started mid-slice is heard at most a slice late; a melody paced by sleeps or 33s is exact, since each wait flushes.
7. **`FileSystemSession` gains a whole-File read** for Sounds, a read that changes nothing and so journals nothing, going through the session so a Testcase reads its own isolated Files.
8. **Z80 note registers are journaled by Audio**, not by the Screen: the Audio journal records instrument, volume and duration before a port write that changes them, keyed by `tStateCount` like the rest of ADR 0059's records.
9. **s68k's sound answers become `SoundOutcome = "Done" | "Busy" | "Missing" | "Unplayable"`**, `Done` meaning the task did what it asked (a play started, a load loaded, a stop stopped; named `Played` in the first draft, which fits neither a load nor a stop), following `FileExistence`, for every sound task but 71, whose answer stays empty. It changes a public TypeScript type, so s68k releases a major version, 4.0.0. The CLI keeps ending the run on a sound task: it has no audio to offer.
10. **M68K Examples write their own WAV and MIDI Files with tasks 51 to 54 before playing them.** A playground carries text Files only, and a program that writes a short square-wave WAV and a one-track MIDI File is itself a fair lesson in both formats. The `.asmproj` packer learns `.wav` and `.mid` anyway. The alternative, a base64 companion fence, adds playground machinery for one Example.
11. **Volume is a slider.** `createValue` gains an optional `{min, max, step}`, which `Setting.svelte` renders as a range input; the Preference is a number from 0 to 100, default 50.
12. **Versions:** a required handler changes both Cores' public types, so `@specy/mips` and `@specy/risc-v` release 5.0.0; the 4.4.0 pending for stop-at-sleep can ship before it or fold into it. s68k releases 4.0.0 (decision 9). Breaking changes are welcome (the owner, 2026-10-23), so no decision here is shaped by compatibility. The editor uses the Cores through `workspace:*`, so it needs submodule commits, not registry versions.

### M2: The Audio Peripheral

Plain TypeScript under `src/lib/languages/peripherals/audio/`, constructible under node, no Web Audio:

- `Audio`: the logical state. Notes (pitch, instrument, volume, start, length); Sounds (kind, length, loop) by player; two slot tables of 256; the standard player's current Sound; the cap of 64 with one-shots cut before loops; `stopLoops()` for the program's end; `reset()`; `silent` mode for a Testcase, in which every length is zero and nothing is ever playing. Time comes from the injected `ProgramClock`, read at the point of use.
- Answers in the design record's terms: `playNote`, `playFileSound(path)` / `loadSlot(player, index, path)` / `playSlot(player, index)` / `control(player, index, code)`, each returning the outcome the adapter hands its Core.
- `AudioOutput`: the interface between the logical state and sound, fed by `flush()` (decision 6) with the batch of starts and stops; a `SilentAudioOutput` and a `RecordingAudioOutput` for tests.
- `soundFiles.ts`: header parsing. A WAV is playable when it is RIFF/WAVE with a `fmt ` of integer PCM at 8, 16, 24 or 32 bits or 32-bit float and a `data` chunk; its length is the data bytes over the byte rate. A MIDI File is playable when it begins with an `MThd` of the right size. Everything else is unplayable, with the format named for the Log.
- The journal of ADR 0059: `TerminalHistory`'s pattern, generic over the position, recording the Notes and Sounds an instruction started, the slot entries it replaced and, for the Z80, the note registers (decision 8); `undoAfter(position)` stops what those records started and restores slots, never starting anything.
- Tests: `Audio.test.ts` (busy on Program time with a fake clock, the standard player one at a time, DirectX mixing, loops, `stopLoops`, the cap's order, a flood pruned to one batch, silent mode answers, mute never consulted), `soundFiles.test.ts` (each WAV format, truncated headers, MIDI), `AudioHistory.test.ts` (undo stops only what an instruction started, slot restore, no restart after an undone stop, capacity).

### M3: The browser output

Under the same folder, loaded with a dynamic `import()` so no page pays for it until a program first sounds.

- `WebAudioOutput`: one `AudioContext`, a master `GainNode` for mute and volume, `resume()` on a gesture. The engine (`WorkletSynthesizer`, worklet module and bank, all `?url` assets) loads on the first Note or MIDI File; Notes on per-Note channels (decision 4); WAV Sounds as `AudioBufferSourceNode`s, looping where asked; MIDI Sounds on pooled synthesizers with a `Sequencer` each, `loopCount` for a loop (decision 3).
- Readiness: `whenReady(kind)` resolves when the engine, the bank or a Sound's decoded audio is ready, and rejects when loading fails; the adapters await it on the wait path. A failed load leaves the output silent for the rest of the page and reports once.
- The synthesizer pool for MIDI Sounds (decision 3): created on demand, kept for reuse, at most 4 playing.
- The bank: `scripts/audio-bank/generate.mjs` and its Java program (decision 5), the SF2 and its `NOTICE` naming `EmergencySoundbank.java`, its OpenJDK version and licence, and how to regenerate it.
- Gestures: `WorkbenchSession`'s `build`, `run` and `step` and the Interactive editor's `buildCode`, `startRun` and `stepCode` call `audioOutput.resume()` first; a suspended context resumes on the next `pointerdown` or `keydown` on the page.
- Tests are browser checks (M8) apart from what runs under node with fakes: the gain follows the Preferences, a rejected load becomes one note.

## Implementation risks

- **Autoplay outside Chrome.** Safari resumes an `AudioContext` only inside the gesture's own call stack; `resume()` must be the first thing the click handlers do, before any `await`.
- **The worklet module through the service worker.** `addModule` with an `_app/immutable/` URL should be cached like any asset; the spike saw the bank and the bundle served from the HTTP cache on a warm load, but the app's service worker path is untested until M8.
- **Firefox is unverified.** Headless Firefox 151 on this machine crashes in `AudioContext.resume()` before any spessasynth code runs, with `PULSE_SERVER` set and with `media.cubeb.force_null_context`; it is the environment, but nothing here has played in Firefox yet.
- **Memory.** A slot holds decoded audio, 10 MB a minute at 44.1 kHz stereo; 256 slots per player and the Undo journal's references can add up. If it bites, the journal's slot records count against the FileSystem's byte budget.
- **Synthesizers for MIDI Files** each hold a copy of the bank and run their worklet every render quantum, which is why at most 4 play at once (decision 3); an idle pooled synthesizer should be disconnected so it costs no audio-thread time.
- **TeaVM and two awaited handlers in one syscall.** 33 awaits `midiOut` and then `sleep` inside one `simulate`; both builds, JS and WASM-GC, must park and resume the coroutine twice, which `midi.mjs` covers under `test:wasm`.

### After the review (2026-10-23, evening)

- **Silent channels, found by the Pac-Man Example's session:** channels `addNewChannel` makes start with every controller at 0, volume and expression included, so every Note past the 16th channel was silent. `loadSynthesizerEngine` now resets the Notes synthesizer after adding its 48 channels. Each MIDI Sound's synthesizer gets four ports of channels, reset, before any song loads, since the sequencer would otherwise add a File's extra ports silent too. A reset after a song had loaded could land after its first program changes. Tests pin both orders.
- **A hold on the bank load ends on Stop:** `Audio.reset()` lets every program held by `prepare` go, as the clock's cancel does for a sleep. The Z80 plays a held Note only if the run that asked is still running, and a Breakpoint or the end right after the `out` still waits for the bank.
- **Sound before a read is heard while it waits:** GenericEmulator's read requests, the MARS handlers' `waitOn` and the M68K file dialog flush Audio first.
- **No copy for a retried Sound:** `FileSystemSession.readWhole` hands over the File's own bytes; `Audio.open` reuses a Sound for the same array, compares a different one, and copies only what it keeps.
- The speaker button's `aria-pressed` now means sound on, and the emulator's first audio activity comes from its Audio.

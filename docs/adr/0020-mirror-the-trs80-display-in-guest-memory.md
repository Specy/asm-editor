# Mirror the TRS-80 display in guest memory

The Z80 gets a second Screen mode: the **memory-mapped character display of the TRS-80 Model I/III** at `0x3C00`, with the keyboard matrix at `0x3800`, beside the port-mapped drawing commands of [ADR 0011](./0011-z80-peripherals-through-the-port-map.md). A program stores a byte into video RAM and a character appears, exactly as it does on the machine `@specy/z80` descends from.

ADR 0011 chose ports because a pixel screen does not fit a 64 KB address space and because there was no Z80 convention to preserve. That reasoning still holds for pixels, and it left a gap this closes: the port map is this project's own invention, so nothing written anywhere else draws through it. The TRS-80 display is the one Z80 graphics interface reachable from here that already has software written for it, and it is 1 KB of character cells rather than a framebuffer, which is precisely why memory mapping is affordable. The fork's own submodule carries the machine it comes from — real ROM dumps, real character-generator glyphs, real games — so this is hardware being emulated, not a second interface being designed.

## Consequences

- No Core change is needed, again: `Z80MachineConfig` already offers `onMemoryWrite`, `onMemoryRead` and `onDebugRead`, which is the same seam upstream decodes its own devices on.
- **The two modes are exclusive.** Undo forces it: a memory-backed image is restored by repainting whole cells from memory, which would erase anything the drawing commands had put underneath. In cell mode the drawing commands, the pixel read and the text cursor stop the program with an error naming what is not available, the rule [ADR 0003](./0003-preserve-simulator-graphics-conventions.md)'s unsupported trap tasks already follow.
- **Console output goes only to the Terminal transcript in cell mode**, which is where the single output window of ADR 0003 gives way: the window shows video RAM, and printing on this machine _is_ storing a byte. Having the character port store into video RAM at a cursor was considered and rejected — a device-side store bypasses the Core's journal, so Undo would leave the image and the memory disagreeing. Testcases are unaffected, because they assert on the transcript.
- **Nothing journals**, and the display is restored by re-reading memory after the Core's own rollback, as [ADR 0005](./0005-restore-screen-state-on-undo.md) already requires of the MARS framebuffer. A welcome consequence: in this mode the Z80's Undo depth is the Core's instruction history alone, rather than the smaller of that and what the Screen's byte budget allows.
- The device's memory-write hook **returns false, never true**: the Core stores and journals a write it performed itself, and claiming the write would silently disable Undo for the display.
- **`onDebugRead` falls through to RAM**, so that the memory panel and the disassembler, which read constantly, do not poll the keyboard matrix and eat the program's keystrokes.
- Writes are collected into a dirty cell range and flushed once per execution slice, not painted one store at a time, as `MarsDevices` already does for the bitmap display.
- The display is 64 by 16 cells of 8 by 24 pixels, so the Screen is 512 by 384: the Model III's own geometry, 4:3 as the machine was, and each of the 128 by 48 chunky graphics pixels is 4 by 8. It is monochrome — the pen color is ink and the fill color becomes paper — because the machine was.
- A program asks for the mode with a **`; @screen trs80` comment directive** read at Build, following the MIPS and RISC-V `@screen` directive, or at runtime with screen command 14. The comment is what matters: a program brought in from outside needs that one line added and nothing else. Anything the directive gets wrong is a warning and never an error, because a comment must not stop an assembly.
- Video RAM is filled with `0x20` on the reset path, which is what the ROM's own clear does; zeroed memory would otherwise open on 1024 copies of glyph 0.
- The character-generator glyphs are copied from the submodule (MIT, compatible with this repository's AGPL) into a plain-data module rather than imported, because upstream's font module pulls in the DOM while this one has to load under node and during prerendering.
- **Port 0 is left unmapped, which is why the editor's ports now start at 0x10.** It is the single address where the machine's own IO map and [ADR 0011](./0011-z80-peripherals-through-the-port-map.md)'s port map collided: everything else the TRS-80 decodes is at 0x75, 0x79, 0xB5, 0xB9 or 0xE0 and above. Two of the three games in the fork's own IDE poll the joystick there, and as a character read it suspended them on an input prompt for a line nobody was typing — a hang, which is the worst way to be wrong. Rather than special-case the port by mode, every group moved up by 0x10 (ADR 0011), so an unmapped port 0 floats high on its own: 0xFF, "none attached", which is what upstream's machine returns unconditionally. Games fall back to the keyboard.
- **ROM is out of scope**, so programs that call ROM entry points do not run. Of the three games in the fork's own IDE, two call none at all and one calls two. The documentation has to say this plainly rather than let a user discover it. Cassette, floppy, printer, sound and the timer interrupt are out of scope with it.

## Considered options

- Only the ports, as ADR 0011 decided: no new mode to document, but nothing written elsewhere ever draws, and no blitting idiom — a pixel costs two or three `out`s where a machine store costs one.
- The whole `Trs80` machine from the submodule, ROM and cassette and CRT renderer included: existing games would run outright, but it is a second product beside the teaching editor, with its own canvas and its own screen abstraction, and it contradicts [ADR 0004](./0004-inject-screens-at-emulator-boundary.md).
- A ZX Spectrum framebuffer: a bigger and more colorful corpus, but nothing in this repository implements it, and Spectrum programs lean far harder on ROM routines and IM 1 interrupts, neither of which exists here.

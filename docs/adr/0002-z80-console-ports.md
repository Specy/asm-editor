# Z80 console through I/O ports

Z80 programs reach the **Terminal** peripheral through a small fixed map of I/O ports — `Z80_PORTS` in `src/lib/languages/Z80/Z80-model.ts`, described for the documentation pages, the hover provider and the coding agent's prompt by `Z80_PORT_DOCS` in the same module — instead of the syscall convention every other language in the app uses. A Z80 has no system call instruction: real machines jumped into a monitor ROM with `rst`/`call`, and every machine's ROM was different, so there is no canonical syscall table to copy. `in`/`out` is architectural instead of per-machine, and `@specy/z80`'s `Z80Machine` already routes every port access through its `onPortRead`/`onPortWrite` hooks, so a port map puts the whole console in the adapter with nothing loaded into the guest's address space. There is one port per output format (character, unsigned decimal, signed decimal, hexadecimal, 16 bit) rather than one port plus a format selector, because an `out` carries exactly one byte of payload and the port number is the only other field the instruction encodes — the format has to live in the address. The 16 bit port also reads the high byte of the address bus, which `out (c),r` drives from B, since that is the only way a single `out` can carry a 16 bit value.

## Consequences

- A port read pauses the machine instead of blocking on the answer. `onPortRead` is a synchronous hook, but input answers are asynchronous (a modal prompt today, a terminal widget later — see ADR 0001), and blocking the only thread would freeze the app the way the removed sync prompt did. Returning `undefined` from the hook makes the core roll the `in` back and stop with `WAITING_FOR_INPUT`; the adapter awaits the Terminal, hands the line to the console device and resumes, and the re-executed `in` finds the byte waiting. The pause is therefore an ordinary **Interrupt**: the machine is in a consistent state at an instruction boundary, so it can still be stepped, undone or abandoned while it waits.
- Testcase input is line based, like the other languages. The Terminal's **Input Source** contract answers a request with a whole string — the interactive prompt returns a line and a testcase carries a list of lines — so there is no per-character source to read from. The character port therefore buffers one answered line (terminated with `0x0A`) and hands out one byte per read, and the numeric ports consume one line per read and parse it. A testcase author writes the same input list they would write for MIPS or RISC-V, and does not have to think about how many `in` instructions the program executes.
- Ports outside the map are an empty bus: writes are dropped, reads return `0xFF`. That is what a Z80 sees when no device decodes the address, and it keeps a program that was written for real hardware runnable here with only its unsupported I/O missing, rather than turning an unknown port number into a crash.
- Interrupts are never raised. The console is polled, not interrupt driven: `di`/`ei` and the `im` modes assemble and execute, but nothing in the app ever interrupts the CPU, so an `ei` + `halt` idle loop would wait forever. The adapter therefore treats the core's `WAITING_FOR_INTERRUPT` stop as termination. Keeping the device request/response only also means the port map is the entire I/O contract: no vector table, no interrupt mode to document, and execution history stays a plain sequence of instructions the user can undo.

## Considered options

- A monitor ROM with `rst`/`call` entry points, imitating a real machine: the routines have to occupy the guest's memory, which collides with wherever the user's `.org` puts the program, and the entry addresses would be just as invented as the port numbers while costing the user memory and instructions.
- A syscall-like convention (an operation number in a register plus one trap instruction): the Z80's only trap-shaped instructions are the eight `rst n`, which are calls into low memory and so have the ROM problem above, and the operation number would then duplicate what the port address already carries.
- One data port plus a control port selecting the output format: two `out`s per printed value, a mode the program has to keep in sync with itself, and no gain — the 256 port addresses are far more room than the five formats need.

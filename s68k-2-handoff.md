# Handoff: what changed from `@specy/s68k` 1.4.2 to 2.0

For the agent that will make the asm-editor use `@specy/s68k` 2.0, after the editor's own multi-file rewrite. This is a description of what changed and what is true about 2.0, not a plan for the editor.

Written on 2026-09-08 against the branch `feat/assembler` of https://github.com/Specy/s68k (commit `4868b57` plus the phase 4 work in progress, which adds `include`/`incbin`). The authoritative descriptions are in the repository itself: `ts-lib/dist/index.d.ts` and `ts-lib/src/index.ts` (the surface), `ts-lib/README.md` (usage and the migration table), `src/ts_types.rs` (every plain-object shape, with the Rust type it mirrors), `docs/design/assembler-rewrite.md` (the design record, with the implementation notes of every phase), `CONTEXT.md` (the glossary), `docs/adr/0001` to `0004`, `docs/grammar.md` (the language, rule by rule), `tests/corpus/README.md` (what 1.4.2 did and what 2.0 changed on purpose) and `tests/diagnostics/` (one small program and snapshot per diagnostic kind).

## 1. Status

- Phases 0 to 3 are done, pushed and green on `feat/assembler`: golden fixtures of 1.4.2, the new front end, every EASy68K directive that is in scope, the missing 68000 instructions and addressing modes, and the 2.0 surface for a single file.
- Phase 4 (in progress when this was written) adds `include` and `incbin` over a project of files, a multi-file smoke test and a directory-aware CLI, on the same branch. Its asm-editor step was NOT run; nothing in the asm-editor clone was changed by the s68k work.
- `@specy/s68k` 2.0.0 is not published. The editor pins `1.4.2`. A local build is made with, from the s68k root, `wasm-pack build --out-dir ts-lib/src/pkg --out-name s68k`, then in `ts-lib` `npm run build-lib` and `npm test`; `npm pack` in `ts-lib` gives a `specy-s68k-2.0.0.tgz` that can be installed into the editor with `npm install --no-save <tgz>` until the package is on npm. CI on the branch runs `cargo test`, `cargo doc` with warnings as errors, the wasm build, the TypeScript build and the smoke test.
- The package is still one ESM entry, `dist/index.js` with `dist/index.d.ts`, `type: module`; the wasm is bundled the same way as before.

## 2. The pipeline, in one paragraph

1.4.2 had a regex lexer, a semantic checker and a compiler that disagreed with each other, and errors came out as three shapes (a `SemanticError` class, bare strings from the compiler, `RuntimeError` from the interpreter). 2.0 has one Assembler (`src/assembler/`: tokenizer, parser, symbol table, expression evaluator, instruction table, analyzer, layout) that produces a `Program` and one list of `Diagnostic`s, and the Interpreter runs the `Program`. The parser follows `docs/grammar.md`; the instruction table is the single source of truth for mnemonics, operand rules and sizes; operands are parsed independently of the instruction so that every rejection can say what was found, what is allowed and what was probably meant (ADR 0003). EASy68K is the reference dialect and s68k is a lenient superset of it (ADR 0001).

## 3. The TypeScript surface

### Removed

`new S68k(code)`, `S68k.compile`, `S68k.semanticCheck`, `S68k.lex`, `S68k.lexOne`, `SemanticError` (and `getMessage`, `getLineIndex`, `getMessageWithLine`, `getLine`, `getError`), `CompiledProgram`, `createInterpreter`, the `CompilationResult` type, the `Step` tuple type, the `ParsedLine`/`LexedLine`/`LexedOperand`/`LexedRegisterType` types of the old lexer (the name `ParsedLine` now means the result of `parseLine`, a different shape), the `Label` type (`{name, address, line}`), `getCurrentLineIndex()`, `runWithBreakpoints(Uint32Array)`, `InstructionLine.parsed_line`, `ExecutionStep.line`, `StackFrame.label_line`.

### Added or changed

- `S68k.assemble(source, options?)`: `source` is a string, or `{ files: Record<string, string | Uint8Array>, entry: string }`. Returns `{ diagnostics: Diagnostic[], program?: Program }`; `program` is present exactly when no diagnostic has severity `error`. Live checking is the same call, ignoring `program`. `options.entry` names the file a bare string is filed under (default `main.m68k`, exported as `DEFAULT_ENTRY_PATH`); pass the buffer's real name so diagnostics and locations name it.
- `Program` (a wrapper over the wasm handle): `getInfo(): ProgramInfo` (`entryPoint`, `endAddress`, `instructionCount`, `symbols`), `getEntryPoint()`, `getEndAddress()`, `getInstructionCount()`, `getSymbols(): Record<string, ProgramSymbol>` (`name`, `kind: "label" | "constant" | "variable" | "register_list"`, `value`, `location`; a local label is listed as `global:local`), `dispose()`.
- `new Interpreter(program, options?)`; default options `{keep_history: true, history_size: 100}`. `dispose()` added. Both `Program` and `Interpreter` hold wasm memory: call `dispose()` when done. `assemble` frees its own assembly when it built no program, so checking on every keystroke leaks nothing.
- `Diagnostic` is a plain object: `{ severity: "error" | "warning" | "suggestion", code: string, message: string, hint?: string, location: Location, related: { location: Location, message: string }[] }`. `code` is a stable snake_case name, the thing to match on; `message` says what is wrong, `hint` what to do (absent when there is nothing short to say); `related` points at other places worth looking at (the first definition of a name defined twice, the `include` lines an included file was reached through).
- `Location`: `{ file: string, line: number, column: number, endColumn: number }`. Lines and columns are 0-based; `endColumn` is exclusive; `file` is the root-relative path with `/` separators as given in `files` (or the `entry` option, or `main.m68k`).
- `Breakpoint`: `{ file: string, line: number }`. `runWithBreakpoints(breakpoints: Breakpoint[], limit?)`. A breakpoint is a line of any file of the project; on a comment, a directive or a label alone it stops nothing; on a line of a file included twice it stops at both copies.
- `getCurrentLocation(): Location | null` replaces `getCurrentLineIndex()`. `getCurrentInstructionAddress(): number` added.
- `InstructionLine` (from `getInstructionAt`, `getNextInstruction`, `getLastInstruction`): `{ instruction: any, address: number, size: number, location: Location, includeChain: Location[], source: string }`. `size` is 4 for every instruction for now (see 4.9). `includeChain` is the `include` lines the instruction was reached through, innermost first, empty for the entry file.
- `step()` now returns `InterpreterStatus` (it returned a `[InstructionLine, InterpreterStatus]` tuple); `stepGetStatus()` still exists and does the same. `stepWithInterruptHandler` resolves to the status.
- `ExecutionStep`: `line` replaced by `location?: Location` (absent when the step ran on no source line); `old_sr` and `new_sr` added (the whole status register as a number, processor numbering: system byte then X=16 N=8 Z=4 V=2 C=1); `old_ccr`/`new_ccr` unchanged (`{bits}` in this crate's own flag bits, converted by the wrapper as before).
- `StackFrame`: `label_line` replaced by `label_location?: Location`; `address`, `source_address`, `registers`, `label_name`, `label_address` unchanged.
- `Cpu.getSr()` and `Interpreter.getSr()`: the 16-bit status register, initial value `$2700`. The flags getters (`getFlagsAsArray`, `getFlagsAsBitfield`, `getFlag`, `getConditionValue`) are unchanged.
- `RuntimeError` gained `ChkOutOfBounds {value, bound}`, `OverflowException` (from `trapv`) and `IllegalInstruction`; the existing variants are unchanged.
- `S68k.parseLine(text): ParsedLine`, for hover and highlighting of one line without its file. Never throws, reports no diagnostic. Shape: `{ kind: "blank" | "comment" | "label" | "instruction" | "directive" | "unknown", label?: {name, colon, span}, operation?: {name, size?, nameSpan, sizeSpan?, span, operands: {mode, description, text, span}[], text?: {text, span}}, comment?: {kind: "line" | "explicit" | "bare", text, span} }`. Spans are 0-based character columns with an exclusive end, so they line up with a diagnostic's columns. `mode` is the addressing-mode name (`immediate`, `data_register_direct`, `postincrement`, `pc_displacement`, ...) and `description` the same in English.
- Naming convention: the Assembler's shapes (`Diagnostic`, `Location`, `ParsedLine`, `ProgramInfo`, `InstructionLine`) are camelCase; the Interpreter's shapes keep 1.4.2's snake_case (`old_ccr`, `source_address`, `keep_history`, `label_name`). A Location nested in an interpreter shape is still camelCase.
- Unchanged: `Interrupt` and `InterruptResult` (every trap task and its payload), `InterpreterOptions`, `MutationOperation`, `Flags`, `Condition`, `Size`, `RegisterOperand`, `Flag`, `ccrToFlags`, `ccrToFlagsArray`, `RegisterType`, `Register`, `Cpu` (plus `getSr`), `answerInterrupt`, `run`, `runWithLimit`, `runWithInterruptHandler`, `undo`, `canUndo`, `getUndoHistory`, `getLastStepId`, `getPreviousMutations`, `getCallStack`, `readMemoryBytes`, `writeMemoryBytes`, `getRegisterValue`, `setRegisterValue`, `getPc`, `getSp`, `hasTerminated`, `hasReachedBottom`, `getStatus`, `getCurrentInterrupt`, `getCpuSnapshot`.

### The editor's current references to the removed API (facts, for the checklist)

`src/lib/languages/M68K/M68KEmulator.svelte.ts` (`S68k.semanticCheck`, `new S68k(code)`, `createInterpreter`, `runWithBreakpoints(Uint32Array)`, `parsed_line.line_index`, `parsed_line.line`, `semanticErrorToDiagnostic` with `SemanticError`, the column computed from indentation), `src/lib/languages/M68K/M68K-language.ts` (`S68k.lexOne(line).parsed` in the hover provider), `src/lib/languages/M68K/M68KEmulator.test.ts` (42 tests on the old shapes), `src/components/specific/project/user-tools/MutationStep.svelte` (`ccrToFlagsArray`, which still exists), and the shared `Diagnostic` type in `src/lib/languages/commonLanguageFeatures.svelte.ts` (`lineIndex`, `column`, `line: {line, line_index}`, `message`, `formatted`, no file). The editor's `CONTEXT.md` says "s68k has no warnings concept"; that is no longer true.

## 4. What the language does differently (visible to users, documentation, hover, completion, examples)

1. **Labels** (asm-editor#15 closed): an identifier followed by `:` anywhere on the line, or an identifier in column 1 that is not a mnemonic or directive name, is a label. Instructions may still start in column 1. A label named exactly like a mnemonic needs the colon. Local labels `.name` exist, scoped between two global labels, listed as `global:local`.
2. **Comments**: `*` or `;` first on a line, `;` anywhere, and EASy68K's bare comment field (`move.b #23,d0    trap task 23`) is accepted; the first bare comment in a file gets a `suggestion` to use `;`. The operand field ends at whitespace not adjacent to a comma, so `d0, d1` and `d0 ,d1` keep working and `#2 * 3` ends the operand at `#2` (a warning explains it). `*` inside an expression is the current address (`lea *,a0`, `org (*+1)&-2` work); it is a comment marker only at line start or after a complete operand field.
3. **Expressions**: EASy68K's operators verbatim (`+ - * / \ & ! | ^ << >> ~`, unary `-`, `*` as current address, `$ % @` prefixes, `'a'`/`'ab'` up to four characters, `''` for a quote) with EASy68K's precedence (shifts, then bitwise, then `* / \`, then `+ -`). `**` no longer means power (in EASy68K `2**3` is `2 * (current address) * 3`). Values are evaluated in 64 bits and range-checked against the operand size.
4. **Symbols**: `equ` names a value once; `set` a value that may be redefined; `reg` a register list for `movem`; labels are addresses. `equ` is no longer a text substitution: `ten equ #10` and `r equ d1` are errors with a rewrite hint. Forward references are allowed in instruction operands and `dc` data and refused where the value decides the layout (`org`, `ds`, `dcb` counts, `equ`, `set`). Names are case sensitive; mnemonics, directives, registers and sizes are not.
5. **Directives** now: `org` (anywhere, backwards too), `equ`, `set`, `dc`, `dcb`, `ds` (reserves and writes nothing; 1.4.2 wrote a wrong number of zeros), `end expr` (entry point; lines after it are ignored with one warning), `reg`, `fail [message]` (an error with that text), `simhalt` (a 4-byte item that ends the run like task 9), `section 0..15` (sixteen location counters), `offset expr` (labels as offsets, no bytes, until `org`), `include`, `incbin`; `opt`, `list`, `nolist`, `page` are accepted and ignored. `memory`, `macro`/`endm`/`mexit`, `ifxx`/`endc` and the structured-control keywords (`if`/`endi`, `while`/`endw`, `repeat`/`until`, `for`/`endf`, `dbloop`/`unless`) are recognised and refused with a diagnostic that names the feature; a macro invocation is reported as such, not as an unknown mnemonic.
6. **Entry point**: the `end` operand, else a label named `START`, else the first instruction. `end START` with a label written `start` finds it, with a warning about the case (`entry_point_case_mismatch`).
7. **Instructions added**: `move`/`andi`/`ori`/`eori` to and from `sr` and `ccr`; `movep`; `tas`; `rtr`; `chk`, `trapv`, `illegal` (end the run with an exception and a new `RuntimeError` variant); `addx`, `subx`, `negx`, `roxl`, `roxr`; `abcd`, `sbcd`, `nbcd`; `extb.l`; `cmpm` written as `cmp (a0)+,(a1)+`. Still refused with a reason: `rte`, `stop`, `reset`, `move usp`. SR: the program always runs as supervisor; the high byte of SR is stored and readable but has no effect.
8. **Addressing modes added**: PC-relative `d16(pc)`, `(d16,pc)`, `label(pc)`, `d8(pc,xn.size)`, `(d8,pc,xn)`; absolute `label.w` / `label.l` (same address, the `.w` form range-checked at 16 bits); EASy68K's parenthesised spellings `(d16,an)`, `(d8,an,xn.w)`, `(an,xn)`. Branch sizes `.s`/`.b`/`.w`/`.l` are accepted (1.4.2 refused `bra.s`), not range-checked. Sizes the EASy68K help lists are accepted where 1.4.2 refused them (`moveq.l`, `lea.l`, `divs.w`, `dbra.w`, `scc.b`, `asr.w (a0)`, `btst.b`...). Some things 1.4.2 accepted are refused now because the 68000 has no such form: `tst a0`, `jmp (a0)+`, `lea (a0)+,a1`, `movem` with the wrong direction of `(an)+`/`-(an)`, a bit number or shift count read from memory, a bit number above the destination's width. `moveq` takes -128 to 255. The full list is in `tests/corpus/README.md`, "What the instruction table of the rewrite accepts and refuses differently".
9. **Layout**: every instruction is still 4 bytes (real sizes are a later decision; `InstructionLine.size` is there so that the editor does not assume 4). Word and long data and instructions are aligned to even addresses (a `dc.w` after an odd `dc.b` is padded; 1.4.2 did not); an odd `org` warns and rounds up; two lines laid out over the same address are an error. The default origin is `$1000`. Memory starts as `$ff` (unchanged).
10. **Characters** (ADR 0004): one byte, Latin-1, everywhere: `dc.b 'è'` is one byte; a source character above code 255 is an assembly error (`character_above_latin1`, with a hint for typographic quotes and dashes); bytes shown through the display tasks decode as Latin-1 (the old "expected UTF-8" runtime error is gone); a character above 255 typed into `ReadChar`/`ReadKeyboardString` cannot be stored, so the host has to refuse or replace it before answering.
11. **The EASy68K originals** in the editor's `examples/m68k/easy68k/` now assemble apart from their macros, structured control and the traps this editor rejects; the remaining diagnostics on them are `unimplemented_operation` (plus one `bare_comment` suggestion and one `entry_point_case_mismatch` warning). The editor's `examples/m68k/README.md` says they do not assemble; that paragraph is out of date.
12. **All 30 editor programs** (the 24 lecture playgrounds and the 6 `examples/m68k/*.x68`) assemble to the same program as with 1.4.2, byte for byte, apart from the `ds` fix; this is asserted by fixtures in `tests/corpus/`.

## 5. Diagnostics, in detail

- Severities: `error` blocks the build; `warning` and `suggestion` come back together with a program. Assembly continues after an error as far as it can, so one build reports every problem, and a live check reports the same list.
- Warnings today: `odd_origin`, `character_literal_too_long`, `constant_above_32_bits`, `code_after_end`, `end_without_an_address`, `entry_point_case_mismatch`, `expression_split_by_space`, `missing_comma_between_operands`. Suggestions today: `bare_comment` (once per file), `space_before_comma`, `double_quoted_string` (once per file), `bare_number_as_address` (a bare number below the origin where `#` was probably meant), `mnemonic_used_as_label`.
- Errors, grouped: lexical (`unexpected_character`, `non_breaking_space`, `character_above_latin1`, `unterminated_string`, `invalid_number`, `number_too_large`, `dot_in_name`, `unknown_size_suffix`, `plus_is_not_a_unary_operator`, `star_is_the_current_address`); line structure (`empty_label`, `two_labels_on_one_line`, `operation_expected`, `unclosed_parenthesis`, `nesting_too_deep`, `malformed_operand`, `unexpected_token_in_operand`, `operand_expected`, `expression_expected`, `value_expected`, `register_in_expression`, `register_list_in_expression`, `register_list_expected`, `register_range_out_of_order`, `reserved_name_as_symbol`); instruction analysis (`unknown_mnemonic` with a did-you-mean and the label hint, `unimplemented_operation` with the reason, `unimplemented_addressing_mode`, `invalid_addressing_mode` naming position, found and allowed, `invalid_operand_pair`, `both_operands_in_memory`, `wrong_operand_count`, `invalid_size`, `address_register_byte_size`, `immediate_out_of_range`, `value_out_of_range`, `invalid_address_width`); symbols and expressions (`undefined_symbol`, `symbol_already_defined` with the first definition in `related`, `forward_reference_not_allowed`, `division_by_zero`, `not_a_register_list`, `register_list_not_defined_yet`); directives and layout (`directive_needs_a_label`, `label_not_allowed`, `address_used_twice` with the first placement in `related`, `no_bytes_in_an_offset_region`, `user_defined_error` from `fail`, `unterminated_macro_definition`); files (`unreadable_file` with the closest existing path as hint, `include_cycle` showing the chain, `include_too_deep`, `end_in_an_included_file`). The definitive list is the `code()` table in `src/assembler/diagnostics.rs` and the case files in `tests/diagnostics/`.
- The notation of allowed addressing modes in messages is the one 1.4.2 used (`Dn`, `An`, `(An)`, `(An)+`, `-(An)`, `d(An)`, `d(An,Xn)`, `Ea/<label>`, `Im`, `<register list>`), so any documentation that quotes it still matches.
- A diagnostic raised in an included file has that file in `location` and the include lines in `related` (message `included from \`main.x68\``, innermost first).

## 6. Projects of several files (phase 4)

- `files` keys are root-relative paths with `/` separators (the same notion as the editor's Project Files); values are text (`string`) or bytes (`Uint8Array`). `entry` is the path assembled first; every other file is reached from it through `include` or `incbin` or is not read at all. Nothing opens a disk.
- `include 'path'`: textual, as in EASy68K: the lines are assembled as if pasted at the include line (same section, same address, one symbol namespace, local-label scopes running across the boundary, `set` seeing the latest definition above it in the assembled order). A label on the include line names the first included byte. Paths resolve relative to the including file's directory first, then the project root; `\` is normalised to `/`; quotes are optional, single or double. A file included twice is assembled twice, and the duplicate-symbol errors that causes say so. A cycle is an error showing the chain; a depth limit is the backstop. `end` inside an included file is an error. `include` of a binary file is an error pointing at `incbin`; a binary entry file is `unreadable_file`.
- `incbin 'path'`: the file's bytes at the current address, as a `dc.b` of the whole file would place them; a text file contributes its Latin-1 bytes; a label on the line names the first byte.
- Every instruction of the program carries its own `location` (file, line, columns) and its `includeChain`; the current location, breakpoints, undo steps and stack frames use the same `Location`. A file included twice has one location per line and two addresses; the chain tells the copies apart.
- The editor's current shared model keeps one `line` number and `breakpoints: number[]` for the entry file only, and the design record lists as an open question what to do with a location in another file while the UI cannot show it (the s68k side has no opinion; the design record's suggestion was to attach it to the include line, with the file name in the message, until multi-file editing exists).

## 7. Open questions recorded for the owner

From `docs/design/assembler-rewrite.md`: whether to show SR (the inert high byte) anywhere in the editor; how locations in files other than the one shown are presented until multi-file editing exists; the release steps (publish `@specy/s68k` 2.0.0, then `npm install @specy/s68k@2.0.0` in the editor so that its lock file resolves); real instruction sizes later; macros and conditional assembly maybe later, structured control not planned.

## 8. Where each fact can be checked

- The surface: `ts-lib/dist/index.d.ts` after a build, or `ts-lib/src/index.ts` and `src/ts_types.rs`.
- Concrete calls: `ts-lib/test/smoke.mjs` (single file, status register, breakpoints on a located file, a four-file project with `include` and `incbin`, a diagnostic inside an included file).
- What a message says: `tests/diagnostics/<code>.asm` and its snapshot under `tests/diagnostics/snapshots/`.
- The language: `docs/grammar.md`; the decisions and their reasons: `docs/adr/*.md`; the vocabulary: `CONTEXT.md`.
- What changed against 1.4.2 program by program: `tests/corpus/README.md` and `tests/corpus/snapshots/`.
- The CLI for quick checks: `cargo run -- path/to/file.x68` prints diagnostics as `file:line:column: severity: message` with hints and related locations, then runs the program; `--show-program` lists the assembled instructions with addresses and locations.
